Cloud Architexcture Termilogies

## What is a Solutions Architect?

A role in a technical organization that architects a technical solution using multiple systems via researching, documentation, experimentation.

## What is a Cloud Architect?

A solutions architect that is focused solely on architecting technical solutions using cloud services.

A cloud architect need to understand **the following terms** and factor them into their designed architecture based on the business requirements.

* **Availability** - Your ability to ensure a service remains available eg. **Highly Available (HA)**
* **Scalability** - Your ability to grow rapidly or unimpeded
* **Elasticity** - Your ability to shrink and grow to meet the demand
* **Fault Tolerance** - Your ability to prevent a failure
* **Disaster Recovery** - Your ability to recover from a failure eg. **Highly Durable (DR)**

A Solutions Architect needs to always consider the following business factors:


## High Availability

Your ability for your service to **remain available** by ensuring there is **no single point of failure** and/or ensure a certain level of performance.

### Elastic Load Balancer

A load balancer allows you to evenly distribute traffic to multiple servers in one or more datacenters. If a datacenter or server becomes unavailable (unhealthy), the load balancer will route the traffic to only available datacenters with servers.

Running your workload across multiple **Availability Zones** ensures that if 1 or 2 **AZs** become unavailable your service / applications remains available.

## High Elasticity

Your ability to **automatically increase or decrease your capacity** based on the current demand of traffic, memory and computing power.

### Auto Scaling Groups (ASG)

**Auto Scaling Groups (ASG)** is an AWS feature that will automatically **add or remove servers** based on scaling rules you define based on metrics.

### Horizontal Scaling

* **Scaling Out** — Add more servers of the same size
* **Scaling In** — Removing underutilized servers of the same size

Vertical Scaling is generally hard for traditional architecture, so you’ll usually only see **horizontal scaling** described with Elasticity.

## Highly Fault Tolerant

Your ability for your service to ensure there is **no single point of failure**. **Preventing the chance of failure.**

### Failover

Fail-over is when you have a plan to **shift traffic to a redundant system** in case the primary system fails.

### RDS Multi-AZ

**RDS Multi-AZ** is when you run a duplicate standby database in another **Availability Zone** in case your primary database fails.

A common example is having a copy (**secondary**) of your database where all ongoing changes are synced. The secondary system is **not in-use until a failover occurs**, and it becomes the primary database.

```text
                    HIGHLY FAULT TOLERANT

                         Application
                              │
                              ▼
                    ┌─────────────────┐
                    │     Primary     │
                    │    Database     │
                    └────────┬────────┘
                             │
                         Sync │
                             ▼
                    ┌─────────────────┐
                    │    Secondary    │
                    │    Database     │
                    │     (Standby)   │
                    └─────────────────┘
                             
                 Primary Database Fails ❌
                              │
                              ▼
                         FAILOVER
                              │
                              ▼
                    Traffic shifts to
                    the Secondary DB
                              │
                              ▼
                    ┌─────────────────┐
                    │    Secondary    │
                    │   becomes the   │
                    │     PRIMARY     │
                    └─────────────────┘
```

### Easy way to remember

```text
Fault Tolerance = Prevent / handle failure
Failover        = Shift to backup when primary fails
RDS Multi-AZ    = Primary DB + Standby DB in another AZ
```

## High Durability

Your ability to **recover from a disaster** and to prevent the **loss of data**.

Solutions that recover from a disaster are known as **Disaster Recovery (DR)**.

### Important Questions

* Do you have a backup?
* How fast can you restore that backup?
* Does your backup still work?
* How do you ensure current live data is not corrupt?

### CloudEndure Disaster Recovery

**CloudEndure Disaster Recovery** continuously replicates your machines into a low-cost staging area in your target AWS account and preferred Region, enabling fast and reliable recovery in case of IT data center failures.

```text id="durability-dr"
                 │  DR / STAGING    │
                 │      AREA        │
                 │   (Low Cost)     │
                 └────────┬─────────┘
                          │
                    DISASTER ❌
                          │
                          ▼
                    ┌───────────┐
                    │  RECOVER  │
                    │   / DR    │
                    └─────┬─────┘
                          │
                          ▼
                 ┌──────────────────┐
```


## Business Continuity Plan (BCP)

A **Business Continuity Plan (BCP)** is a document that outlines how a business will **continue operating during an unplanned disruption in services**.

### Recovery Point Objective (RPO)

The **maximum acceptable amount of data loss** after an unplanned data-loss incident, expressed as an amount of time.

👉 **Question to ask:**
**"How much data are you willing to lose?"**

Example: If your RPO is **1 hour**, you can tolerate losing up to **1 hour of data**.

### Recovery Time Objective (RTO)

The **maximum amount of downtime** your business can tolerate without incurring a significant financial loss.

👉 **Question to ask:**
**"How much time are you willing to go down?"**

Example: If your RTO is **2 hours**, your service should be restored within **2 hours**.

```text
                 BUSINESS CONTINUITY PLAN (BCP)

        ←────────────── TIME ──────────────────────────→

        Data Loss                    Downtime
           │                            │
           │                            │
           ▼                            ▼
──────────●───────────────🔥────────────●─────────────────►
          ↑                            ↑
         RPO                           RTO
    Recovery Point                Recovery Time
     Objective                     Objective

          │            DISASTER            │
          │                🔥              │
          │                                │
          └── How much data          How much time
              can we lose?            can we be down?
```

### Easy way to remember

```text
RPO = DATA
     "How much data can I afford to lose?"

RTO = TIME
     "How long can I afford to be down?"

RPO → Data Loss
RTO → Downtime
```

**Example:**

```text
Disaster happens at 12:00 PM

RPO = 1 hour
→ Maximum acceptable data loss = 1 hour
→ You should have recoverable data from around 11:00 AM

RTO = 2 hours
→ Maximum acceptable downtime = 2 hours
→ Service should be restored by 2:00 PM
```

## Disaster Recovery Options

There are multiple options for recovery that **trade cost vs. time to recover**.

As you move from **Backup & Restore → Pilot Light → Warm Standby → Multi-site Active/Active**, the **cost increases**, but the **time to recover decreases**.

```text
                 DISASTER RECOVERY OPTIONS

LOW COST                                           HIGH COST
   │                                                   │
   ▼                                                   ▼

┌────────────────┐   ┌────────────┐   ┌────────────┐   ┌──────────────────┐
│ Backup &       │ → │ Pilot      │ → │ Warm       │ → │ Multi-site       │
│ Restore        │   │ Light      │   │ Standby    │   │ Active/Active    │
└────────────────┘   └────────────┘   └────────────┘   └──────────────────┘
       │                   │                │                    │
       ▼                   ▼                ▼                    ▼
    Hours               ~10 mins         Minutes             Real-time
    RPO/RTO              RPO/RTO          RPO/RTO              RPO/RTO
```

### 1. Backup & Restore

You **backup your data** and restore it to new infrastructure after a disaster.

* Lower priority use cases
* Restore data after event
* Deploy resources after event
* **Cost: $**

```text
BACKUP → DISASTER → CREATE INFRASTRUCTURE → RESTORE DATA → RUN
```

---

### 2. Pilot Light

Data is **replicated to another Region** with minimal services running.

* Less stringent RTO & RPO
* Core services running
* Start and scale resources after event
* **Cost: $$**
* RPO/RTO: **~10 minutes**

```text
PRIMARY REGION              DR REGION
     │                          │
     │── Replicate Data ──────►│
     │                          │
   RUNNING                  MINIMAL SERVICES
                                │
                         DISASTER OCCURS
                                │
                                ▼
                         START & SCALE UP
```

---

### 3. Warm Standby

A **scaled-down copy of your infrastructure** is already running and ready to scale up.

* Business-critical services
* Scale resources after event
* **Cost: $$$**
* RPO/RTO: **Minutes**

```text
PRIMARY REGION              DR REGION
     │                          │
  FULL SIZE                SMALL / SCALED DOWN
     │                          │
     │────── Replication ──────►│
                                │
                         DISASTER OCCURS
                                │
                                ▼
                           SCALE UP
```

---

### 4. Multi-site Active/Active

A **scaled-up copy of your infrastructure** is running in another Region.

* **Zero downtime**
* **Near-zero data loss**
* Mission-critical services
* **Cost: $$$$**
* RPO/RTO: **Real-time**

```text
                 TRAFFIC
                    │
              ┌─────┴─────┐
              ▼           ▼
        ┌──────────┐ ┌──────────┐
        │ REGION 1 │ │ REGION 2 │
        │  ACTIVE  │ │  ACTIVE  │
        └──────────┘ └──────────┘
              ▲           ▲
              └───SYNC────┘

       Both regions serve traffic
              simultaneously
```

### Easy way to remember

```text
                    COST ↑
                         │
Backup & Restore  ───────┼───────  Cheapest / Slowest
                         │
Pilot Light       ───────┤
                         │
Warm Standby      ───────┤
                         │
Multi-site        ───────┼───────  Most Expensive / Fastest
Active/Active             │
                         │
                    RECOVERY TIME ↓
```

**Exam shortcut:**

| Option                       | RPO/RTO   | Infrastructure   | Cost |
| ---------------------------- | --------- | ---------------- | ---- |
| **Backup & Restore**         | Hours     | Nothing running  | $    |
| **Pilot Light**              | ~10 mins  | Minimal services | $$   |
| **Warm Standby**             | Minutes   | Scaled-down      | $$$  |
| **Multi-site Active/Active** | Real-time | Full-sized       | $$$$ |

**Think:**

> **More infrastructure running → Faster recovery → Higher cost**


## RTO — Recovery Time Objective

**Recovery Time Objective (RTO)** is the **maximum acceptable delay between the interruption of a service and the restoration of that service**.

In simple terms:

> **RTO = How long can the business afford to have the service DOWN?**

The acceptable recovery time is **defined by the organization** based on its business requirements.

## RPO — Recovery Point Objective

**Recovery Point Objective (RPO)** is the **maximum acceptable amount of time since the last data recovery point**.

In simple terms:

> **RPO = How much data can the business afford to LOSE?**

It determines the acceptable amount of data loss between the **last recovery point** and the **service interruption**.

### RPO Diagram

```text
                         RPO — RECOVERY POINT OBJECTIVE

Cost &
Complexity
    ▲
    │
    │  ● Multi-Site Active/Active
    │   \
    │    \
    │     \
    │      ● Warm Standby
    │      │
    │      │
    │      ● Pilot Light
    │       \
    │        \
    │         ● Backup & Restore
    │
    │──────────────────────────────────────  Acceptable Recovery Cost
    │
    └──────────────────────────────────────────────►
       │
       │
       │ Recovery Point Objective
       │
       ▼
   Data Loss before Service Interruption
```

### Think of RPO as a timeline

```text
              LAST RECOVERY POINT
                       │
                       │
                       ▼
───────────────────────●───────────────────────🔥──────►
                       │                         │
                       │◄─────── RPO ──────────►│
                                                 │
                                              DISASTER
                                           / INTERRUPTION

                    DATA THAT COULD BE LOST
```

### Example

Suppose your database is backed up every **4 hours**:

```text
Backup             Backup              Disaster
  │                   │                    │
  ▼                   ▼                    ▼
10 AM ─────────────── 2 PM ─────────────── 5 PM
                         ◄──── RPO ───────►
                              3 hours
```

If the disaster happens at **5 PM**, the latest recovery point is **2 PM**.

So you could potentially lose the data created between **2 PM and 5 PM**.

### RPO vs RTO

```text
RPO = DATA
      ↓
"How much data can I afford to lose?"

RTO = TIME
      ↓
"How long can my service be DOWN?"
```

**Exam shortcut:**

> 🟢 **RPO → Recovery Point → Data Loss**
> 🔵 **RTO → Recovery Time → Downtime**

AWS specifically lists draw.io among tools for creating AWS architecture diagrams, and draw.io has AWS shape libraries and templates built in. ([Amazon Web Services, Inc.][1])

[Open draw.io AWS diagram tutorial](https://www.drawio.com/docs/diagram-types/aws-diagrams/?utm_source=chatgpt.com)

### Your workflow should be:

```text
Learn AWS service
       ↓
Understand how it connects
       ↓
Draw architecture
       ↓
Explain traffic flow
       ↓
Identify failure points
       ↓
Improve architecture
```

# 9. Official AWS resources you should use

### AWS Architecture Icons

Get the official AWS icons here. AWS updates its icon packages periodically, so use the current set rather than old icon libraries. ([Amazon Web Services, Inc.][1])

[AWS Architecture Icons](https://aws.amazon.com/architecture/icons/?utm_source=chatgpt.com)

### AWS Architecture Center

This is probably the **best resource for studying real architectures**.

It contains reference architectures, diagrams, Well-Architected guidance and decision guides. ([Amazon Web Services, Inc.][2])

[AWS Architecture Center](https://aws.amazon.com/architecture/?utm_source=chatgpt.com)

### AWS diagram design guide

AWS has a newer guide explaining how to build diagrams from foundational components such as:

```text
AWS Account
    ↓
Region
    ↓
VPC
    ↓
Availability Zones
    ↓
Subnets
    ↓
Networking
    ↓
Application Services
    ↓
Database / Storage
```

It also recommends separating architecture into logical layers to keep diagrams readable. ([AWS Builder Center][3])

[AWS guide — How to Design Better Architecture Diagrams](https://builder.aws.com/content/3DttzYU07FWj09CqNczGbfSnYF4/how-to-design-better-aws-architecture-diagrams?utm_source=chatgpt.com)
