# 🔐 Identity Providers (IdPs)

## 1. Definition

An **Identity Provider (IdP)** is a system that **creates, maintains, and manages identity information** for users (principals) and provides authentication services to applications within a **federation or distributed network**.

Simple idea:

> **IdP = The trusted system that verifies who you are.**

For example, when you choose **“Sign in with Google”** on another website, Google can act as the Identity Provider.

The screenshot gives examples such as:

* Facebook
* Amazon
* Google
* Twitter
* GitHub
* LinkedIn

---

# 2. What Does an IdP Do?

An IdP primarily manages identity information and provides authentication.

A simplified flow:

```text
User
  ↓
Application
  ↓
"Who are you?"
  ↓
Identity Provider
  ↓
Authenticate user
  ↓
Application grants appropriate access
```

Instead of every application maintaining a completely separate identity for the same user, identity can be provided through a trusted IdP.

---

# 3. Federated Identity

The screenshot defines **federated identity** as:

> A method of linking a user's identity across multiple separate identity management systems.

Think:

```text
Google Account
      ↓
Federated Identity
      ↓
Website A
Website B
Website C
```

You can use an identity managed by one system to authenticate to another service.

### Scenario

You visit an application and see:

**"Continue with Google"**

You authenticate with Google rather than creating a separate username/password specifically for that application.

---

# 4. OpenID

### Definition

The screenshot describes **OpenID** as an open standard and decentralized authentication protocol.

Its main focus is:

> **"Who are you?"**

So OpenID is associated with **authentication / identity**.

Example from the screenshot:

```text
Google Account
      ↓
OpenID
      ↓
Authenticate
      ↓
Another platform
```

### Memory

> **OpenID → Identity**

---

# 5. OAuth 2.0

### Definition

The screenshot describes **OAuth 2.0** as an industry-standard protocol for **authorization**.

It uses **authorization tokens** rather than sharing password data between consumers and service providers.

The key phrase from your source:

> **OAuth is about granting access to functionality.**

### Example

Imagine an application wants permission to access something from another service.

Instead of giving the application your password:

```text
❌ Application → Your password
```

OAuth uses a token:

```text
Application
     ↓
Authorization
     ↓
Access token
     ↓
Allowed functionality
```

### Memory

> **OAuth → Authorization / Access**

---

# 6. SAML

### Definition

**SAML = Security Assertion Markup Language**

The screenshot describes SAML as an **open standard for exchanging authentication and authorization information between an Identity Provider and a Service Provider**.

One of its important use cases is:

> **Single Sign-On (SSO) via a web browser**

---

## SAML SSO Example

Imagine a company uses an identity provider for employees.

```text
Employee
   ↓
Company IdP
   ↓
Authenticate
   ↓
SAML assertion
   ↓
Application
   ↓
Access granted
```

The employee doesn't necessarily need to create a separate login for every application.

---

# 🔥 OpenID vs OAuth vs SAML

This is the part I'd memorize for your exam:

| Technology    | Main idea                                                         |
| ------------- | ----------------------------------------------------------------- |
| **OpenID**    | Authentication / identity                                         |
| **OAuth 2.0** | Authorization / granting access                                   |
| **SAML**      | Authentication & authorization information exchange, commonly SSO |

### Very simple memory:

```text
OpenID
  ↓
WHO ARE YOU?

OAuth
  ↓
WHAT CAN YOU ACCESS?

SAML
  ↓
SSO / IDENTITY INFORMATION EXCHANGE
```

# 🎯 Scenario

Suppose your company has an internal application.

An employee opens it:

```text
Employee
   ↓
Application
   ↓
Redirect to IdP
   ↓
Employee authenticates
   ↓
IdP provides identity information
   ↓
Application
   ↓
Access
```

If the organization uses **SAML**, it can be used to support browser-based **Single Sign-On**.

If another application needs delegated access to functionality without receiving the user's password, **OAuth 2.0** can be used.
