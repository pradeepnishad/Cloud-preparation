# 🔐 AWS Shared Responsibility Model

The **AWS Shared Responsibility Model** explains **how security responsibilities are divided between AWS and the customer** when using AWS Cloud services.

The most important sentence to remember is:

> **AWS is responsible for security OF the cloud, while the customer is responsible for security IN the cloud.**

However, the exact division depends on the **AWS service being used**.

---

## 1. What Does "Shared Responsibility" Mean?

When you use AWS, there are two sides:

```text
              AWS CLOUD
                  │
       ┌──────────┴──────────┐
       │                     │
      AWS                 CUSTOMER
       │                     │
 Security OF             Security IN
 the Cloud               the Cloud
```

AWS protects the underlying cloud infrastructure.

You protect your resources, data, applications, identities, and configurations within that infrastructure.

---

# 2. AWS Responsibility — Security OF the Cloud

AWS is responsible for protecting the infrastructure that runs AWS services.

This includes things such as:

```text
AWS
│
├── Physical data centers
├── Physical servers
├── Physical storage
├── Physical networking
├── Hardware
└── Underlying virtualization infrastructure
```

### Example

You don't have to physically secure an AWS data center.

AWS handles things such as:

* Physical access controls
* Data-center infrastructure
* Physical hardware
* Underlying networking
* Replacement/maintenance of AWS hardware

### Memory:

> **AWS secures the building and the infrastructure.**

---

# 3. Customer Responsibility — Security IN the Cloud

The customer is responsible for appropriately securing and configuring what they run or store in AWS.

This can include:

```text
Customer
│
├── Data
├── IAM users/roles
├── IAM permissions
├── Applications
├── Security configuration
├── Network configuration
└── Guest operating system
```

The exact responsibilities depend on the service.

---

# 4. Example: EC2

Suppose you launch a Windows Server EC2 instance.

```text
             EC2
              │
      ┌───────┴───────┐
      │               │
     AWS           Customer
      │               │
 Physical          Windows OS
 server             Application
 Hardware           Data
 Network            IAM
 Virtualization     Security configuration
```

### AWS manages:

* Physical server
* Physical networking
* Data center
* Hardware
* Underlying virtualization

### Customer manages:

* Guest operating system
* OS configuration
* OS patches
* Applications
* Data
* IAM permissions
* Security group configuration

So if your EC2 Windows Server has an application vulnerability, AWS isn't responsible for fixing your application.

---

# 5. Example: Amazon S3

Suppose you store company files in S3.

AWS provides the underlying S3 infrastructure.

But you still need to configure access appropriately.

```text
Customer
   ↓
S3 Bucket
   ↓
Permissions
   ↓
Who can access data?
```

You are responsible for things such as:

* Appropriate access permissions
* IAM policies
* Data protection configuration
* Encryption choices/configuration where applicable
* Appropriate bucket access settings

### Example

If you accidentally configure your data to be accessible to unintended users, that's generally a **customer-side configuration responsibility**.

---

# 6. Example: IAM

IAM is particularly important.

Suppose you create:

```text
IAM User
   ↓
IAM Policy
   ↓
Permissions
```

You are responsible for deciding what permissions that identity should have.

For example:

```text
Developer
   ↓
S3
   ↓
Only required permissions
```

This is the **principle of least privilege**.

Therefore:

> **Managing your IAM identities and permissions is a customer responsibility.**

---

# 7. Example: Security Groups

Suppose you create an EC2 web server.

You configure its security group:

```text
Inbound
TCP 443
   ↓
HTTPS
```

AWS provides the security-group functionality.

But **you are responsible for configuring the rules appropriately**.

For example:

```text
❌ Unnecessarily broad access
```

could expose your resource.

Therefore:

> **Security group configuration is a customer responsibility.**

---

# 8. Responsibility Changes With the Service

This is one of the most important concepts.

AWS doesn't manage every service at the same level.

Compare:

### EC2

You manage the guest OS.

```text
EC2
AWS → Physical infrastructure
Customer → OS + application + data
```

### RDS

AWS manages much more of the underlying database infrastructure and platform.

```text
RDS
AWS → Infrastructure + managed database platform
Customer → Data + access + appropriate configuration
```

So:

> **The more managed the service, the more infrastructure management AWS takes on.**

---

# 9. IaaS → PaaS → SaaS Connection

This connects directly to the service models you learned earlier.

```text
                Customer Responsibility
                         ↓

On-Premises       ████████████████████
IaaS              ███████████████
PaaS              █████████
SaaS              ███
                         ↓
                AWS Responsibility
                         ↑
```

As you move toward more managed services:

```text
IaaS → PaaS → SaaS
```

AWS generally takes responsibility for more of the underlying technology stack.

For example:

```text
EC2
 ↓
More customer management

Managed AWS service
 ↓
More AWS management
```

But **the customer still retains responsibilities**, especially around data, access, and service configuration.

---

# 10. Shared Responsibility Is NOT 50/50

Don't think:

```text
AWS = 50%
Customer = 50%
```

That's not what "shared" means.

Instead:

```text
Responsibility
      ↓
Depends on:
      ↓
AWS Service
      +
How you configure/use it
```

For example:

```text
EC2 → Customer manages more

RDS → AWS manages more

S3 → AWS manages the service infrastructure,
     customer manages data/access configuration
```

---

# 11. How to Use the Shared Responsibility Model

When you're troubleshooting a security or infrastructure problem, ask:

### Step 1 — What service am I using?

```text
EC2?
S3?
RDS?
Lambda?
```

### Step 2 — What layer is the problem?

```text
Physical infrastructure?
OS?
Application?
Data?
IAM?
Network configuration?
```

### Step 3 — Who manages that layer?

```text
AWS?
Customer?
```

This helps determine who is responsible for addressing the issue.

# 12. Scenario

Imagine you have:

```text
Internet
   ↓
Load Balancer
   ↓
EC2
   ↓
RDS
```

### AWS responsibility

```text
AWS
│
├── Physical data centers
├── Physical servers
├── Physical networking
└── Underlying AWS infrastructure
```

### Your responsibility

```text
Customer
│
├── IAM
├── Application security
├── EC2 OS
├── Security Groups
├── Data
└── Appropriate service configuration
```

If the physical AWS server has a hardware issue:

> **AWS responsibility**

If your EC2 server has an unpatched operating system:

> **Customer responsibility**

If an IAM user has excessive permissions:

> **Customer responsibility**

# 13. Common Exam Questions

### "Who is responsible for physical security of AWS data centers?"

**AWS**

---

### "Who is responsible for patching the operating system on an EC2 instance?"

**Customer**, when the customer manages the guest OS.

---

### "Who is responsible for configuring IAM permissions?"

**Customer**

---

### "Who is responsible for the physical hardware?"

**AWS**

---

### "Who is responsible for application security?"

**Customer**

---

### "Who is responsible for security group rules?"

**Customer**

---

### "Does AWS handle all security when you use AWS?"

**No.**

Security responsibilities are shared, and the exact responsibilities depend on the service.

# 🎯 Final Summary

The entire concept can be reduced to:

```text
             AWS SHARED RESPONSIBILITY

                    AWS
                     ↓
             Security OF Cloud
                     ↓
       Physical Infrastructure
       Data Centers
       Hardware
       Networking
       Virtualization

                     +

                  CUSTOMER
                     ↓
             Security IN Cloud
                     ↓
       Data
       IAM
       Applications
       OS (where applicable)
       Permissions
       Configurations
```

### 🔥 Remember these three rules

**1. AWS = Security OF the cloud**

**2. Customer = Security IN the cloud**

**3. The exact responsibility depends on the AWS service.**

> **Exam memory trick: AWS protects the infrastructure; you protect and configure what you put/use in AWS.**
