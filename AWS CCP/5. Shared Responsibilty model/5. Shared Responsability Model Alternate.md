# 🔐 AWS Shared Responsibility Model — Alternate Responsibilities

In AWS, the **Shared Responsibility Model** can also be understood through **two categories of responsibility**:

1. **AWS responsibility**
2. **Customer responsibility**

The important point is that the boundary **changes depending on the AWS service**.

---

# 1. AWS Responsibility

AWS is responsible for **security OF the cloud**.

This means AWS protects the infrastructure that AWS operates.

```text
AWS Responsibility
│
├── Physical Data Centers
├── Physical Servers
├── Physical Networking
├── Storage Hardware
├── Power & Cooling
├── Physical Security
└── Underlying Infrastructure
```

### Example

You launch an EC2 instance.

You don't have to worry about:

> "Who protects the physical AWS server from unauthorized physical access?"

That's AWS's responsibility.

---

# 2. Customer Responsibility

The customer is responsible for **security IN the cloud**.

This includes appropriately securing the resources and workloads that the customer deploys.

```text
Customer Responsibility
│
├── Customer Data
├── IAM
├── Applications
├── Access Permissions
├── Network Configuration
├── Security Groups
├── Operating System
└── Application Configuration
```

However, not every item applies identically to every AWS service.

For example, with EC2, you manage the guest operating system. With a managed service, AWS may manage more of the operating system/platform.

---

# 3. The Responsibility Changes With the Service

This is the **alternate way of looking at the Shared Responsibility Model**.

Instead of simply asking:

> "Is AWS or the customer responsible?"

ask:

> **"How much of the technology stack is AWS managing for this service?"**

For example:

```text
                  More Customer Responsibility
                            ↓

                         EC2
                          │
                    You manage OS
                          │
                          ↓
                    More control

                            ↓

                    Managed Services
                          │
                    AWS manages more
                          │
                          ↓

                        Lambda
                            ↓
                  More AWS management
```

This is why **service selection affects your security responsibilities**.

---

# 4. Compute Example

### EC2

```text
AWS
│
├── Physical hardware
├── Data center
├── Networking
└── Virtualization

Customer
│
├── Guest OS
├── OS patches
├── Applications
├── Data
└── Security configuration
```

### Lambda

```text
AWS
│
├── Physical infrastructure
├── Servers
├── OS
└── Underlying runtime infrastructure

Customer
│
├── Function code
├── Data
├── IAM
└── Function configuration
```

Therefore:

> **EC2 gives the customer more infrastructure control and therefore more management responsibility.**

> **Lambda abstracts more infrastructure away from the customer.**

---

# 5. Storage Example

Consider S3.

AWS manages:

```text
Physical storage
Storage infrastructure
Underlying AWS infrastructure
```

The customer manages things such as:

```text
Data
Access permissions
IAM
Bucket configuration
Encryption choices/configuration where applicable
```

For example:

```text
Customer
   ↓
S3 Bucket
   ↓
IAM permissions
   ↓
Who can access the data?
```

AWS provides the security mechanisms, but you must configure them appropriately.

---

# 6. Database Example

With a managed database service such as **Amazon RDS**, AWS manages more of the underlying infrastructure/platform than it does with EC2.

```text
EC2
Customer → OS + application + data

RDS
AWS → underlying infrastructure + managed database platform
Customer → data + access + applicable configuration
```

The exact responsibility depends on the service and configuration.

---

# 7. Why Is This Called "Alternate"?

You can think about the model from two perspectives.

### Traditional view

```text
AWS
 ↓
Security OF the Cloud

Customer
 ↓
Security IN the Cloud
```

### Service-based view

```text
Customer Responsibility
        ↓
   Depends on service
        ↓
┌───────┼────────┐
EC2     RDS     Lambda
│        │         │
More     Less      Less
customer customer customer
responsibility responsibility responsibility
```

The second view helps you understand **why responsibilities aren't identical across AWS services**.

---

# 8. Scenario

Suppose you're building an application:

```text
Internet
   ↓
Load Balancer
   ↓
EC2
   ↓
RDS
```

### AWS:

```text
Physical data centers
Physical hardware
Underlying networking
Underlying infrastructure
```

### Customer:

```text
IAM
Security Groups
EC2 OS
Application

Access configuration
```

### RDS:

AWS manages more of the database infrastructure, while you remain responsible for your data, access controls, and appropriate configuration.

# 🎯 Exam Perspective

When you see a question, identify **the service first**.

Then ask:

### Physical infrastructure?

→ **AWS**

### Customer data?

→ **Customer**

### IAM permissions?

→ **Customer**

### EC2 guest OS?

→ **Customer**

### Physical AWS hardware?

→ **AWS**

### Managed-service infrastructure?

→ **AWS takes more responsibility**

### Customer application/code?

→ **Customer**

---

# 🧠 Final Summary

The **alternate way to understand the AWS Shared Responsibility Model** is:

```text
                    SHARED RESPONSIBILITY
                            │
                            ↓
                 What service are you using?
                            │
              ┌─────────────┴─────────────┐
              ↓                           ↓
        More AWS managed            More customer managed
              │                           │
          Lambda/RDS                  EC2
              │                           │
       AWS manages more            Customer manages more
       infrastructure              of the environment
```

But the fundamental rule remains:

> **AWS → Security OF the cloud**

> **Customer → Security IN the cloud**

> **The AWS service determines where the responsibility boundary lies.**

### 🔥 Memory trick

**More control → More responsibility.**

**More AWS-managed → Less underlying infrastructure responsibility for you.**
