# 🔐 Introduction to the AWS Shared Responsibility Model

## 1. Definition

The **AWS Shared Responsibility Model** defines **which security responsibilities belong to AWS and which belong to the customer** when using AWS services.

The central idea is:

> **AWS is responsible for security OF the cloud, while the customer is responsible for security IN the cloud.**

Think of it like renting an apartment:

```text
AWS
 ↓
Secures the building and infrastructure

Customer
 ↓
Secures what they put inside the building
```

AWS provides the secure cloud infrastructure, but customers are still responsible for properly securing and configuring the resources they use.

---

# 2. Why Do We Need the Shared Responsibility Model?

When you move from an on-premises data center to AWS, you don't suddenly stop having security responsibilities.

In a traditional data center, your organization may be responsible for:

```text
Physical building
      ↓
Physical servers
      ↓
Networking
      ↓
Operating system
      ↓
Applications
      ↓
Data
      ↓
Access control
```

With AWS, AWS takes responsibility for much of the underlying infrastructure.

```text
AWS
├── Data centers
├── Physical servers
├── Physical networking
└── Virtualization infrastructure

Customer
├── Data
├── IAM
├── Applications
├── Configurations
└── Other responsibilities depending on service
```

The Shared Responsibility Model makes this boundary clear.

---

# 3. The Two Sides

## 🟦 AWS Responsibility

AWS is responsible for **security OF the cloud**.

This means AWS protects the infrastructure that runs AWS services.

Examples include:

* Physical data centers
* Physical servers
* Physical networking
* Hardware
* AWS global infrastructure
* Underlying virtualization infrastructure

Simplified:

```text
AWS
 ↓
"Is the cloud infrastructure itself secure?"
```

AWS handles that part.

---

# 4. Customer Responsibility

The customer is responsible for **security IN the cloud**.

This includes things such as:

* Customer data
* IAM users and permissions
* Application security
* Appropriate network configuration
* Security group configuration
* Encryption configuration where applicable
* Operating-system configuration/patching when the customer manages the OS

The exact customer responsibility depends on the AWS service being used.

Simplified:

```text
Customer
 ↓
"Are the resources and data I'm putting in AWS configured securely?"
```

# 6. Why Does Responsibility Change?

This is extremely important.

AWS doesn't manage every service in exactly the same way.

Consider **EC2**.

With EC2, AWS manages the physical infrastructure, but you manage much more of the software environment.

```text
EC2
│
├── AWS
│   ├── Data center
│   ├── Physical server
│   ├── Hardware
│   └── Virtualization
│
└── Customer
    ├── Guest OS
    ├── Applications
    ├── Data
    ├── IAM configuration
    └── Security configuration
```

Now consider a more managed service such as **Amazon RDS**.

AWS manages much more of the underlying infrastructure and database platform.

```text
RDS
│
├── AWS
│   ├── Physical infrastructure
│   ├── Servers
│   ├── OS/platform management
│   └── Database infrastructure
│
└── Customer
    ├── Data
    ├── Access permissions
    └── Database configuration
       according to the service
```

So:

> **The more managed the service is, the more infrastructure responsibility AWS takes on.**

---

# 7. EC2 Example

Suppose you launch:

```text
EC2
 ↓
Windows Server
 ↓
Your application
```

AWS is responsible for:

```text
Physical server
Physical network
Data center
Underlying infrastructure
Virtualization
```

You are responsible for things such as:

```text
Windows configuration
OS patching
Application
Data
IAM permissions
Security group configuration
```

So if you forget to patch your Windows Server, that's generally a **customer responsibility** for an EC2 instance where you manage the guest OS.

---

# 8. RDS Example

Suppose you use:

```text
Amazon RDS
 ↓
Database
```

AWS manages much of the underlying infrastructure and managed database platform.

You still need to consider:

```text
Who can access the database?
What data is stored?
What permissions are configured?
What network access is allowed?
What encryption/configuration is appropriate?
```

So moving to a managed service doesn't mean:

> "AWS handles all security."

It means:

> **AWS takes on more of the underlying operational/security responsibility, while you retain responsibilities appropriate to the service.**

---

# 9. IAM Is a Customer Responsibility

This is a common exam area.

Suppose you create:

```text
IAM User
     ↓
Permissions
```

You need to make sure the user has appropriate permissions.

For example:

```text
Developer
   ↓
S3
   ↓
Only required access
```

You shouldn't give unnecessary permissions.

This relates to the **principle of least privilege**.

So:

> **Managing IAM users, roles, permissions and policies is generally a customer responsibility.**

---

# 10. Security Groups

Suppose you launch an EC2 web server.

You configure:

```text
Security Group
       ↓
Allow TCP 443
       ↓
HTTPS
```

AWS provides the security-group capability and underlying infrastructure.

But **you are responsible for configuring it appropriately**.

If you accidentally allow unnecessary inbound traffic, that's a customer configuration issue.

---

# 11. Data Protection

Your organization's data is your responsibility.

For example:

```text
Customer Data
      ↓
S3
```

You need to consider:

```text
Who can access it?
Is encryption configured?
Are permissions appropriate?
Are public-access settings appropriate?
```

AWS provides security features and services to help you protect the data, but you must configure and use them appropriately.

---

# 12. Physical Security

Now consider the AWS data center.

You don't physically manage:

```text
AWS Data Center
      ↓
Physical servers
      ↓
Physical networking
      ↓
Power
      ↓
Physical security
```

AWS handles the underlying physical infrastructure.

So if an exam asks:

> **Who is responsible for physical security of AWS data centers?**

Answer:

**AWS.**

# 13. Simple Comparison

| Responsibility                      |   AWS   | Customer |
| ----------------------------------- | :-----: | :------: |
| AWS data centers                    |    ✅    |          |
| Physical servers                    |    ✅    |          |
| Physical networking                 |    ✅    |          |
| Underlying infrastructure           |    ✅    |          |
| Customer data                       |         |     ✅    |
| IAM permissions                     |         |     ✅    |
| Application security                |         |     ✅    |
| Security group configuration        |         |     ✅    |
| Guest OS on EC2                     |         |     ✅    |
| OS patching on customer-managed EC2 |         |     ✅    |
| Service-specific configuration      | Depends |  Depends |

The last two columns aren't always absolute because responsibility **depends on the service**.

---

# 14. Shared Responsibility ≠ 50/50

This is an important misconception.

It doesn't mean:

```text
AWS = 50%
Customer = 50%
```

Instead:

> **Responsibilities are divided according to the AWS service and the specific task.**

For example:

```text
EC2
AWS → more infrastructure responsibility
Customer → more OS/application responsibility

RDS
AWS → more platform/infrastructure responsibility
Customer → data/access/configuration responsibility
```

# 15. Scenario-Based Example

Imagine you're running an application:

```text
Internet
   ↓
Load Balancer
   ↓
EC2
   ↓
RDS
```

### AWS is responsible for things such as:

```text
Physical data centers
Physical hardware
Physical networking
Underlying cloud infrastructure
```

### You are responsible for things such as:

```text
IAM permissions
Application security
EC2 OS configuration
Security group rules
Your application
Your data
Appropriate encryption/configuration
```

So if your application has a vulnerability:

```text
Application vulnerability
        ↓
Customer responsibility
```

But if the underlying AWS physical infrastructure needs protection:

```text
AWS physical infrastructure
        ↓
AWS responsibility
```

# 16. The Key Exam Trick

AWS Cloud Practitioner questions often describe a security problem and ask **who is responsible**.

### If the question says:

> Physical data center security

→ **AWS**

### If it says:

> IAM permissions

→ **Customer**

### If it says:

> EC2 operating-system patches

→ **Customer**

### If it says:

> Physical hardware

→ **AWS**

### If it says:

> Customer application security

→ **Customer**

### If it says:

> Security group configuration

→ **Customer**

### If it says:

> Underlying AWS infrastructure

→ **AWS**

# 🎯 Final Summary

The **AWS Shared Responsibility Model** establishes the division of security responsibilities between AWS and its customers.

### AWS:

> **Security OF the Cloud**

Responsible for the underlying AWS infrastructure, including:

```text
Data centers
Physical hardware
Physical networking
Underlying infrastructure
```

### Customer:

> **Security IN the Cloud**

Responsible for things such as:

```text
Data
IAM
Applications
Permissions
Security configurations
Guest OS on EC2
```

### And the biggest rule:

> **The exact responsibility changes depending on the AWS service.**

### 🧠 One-line memory

**AWS protects the cloud → Customer protects what's inside the cloud.**
