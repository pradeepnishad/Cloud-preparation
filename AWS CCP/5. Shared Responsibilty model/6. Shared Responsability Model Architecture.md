# 🏗️ AWS Shared Responsibility Model — Architecture

The **architecture of the AWS Shared Responsibility Model** shows **where AWS's security responsibilities end and where the customer's responsibilities begin**.

The core idea is:

> **AWS is responsible for security OF the cloud, while the customer is responsible for security IN the cloud.**

The exact boundary changes depending on the AWS service.

---

# 1. The Overall Architecture

Think of AWS infrastructure as several layers:

```text
                    AWS CLOUD
┌───────────────────────────────────────────────┐
│                                               │
│       AWS RESPONSIBILITY                      │
│       Security OF the Cloud                   │
│                                               │
│  ┌─────────────────────────────────────────┐  │
│  │ Physical Data Centers                   │  │
│  │ Physical Servers                        │  │
│  │ Physical Networking                     │  │
│  │ Storage Hardware                        │  │
│  │ Power / Cooling / Physical Security     │  │
│  └─────────────────────────────────────────┘  │
│                     ↓                         │
│              Virtualization                   │
│                     ↓                         │
│  ───────────────────────────────────────────  │
│       RESPONSIBILITY BOUNDARY                 │
│  ───────────────────────────────────────────  │
│                                               │
│       CUSTOMER RESPONSIBILITY                 │
│       Security IN the Cloud                   │
│                                               │
│  ┌─────────────────────────────────────────┐  │
│  │ Operating System*                      │  │
│  │ Applications*                          │  │
│  │ IAM / Permissions                      │  │
│  │ Network Configuration                  │  │
│  │ Customer Data                          │  │
│  │ Security Configuration                 │  │
│  └─────────────────────────────────────────┘  │
│                                               │
└───────────────────────────────────────────────┘

*Depends on the AWS service
```

The most important thing here is that **the boundary is not fixed for every AWS service**.

---

# 2. AWS's Side of the Architecture

AWS operates the underlying infrastructure required to provide AWS services.

This includes areas such as:

```text
AWS
│
├── Physical Facilities
│
├── Physical Hardware
│
├── Physical Networking
│
├── Storage Infrastructure
│
└── Underlying Cloud Infrastructure
```

### Example

When you create an EC2 instance, AWS doesn't ask you to:

* Build a physical server
* Install physical networking equipment
* Secure the data center
* Maintain power and cooling
* Replace failed physical hardware

Those are part of AWS's responsibility.

---

# 3. Customer's Side of the Architecture

The customer is responsible for appropriately securing and configuring what they deploy and store in AWS.

Depending on the service, this can include:

```text
Customer
│
├── Data
├── IAM
├── Permissions
├── Applications
├── Network configuration
├── Security configuration
└── Operating system*
```

For example, with EC2:

```text
EC2
│
├── AWS
│   ├── Physical server
│   ├── Data center
│   ├── Physical network
│   └── Virtualization
│
└── Customer
    ├── Guest OS
    ├── OS configuration
    ├── Applications
    ├── Data
    └── Security configuration
```

---

# 4. The Responsibility Boundary

This is the most important architectural concept.

```text
             AWS
              ↓
       Infrastructure
              ↓
       Virtualization
              ↓
════════════════════════════
   SHARED RESPONSIBILITY
        BOUNDARY
════════════════════════════
              ↓
       Customer workload
              ↓
      Application / Data
```

The boundary can move depending on how much AWS manages.

---

# 5. EC2 Architecture

EC2 provides a virtual machine.

The simplified stack looks like:

```text
┌──────────────────────────┐
│ Customer Application     │ ← Customer
├──────────────────────────┤
│ Guest Operating System   │ ← Customer
├──────────────────────────┤
│ EC2 Virtual Machine      │
├──────────────────────────┤
│ Virtualization           │ ← AWS
├──────────────────────────┤
│ Physical Hardware        │ ← AWS
├──────────────────────────┤
│ AWS Data Center          │ ← AWS
└──────────────────────────┘
```

So EC2 gives you significant control.

And remember:

> **More control generally means more customer responsibility.**

---

# 6. Managed Service Architecture

Now consider a more managed service.

The simplified idea is:

```text
┌──────────────────────────┐
│ Customer Application     │ ← Customer
├──────────────────────────┤
│ Customer Data            │ ← Customer
├──────────────────────────┤
│ Managed AWS Service      │ ← AWS manages much more
├──────────────────────────┤
│ Operating Environment    │ ← AWS
├──────────────────────────┤
│ Infrastructure           │ ← AWS
├──────────────────────────┤
│ Physical Hardware        │ ← AWS
└──────────────────────────┘
```

AWS takes responsibility for more of the underlying environment.

This is why managed services can reduce the amount of infrastructure administration you have to perform.

---

# 7. Compute Architecture Example

Compare EC2 and Lambda:

```text
                CUSTOMER
                   ↓
        ┌───────────────────┐
        │ Application       │
        │                   │
        │ EC2 → OS          │ ← Customer
        └───────────────────┘
                   ↓
             AWS manages
             infrastructure


              LAMBDA

        ┌───────────────────┐
        │ Function Code     │ ← Customer
        └───────────────────┘
                   ↓
        ┌───────────────────┐
        │ Runtime/Servers   │ ← AWS
        │ Infrastructure    │
        └───────────────────┘
```

With Lambda, you don't manage the underlying servers in the same way you do with EC2.

---

# 8. Storage Architecture Example

Consider S3:

```text
┌──────────────────────────┐
│ Customer Data            │ ← Customer
├──────────────────────────┤
│ Bucket Access/Config     │ ← Customer
├──────────────────────────┤
│ S3 Service               │ ← AWS
├──────────────────────────┤
│ Storage Infrastructure   │ ← AWS
├──────────────────────────┤
│ Physical Hardware        │ ← AWS
└──────────────────────────┘
```

AWS manages the storage infrastructure.

You remain responsible for appropriately configuring access to your data and using available security controls.

---

# 9. Network Security Architecture

The same model applies to networking.

For example:

```text
Internet
   ↓
AWS Networking Infrastructure
   ↓
VPC
   ↓
Subnet
   ↓
Security Group
   ↓
EC2
```

AWS provides the underlying networking infrastructure.

But you configure things such as:

```text
VPC
Subnets
Route Tables
Security Groups
Network ACLs
```

according to the service and architecture.

So:

> **AWS provides the infrastructure and security capabilities; the customer is responsible for appropriately configuring the resources they control.**

# 10. Who Is Responsible for What?

| Layer                          | Typical responsibility |
| ------------------------------ | ---------------------- |
| Physical data center           | AWS                    |
| Physical hardware              | AWS                    |
| Physical networking            | AWS                    |
| Underlying AWS infrastructure  | AWS                    |
| Virtualization infrastructure  | AWS                    |
| Guest OS on EC2                | Customer               |
| Applications                   | Customer               |
| Customer data                  | Customer               |
| IAM permissions                | Customer               |
| Security Group rules           | Customer               |
| Service-specific configuration | Depends on service     |

---

# 11. The Architecture Changes With the Service

This is the key exam concept.

Think:

```text
             AWS
              ↑
              │
       AWS manages more
              │
        Managed Service
              │
        ──────┼──────
              │
           Customer
              ↓
       Customer manages
          less underlying
          infrastructure
```

For example:

```text
EC2
↓
Customer manages guest OS

RDS
↓
AWS manages more of the database platform

Lambda
↓
AWS manages the underlying compute environment
```

Imagine you deploy a web application:

```text

                     ↓
              ┌──────┴──────┐
              ↓             ↓
             EC2           EC2
              ↓             ↓
              └──────┬──────┘
                     ↓
                    RDS
```

### AWS responsibility

```text
Physical infrastructure
        ↓
Data centers
        ↓
Servers
        ↓
Physical networking
        ↓
Underlying AWS infrastructure
```

### Customer responsibility

```text
IAM
 ↓
Security Groups
 ↓
EC2 OS
 ↓
Application
 ↓
Customer Data
```

### RDS

AWS takes on more responsibility for the managed database platform, while you still manage your data, access, and applicable configuration.

# 🎯 How to Think About the Architecture in the Exam

Whenever you get a Shared Responsibility question, mentally draw:

```text
          AWS
           ↓
  Physical Infrastructure
           ↓
      AWS-managed layer
           ↓
════════════════════════
 Responsibility Boundary
════════════════════════
           ↓
   Customer-controlled
        workload
           ↓
     Application/Data
```

Then ask:

### "Is the question about physical infrastructure?"

→ **AWS**

### "Is it about my application or data?"

→ **Customer**

### "Is it about EC2's guest OS?"

→ **Customer**

### "Is it about a managed service's underlying infrastructure?"

→ **AWS**

### "Could responsibility vary by service?"

→ **Yes**

# 🧠 Final Summary

The **architecture of the AWS Shared Responsibility Model** is essentially a **layered model**:

```text
                    AWS
                     │
                     ↓
          Physical Infrastructure
                     ↓
              Cloud Infrastructure
                     ↓
          ─────────────────────
          Responsibility Boundary
          ─────────────────────
                     ↓
            Customer Workload
                     ↓
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        IAM      Application    Data
                     ↓
                 Customer
```

### Remember:

**AWS → Security OF the cloud**

**Customer → Security IN the cloud**

**Service → Determines where the responsibility boundary sits**

And the easiest rule:

> 🔑 **The more infrastructure AWS manages for you, the less underlying infrastructure you have to manage yourself.**
