# 🔐 Identity and Access Management (IAM)

## 1. Definition

**AWS Identity and Access Management (IAM)** is an AWS service that helps you **control who can access AWS resources and what actions they are allowed to perform**.

Simple definition:

> **IAM = Who can access AWS + What they can do.**

For example:


User
 ↓
IAM
 ↓
Can access S3
 ↓
Can upload files
 ❌ Cannot delete files


IAM is a **global AWS service** and is fundamental to AWS security.

---

# 2. What Is IAM / How Does It Work?

IAM controls access using **identities, permissions, and policies**.

The main IAM components you should know for Cloud Practitioner are:

1. **Users**
2. **Groups**
3. **Roles**
4. **Policies**

Think of it like an organization:


                IAM
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
     Users     Groups     Roles
       │         │         │
       └─────────┼─────────┘
                 ↓
              Policies
                 ↓
            Permissions


---

# 3. IAM Users

An **IAM user** represents an identity that can access AWS.

For example:


AWS Account
    ↓
IAM
    ↓
John
    ↓
Permissions
    ↓
S3


You can give the user specific permissions.

For example:

> John can view S3 objects but cannot delete them.

---

# 4. IAM Groups

An **IAM group** is a collection of IAM users.

Instead of assigning the same permissions individually:


John   ─┐
Sarah  ─┼→ Developers Group → Permissions
Mike   ─┘


You can attach permissions to the group.

This makes managing permissions easier when multiple users need the same access.

### Example


Developers Group
       ↓
EC2 access
S3 access
CloudWatch access


Any appropriate users added to that group receive those permissions.

---

# 5. IAM Roles

An **IAM role** is an identity with permissions that can be **assumed** by trusted entities.

Roles are especially important for:

* AWS services
* Applications
* EC2 instances
* Users
* Federated identities
* Cross-account access

### Example

Suppose an EC2 instance needs to read files from S3.

❌ Bad approach:


EC2
 ↓
Hard-coded AWS access keys
 ↓
S3


✅ Better:


EC2
 ↓
IAM Role
 ↓
Permission to read S3
 ↓
S3


The application doesn't need to store long-term credentials.

---

# 6. IAM Policies

A **policy** is a document that defines **permissions**.

It answers questions such as:

> What actions are allowed or denied?

For example:


User
 ↓
Policy
 ↓
Allow: Read S3 objects
 ↓
S3


A policy can specify:

* **Effect** → Allow or Deny
* **Action** → What operation can be performed
* **Resource** → Which AWS resource
* **Condition** → Under what conditions

Conceptually:


Allow
 ↓
Read
 ↓
S3 bucket
 ↓
Under specific conditions


---

# 7. Why Use IAM?

IAM helps you implement **secure and controlled access** to AWS resources.

### 🔐 1. Control access

You decide who can access what.

### 🛡️ 2. Apply least privilege

Give users/applications **only the permissions they need**.

For example:


Developer
 ↓
Needs to read S3
 ↓
Give S3 read permission

❌ Don't give full AWS administrator access


### 👥 3. Manage users

Organizations can create identities for employees, teams, applications, etc.

### 🔄 4. Use roles instead of long-term credentials

Applications and AWS services can use IAM roles to obtain appropriate permissions.

---

# 8. How to Use IAM

A basic process:


1. Create identity
       ↓
2. Determine required access
       ↓
3. Create/choose policy
       ↓
4. Attach permissions
       ↓
5. Test access
       ↓
6. Review and reduce unnecessary permissions


For example:


Developer
   ↓
Needs S3 read access
   ↓
Create/assign appropriate policy
   ↓
Developer can read required S3 data


---

# 9. When Should You Use IAM?

**Always**, when controlling access to AWS resources.

Typical situations:

* Employees need AWS access
* Developers need specific AWS permissions
* Applications need to access AWS services
* EC2 needs access to S3
* Different teams need different permissions
* You need to restrict sensitive resources
* You need to implement least privilege

# 11. IAM and the Root User

This connects directly to the topic you just learned.

### Root user


Root
 ↓
Extremely powerful / full account access


### IAM


IAM
 ↓
Controlled identities
 ↓
Specific permissions


Therefore:

> **Don't use the root user for everyday AWS tasks.**

Use appropriate IAM identities/roles instead.

---

# 12. IAM and MFA

IAM can also be combined with **MFA**.


IAM Identity
      +
Password
      +
MFA
      ↓
AWS Access


This provides stronger protection against compromised credentials.

---

# 13. IAM vs Authentication vs Authorization

This distinction is important.

### Authentication

> **Who are you?**


User → Login


### Authorization

> **What are you allowed to do?**


User
 ↓
Permissions
 ↓
Can read S3
❌ Cannot delete S3


### IAM

IAM provides the mechanisms used to manage **identity and access control** in AWS.

Memory:

> **Authentication = Who?**
> **Authorization = What can they do?**

# 🧠 Quick Summary

| IAM Component  | Purpose                                                |
| -------------- | ------------------------------------------------------ |
| **User**       | Represents an AWS identity                             |
| **Group**      | Collection of users                                    |
| **Role**       | Assumable identity used by users/services/applications |
| **Policy**     | Defines permissions                                    |
| **Permission** | Specifies what actions are allowed/denied              |
| **MFA**        | Adds additional authentication protection              |
