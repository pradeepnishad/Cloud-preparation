# 🔐 AWS Shared Responsibility Model

## 1. Definition

The **AWS Shared Responsibility Model** defines **which security responsibilities belong to AWS and which belong to the customer**.

The basic idea is:

> **AWS is responsible for security OF the cloud, while the customer is responsible for security IN the cloud.**

So security is a **shared responsibility** between AWS and the customer.

---

# 2. What Is It / How Does It Work?

Think of AWS infrastructure as a building.


                 AWS CLOUD
                    │
        ┌───────────┴───────────┐
        │                       │
   AWS Responsibility      Customer Responsibility
   "Security OF cloud"    "Security IN cloud"


### AWS is responsible for:

The security of the **underlying cloud infrastructure**, including things such as:

* Physical data centers
* Physical servers
* Networking infrastructure
* Hardware
* Virtualization layer
* Physical facilities

Example:


AWS Data Center
      ↓
Physical Servers
      ↓
Networking
      ↓
Hardware
      ↓
Virtualization


AWS secures and maintains this underlying infrastructure.

---

### Customer is responsible for:

Security of what they **put into and configure within AWS**, depending on the service.

This can include:

* Data
* IAM users and permissions
* Passwords/credentials
* Application security
* Operating system configuration
* Network configuration
* Security groups
* Encryption configuration
* Guest OS patching for services where the customer manages the OS

For example, if you launch an EC2 instance:


AWS
 ↓
Physical hardware
 ↓
Data center
 ↓
Networking
 ↓
Hypervisor


AWS manages those layers.

You manage:


EC2
 ↓
Operating System
 ↓
Applications
 ↓
Data
 ↓
Access permissions


---

# 3. Why Use the Shared Responsibility Model?

The model helps you understand **who is responsible for securing each part of your AWS environment**.

This is important because:

> Using AWS does NOT mean AWS automatically secures everything you create.

For example, AWS can secure the physical data center, but if you give an unauthorized user excessive IAM permissions, **that's your responsibility**.

It helps organizations:

* Understand security responsibilities
* Avoid security gaps
* Configure AWS resources correctly
* Meet compliance requirements
* Protect applications and data
* Design secure architectures

---

# 4. How Does Responsibility Change With Different Services?

This is very important.

The amount of responsibility you have depends on **how much AWS manages for you**.

### EC2 — More customer responsibility


AWS
↓
Physical infrastructure
↓
Virtualization
↓
EC2 infrastructure

Customer
↓
Guest OS
↓
Applications
↓
Data
↓
Configuration


### RDS — Less customer infrastructure responsibility


AWS
↓
Infrastructure
↓
Operating system
↓
Database platform
↓
Maintenance capabilities

Customer
↓
Data
↓
Database configuration
↓
Access


### SaaS-style service — Even less infrastructure responsibility

As AWS manages more of the service, **your infrastructure-management responsibility decreases**.


More AWS-managed
       ↑
       │
      SaaS
       │
      PaaS
       │
      IaaS
       ↓
More customer-managed


This connects directly to what you learned earlier about **IaaS, PaaS, SaaS, and managed services**.

# 5. When Do You Need to Think About It?

Always.

But it becomes particularly important when:

* Creating IAM policies
* Protecting sensitive data
* Launching EC2 instances
* Configuring security groups
* Managing operating systems
* Encrypting data
* Configuring applications
* Meeting compliance requirements
* Designing AWS architectures

Whenever you ask:

> **"Who is responsible for securing this?"**

think about the Shared Responsibility Model.

# 6. Scenario-Based Example

Imagine you're hosting a website on an EC2 instance.


              Website
                 ↓
               EC2
                 ↓
        ┌────────┴────────┐
        ↓                 ↓
       AWS              Customer


### AWS handles:

* Physical data center security
* Physical servers
* Physical networking
* Hardware
* Virtualization infrastructure

### You handle:

* EC2 operating system
* Installing/patching your software where applicable
* Application security
* User permissions
* Security group configuration
* Protecting your website data

Suppose you leave an unnecessary network port open in your security group.


Security group
      ↓
Port unnecessarily open
      ↓
Security risk


AWS's physical infrastructure can be completely secure, but **your configuration can still create a vulnerability**.

That's exactly why the model exists.

| Physical networking           | ✅                         | ❌                         |

# 8. Shared Responsibility vs Shared Controls

AWS also provides security **controls and capabilities** that customers can use.

For example:


AWS provides
     ↓
IAM
Encryption services
Logging
Monitoring
Network security tools
     ↓
Customer configures/uses them correctly


So AWS provides the **security tools and infrastructure**, but customers must configure and use them appropriately.

---

# 9. Exam Perspective 🎯

This is a **very important foundational AWS exam topic**.

### If the question says:

> Who is responsible for physical security of AWS data centers?

**→ AWS**

---

> Who is responsible for configuring IAM permissions?

**→ Customer**

---

> Who is responsible for patching the guest operating system on an EC2 instance?

**→ Customer**

---

> Who is responsible for the physical hardware?

**→ AWS**

---

> Who is responsible for securing customer data?

**→ Customer**, while AWS provides security capabilities and the exact responsibilities can vary by service.

---

### Golden exam rule:

> **Security OF the cloud → AWS**

> **Security IN the cloud → Customer**
