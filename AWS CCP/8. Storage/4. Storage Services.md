# 1. Amazon S3

## Definition

**Amazon Simple Storage Service (S3)** is a **serverless object storage service**.

It stores data as **objects inside buckets**.

```text
S3
 ↓
Bucket
 ↓
Objects
 ├── image.jpg
 ├── video.mp4
 ├── report.pdf
 └── backup.zip
```

The source highlights that you can upload very large files and don't need to manage the underlying filesystem or increase a disk size manually.

---

## Why use S3?

Use S3 when you need highly scalable storage for objects such as:

* Images
* Videos
* Documents
* Backups
* Logs
* Data files

### Scenario

A website allows users to upload photos:

```text
User
 ↓
Application
 ↓
S3 Bucket
 ↓
profile.jpg
```

You don't need to attach a disk to the application server just to store those images.

### 🧠 Memory

> **S3 = Serverless Object Storage**

---

# 2. S3 Glacier

## Definition

**S3 Glacier** is a **cold storage service** designed for **archiving and long-term backup**.

The key idea is:

> **Store data cheaply when you don't need to access it frequently.**

Think:

```text
Frequently used data
       ↓
   Normal S3

Rarely accessed / archival data
       ↓
   S3 Glacier
```

---

## Why use Glacier?

Suppose a company has old records:

```text
2018 records
2019 records
2020 records
2021 records
```

They rarely need to access them, but they must retain them.

Instead of keeping everything in frequently accessed storage, archival storage can be used.

### Scenario

A company must retain financial records for many years.

```text
Old records
     ↓
S3 Glacier
     ↓
Long-term archival
```

### 🧠 Memory

> **S3 = General object storage**

> **S3 Glacier = Cold/archive storage**

---

# 3. Amazon EBS

## Definition

**Amazon Elastic Block Store (EBS)** is a **persistent block storage service** used primarily with EC2.

Think of it as:

> **A virtual hard drive in AWS.**

```text
EC2
 │
 └── EBS Volume
       ↓
    Filesystem
       ↓
    Application/Data
```

The source mentions different EBS volume categories, including:

* SSD
* IOPS-optimized SSD
* Throughput HDD
* Cold HDD

The specific volume type should be selected according to workload requirements.

---

## Why use EBS?

Use EBS when an EC2 instance needs block-level storage.

Examples:

```text
Operating System
Application files
Database
Logs
```

### Scenario

You launch an EC2 instance running Linux:

```text
EC2
 ↓
EBS
 ↓
Linux filesystem
 ↓
Application
```

### 🧠 Memory

> **EBS = Persistent virtual disk for EC2**

---

# 4. Amazon EFS

## Definition

**Amazon Elastic File System (EFS)** is a **cloud-native managed file system**.

The source specifically highlights that it can be mounted to **multiple EC2 instances at the same time**.

```text
             EFS
          /   |   \
         ↓    ↓    ↓
       EC2   EC2   EC2
```

All those EC2 instances can access the shared filesystem according to the configured permissions.

---

## Why use EFS?

Use EFS when:

> **Multiple servers need access to shared files.**

### Scenario

You have three web servers:

```text
Load Balancer
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
EC2  EC2  EC2
 \    |    /
      ↓
     EFS
```

All three servers need access to the same application files.

### 🧠 Memory

> **EFS = Shared cloud file system**

---

# 5. EBS vs EFS vs S3

This is one of the most important comparisons.

| Service | Type   | Main use                |
| ------- | ------ | ----------------------- |
| **EBS** | Block  | Virtual disk for EC2    |
| **EFS** | File   | Shared filesystem       |
| **S3**  | Object | Scalable object storage |

Remember:

```text
EBS → Disk
EFS → Shared Files
S3  → Objects
```

---

# 6. AWS Storage Gateway

## Definition

**AWS Storage Gateway** is a **hybrid cloud storage service** that connects your **on-premises storage environment with AWS storage**.

The idea is:

```text
On-Premises
     ↓
Storage Gateway
     ↓
AWS
```

It allows organizations to continue working with existing on-premises applications/storage while using AWS storage services.

---

# 7. Why Use Storage Gateway?

Suppose a company already has:

```text
On-Premises Data Center
       ↓
Existing applications
       ↓
Existing storage
```

but wants to extend its storage environment to AWS.

Instead of immediately replacing everything:

```text
Existing Storage
      +
AWS Cloud Storage
```

Storage Gateway provides a bridge between them.

### 🧠 Memory

> **Storage Gateway = On-premises storage ↔ AWS**

---

# 8. File Gateway

## Definition

**File Gateway extends local storage to Amazon S3.**

It provides a file-based interface for applications/users while storing the data in AWS S3.

Conceptually:

```text
On-Premises Application
         ↓
     File Gateway
         ↓
         S3
         ↓
      Objects
```

### Scenario

A company has an on-premises application that expects to work with files, but the organization wants the data stored in S3.

File Gateway can provide that bridge.

### 🧠 Memory

> **File Gateway → S3**

---

# 9. Volume Gateway

## Definition

**Volume Gateway** provides block-storage integration between on-premises environments and AWS.

The source describes it as caching local drives to S3 so that local files/data have a cloud-based backup.

Conceptually:

```text
On-Premises
    ↓
Volume Gateway
    ↓
AWS Storage
```

The exact implementation includes cached/stored volume modes, so don't reduce it to simply "S3 backup"; its broader purpose is providing cloud-backed block storage for on-premises applications.

### 🧠 Memory

> **Volume Gateway → Block/volume storage**

---

# 10. Tape Gateway

## Definition

**Tape Gateway** provides **virtual tape storage** for backup workflows.

Instead of maintaining physical tape infrastructure, organizations can use virtual tapes backed by AWS storage.

```text
Backup Application
       ↓
 Tape Gateway
       ↓
Virtual Tapes
       ↓
AWS Storage
```

---

## Why use Tape Gateway?

Organizations that already use **tape-based backup workflows** can transition those workflows to AWS without completely changing their backup applications.

### 🧠 Memory

> **Tape Gateway → Virtual tapes → Backup**

---

# 11. Storage Gateway — Quick Comparison

| Gateway            | Main concept                     |
| ------------------ | -------------------------------- |
| **File Gateway**   | File interface → S3              |
| **Volume Gateway** | Block/volume storage integration |
| **Tape Gateway**   | Virtual tape backup              |

### Memory:

> **File → S3**

> **Volume → Volumes**

> **Tape → Backup**

# 12. AWS Snow Family

## Definition

The **AWS Snow Family** consists of physical devices used to **physically migrate large amounts of data to or from AWS**.

The key reason is:

> Network transfer may be too slow, difficult, or expensive.

```text
Normal:
Data Center → Internet → AWS

Snow:
Data Center → Snow Device → Physical Transport → AWS
```

---

## Devices from your source

### Snowball / Snowball Edge

Briefcase-sized data transfer devices.

The slide describes roughly:

> **50–80 TB**

### Snowmobile

A large cargo container containing storage and compute equipment.

The source states:

> **Up to 100 PB per trailer**

### Snowcone

A smaller Snow device.

The source states:

> **8 TB**

### 🧠 Memory

```text
Snowcone
 ↓
Small

Snowball Edge
 ↓
Large

Snowmobile
 ↓
Massive
```

---

# 13. AWS Backup

## Definition

**AWS Backup** is a **fully managed backup service** that helps centralize and automate backups across AWS services.

The source gives examples including:

* EC2
* EBS
* RDS
* DynamoDB
* EFS
* Storage Gateway

You create **backup plans** to define how backups should be performed.

---

## Why use AWS Backup?

Instead of configuring backups individually for many AWS services:

```text
EC2 backup
EBS backup
RDS backup
EFS backup
DynamoDB backup
```

you can centrally manage backup policies.

```text
              AWS Backup
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
      EC2        EBS        RDS
       ↓          ↓          ↓
                 ...
```

### Scenario

An organization wants daily backups for multiple AWS resources.

AWS Backup can help centralize those backup requirements.

### 🧠 Memory

> **AWS Backup = Centralized and automated AWS backups**

---

# 14. CloudEndure Disaster Recovery

## Definition

The source describes **CloudEndure Disaster Recovery** as continuously replicating machines into a low-cost staging area in a target AWS account and preferred Region.

The purpose is:

> **Fast and reliable recovery if an IT/data-center failure occurs.**

Conceptually:

```text
Primary Data Center
       │
       │ Continuous replication
       ↓
AWS Staging Environment
       │
       ↓
Disaster
       │
       ↓
Recover workload
```

---

## Backup vs Disaster Recovery

This distinction is important.

### Backup

> **Keep a copy of data so you can restore it.**

```text
Data
 ↓
Backup
 ↓
Restore when needed
```

### Disaster Recovery

> **Recover the workload/environment after a major failure.**

```text
Primary Environment
       ↓
      FAIL
       ↓
Recovery Environment
       ↓
Application restored
```

### 🧠 Memory

> **Backup = Save a copy**

> **DR = Recover after failure**

---

# 15. Amazon FSx

## Definition

**Amazon FSx** provides **fully managed, feature-rich file systems** designed for specific workloads.

The source highlights:

> **Feature-rich and highly performant file system**

It supports different file-system technologies.

The screenshot specifically introduces:

```text
Amazon FSx
│
├── FSx for Windows File Server
└── FSx for Lustre
```

---

# 16. Amazon FSx for Windows File Server

## Definition

**Amazon FSx for Windows File Server** provides a managed Windows file system using the **SMB protocol**.

The source states that it can be mounted to Windows servers.

Conceptually:

```text
Windows Server
      ↓
     SMB
      ↓
FSx for Windows File Server
```

---

## Why use it?

Use it when Windows workloads need a managed shared file system compatible with Windows file-sharing environments.

### Scenario

An organization has Windows applications that expect SMB-based file shares.

Instead of managing the file server infrastructure themselves:

```text
Windows Application
       ↓
SMB
       ↓
FSx for Windows File Server
```

### 🧠 Memory

> **FSx for Windows = Windows + SMB**

---

# 17. Amazon FSx for Lustre

## Definition

**Amazon FSx for Lustre** provides a managed filesystem based on the **Lustre** filesystem.

The source associates it with Linux workloads.

```text
Linux Server
     ↓
 Lustre
     ↓
FSx for Lustre
```

Lustre is designed for **high-performance computing and high-throughput workloads**.

### Scenario

A research organization performs large-scale computational workloads requiring a high-performance shared filesystem.

FSx for Lustre can be considered for such workloads.

### 🧠 Memory

> **FSx for Lustre = High-performance Linux/Lustre workloads**

---

# 18. FSx vs EFS

This is an important distinction.

### EFS

General-purpose managed cloud file system:

```text
EC2
 ↓
EFS
 ↓
Shared files
```

### FSx

Provides managed file systems based on specific technologies and workload requirements:

```text
FSx
├── Windows File Server
└── Lustre
```

So think:

> **EFS = General AWS managed file system**

> **FSx = Managed specialized file systems**
