# AWS Config

## 1. What is Change Management?

### Definition

In cloud infrastructure, **change management** is a formal process used to:

* **Monitor** changes
* **Enforce** required changes/configurations
* **Remediate** changes

The main idea is to make sure cloud resources remain in the required configuration.

### Simple example

Suppose your company requires an EC2 instance to have a specific security configuration.

```text
Required configuration
        ↓
Monitor
        ↓
Configuration changes?
        ↓
Yes → Remediate
```

---

# 2. What is Compliance-as-Code (CaC)?

### Definition

**Compliance-as-Code** means using programming/configuration rules to automate:

* Monitoring compliance
* Enforcing compliance
* Remediating configuration changes

Instead of manually checking every AWS resource, you define the expected configuration and let automation check resources against it.

### Simple idea

```text
Compliance Requirement
        ↓
     Code/Rule
        ↓
Check AWS Resource
        ↓
 ┌──────┴──────┐
 ↓             ↓
Compliant   Non-compliant
 ↓             ↓
Pass        Remediate
```

---

# 3. What is AWS Config?

### Definition

**AWS Config** is a **Compliance-as-Code framework/service** that allows you to **manage and monitor configuration changes in your AWS accounts on a per-Region basis**.

The key idea from your source is:

> **AWS Config = Compliance + Configuration Change Management**

It helps you understand whether AWS resources are configured according to your required rules.

---

# 4. How AWS Config Works

A simplified flow is:

```text
AWS Resource
     ↓
AWS Config
     ↓
Config Rule
     ↓
Evaluate Resource
     ↓
 ┌───────────────┐
 │               │
 ↓               ↓
Compliant    Non-compliant
 │               │
 ↓               ↓
Pass          Remediate
```

If it doesn't:


# 5. When Should You Use AWS Config?

Your screenshot gives several important use cases.

### ① Keep resources configured in a specific way for compliance

For example, you want resources to follow a required configuration standard.

```text
Required configuration
        ↓
AWS Config Rule
        ↓
Resource evaluation
```

If the configuration changes and violates the rule, AWS Config can identify it.

---

### ② Track configuration changes

You want to keep track of changes made to AWS resources.

For example:

```text
EC2 configuration
      ↓
Configuration changed
      ↓
AWS Config records/evaluates change
```

This is useful when you need to understand how resource configurations changed over time.

---

### ③ Get a list of resources within a Region

AWS Config can help you obtain information about resources and their configurations within an AWS Region.

Think:

> **"What resources do I have in this Region, and how are they configured?"**

---

### ④ Analyze potential security weaknesses

The screenshot specifically mentions using **detailed historical information** to analyze potential security weaknesses.

For example, you may want to investigate:

```text
Resource configuration
       ↓
Historical changes
       ↓
Identify configuration problems
       ↓
Investigate security weakness
```

# 6. AWS Config Rules

A **Config Rule** defines the configuration/compliance condition that a resource should satisfy.

Conceptually:

```text
Rule:
"Resource must satisfy X"
          ↓
       AWS Config
          ↓
      Evaluate
       ↙     ↘
    Pass     Fail
```

### Example

Imagine a rule requiring a particular configuration.

```text
EC2
 ↓
Config Rule
 ↓
Does it meet requirement?
 ↓
 ├── YES → Compliant ✅
 └── NO  → Non-compliant ❌
```

The source image illustrates this using Lambda-based rule logic.

---

# 7. Remediation

### Definition

**Remediation** means taking action to correct a resource that does not satisfy the required configuration.

Example:

```text
AWS Config
    ↓
Rule evaluation
    ↓
❌ Non-compliant
    ↓
Remediation
    ↓
✅ Correct configuration
```

This is one of the important differences between simply **monitoring** configuration and actually **correcting** it.

---

# 8. Important Concept: Per Region

Your source specifically states that AWS Config manages changes **on a per-Region basis**.

So when studying AWS Config, remember:

> **AWS Config configuration data/rules are Region-specific unless you use additional aggregation mechanisms.**

For the foundational exam, associate AWS Config strongly with **resource configuration and compliance in a Region**.

# AWS Config vs CloudTrail

This distinction is very useful:

| Service            | Main purpose                        |
| ------------------ | ----------------------------------- |
| **AWS Config**     | Resource configuration & compliance |
| **AWS CloudTrail** | API activity / API calls            |

### Easy example

If you ask:

**"Is my resource configured correctly?"**

→ **AWS Config**

If you ask:

**"Who made this API call?"**

→ **AWS CloudTrail**

### Memory

> **Config = Configuration**
> **CloudTrail = API activity**

---

# AWS Config vs Trusted Advisor

| Service             | Main purpose                      |
| ------------------- | --------------------------------- |
| **AWS Config**      | Configuration compliance          |
| **Trusted Advisor** | AWS best-practice recommendations |

Example:

**"Check whether resources follow my required configuration rules."**

→ AWS Config

**"Give me recommendations to improve my AWS environment."**

→ Trusted Advisor

# Scenario-Based Example

Imagine your company requires certain AWS resources to maintain a specific security configuration.

You create:

```text
Compliance requirement
        ↓
AWS Config Rule
        ↓
Evaluate resources
        ↓
 ┌───────────────┐
 │               │
 ↓               ↓
Compliant    Non-compliant
 │               │
 ↓               ↓
Continue      Remediation
```

Now if someone changes a resource and it no longer satisfies the requirement, AWS Config can identify the configuration as **non-compliant** and remediation can be performed.
