# 💰 Standard RI vs Convertible RI

This screenshot explains the main difference between **Standard Reserved Instances** and **Convertible Reserved Instances**.

The core idea is:

> **Standard RI = more limited flexibility**
> **Convertible RI = more flexibility through exchange**

---

## 1. Standard Reserved Instance

### Definition

A **Standard RI** provides discounted pricing with more limited flexibility compared with a Convertible RI.

According to your source, **RI attributes can be modified** in certain ways.

### Modifications shown in the source

You can:

* Change the **Availability Zone within the same Region**
* Change the scope of a **Zonal RI ↔ Regional RI**
* Change the **instance size** — Linux/Unix only, default tenancy
* Change the network from **EC2-Classic → VPC and vice versa** (source-specific/legacy concept)

So the important idea is:

> **Standard RI → modify certain attributes, but cannot be exchanged for another RI.**

---

## 2. Standard RI Cannot Be Exchanged

The screenshot says:

> **Can't be exchanged**

So you cannot exchange a Standard RI for a different Standard RI with a completely different set of attributes.

However, the source does show certain **modifications** are possible.

This distinction is important:

```text
Standard RI
     ↓
Modify certain attributes
     ✗
Exchange for another RI
```

---

# 3. Convertible Reserved Instance

### Definition

A **Convertible RI** provides more flexibility because you can **exchange it during the term** for another Convertible RI with different attributes.

The screenshot says RI attributes **can't be modified directly**; instead, you perform an **exchange**.

```text
Convertible RI
      ↓
Exchange
      ↓
Another Convertible RI
```

---

## 4. What Can Be Changed Through Exchange?

According to your source, a Convertible RI can be exchanged for another Convertible RI with new:

* **Instance family**
* **Instance type**
* **Platform**
* **Scope**
* **Tenancy**

For example:

```text
Convertible RI
m5.large
   ↓
Exchange
   ↓
r5.xlarge
```

The exact exchange must satisfy the applicable Convertible RI rules, including the value requirement covered in your earlier material.

---

# 5. Standard vs Convertible

| Feature                | Standard RI                 | Convertible RI          |
| ---------------------- | --------------------------- | ----------------------- |
| Modify attributes      | ✅ Certain modifications     | ❌ Direct modification   |
| Exchange during term   | ❌                           | ✅                       |
| Change instance family | Not through exchange        | ✅ Through exchange      |
| Change instance type   | Limited modification rules  | ✅ Through exchange      |
| Change platform        | Limited                     | ✅ Through exchange      |
| Change scope           | Certain scope modifications | ✅ Through exchange      |
| Change tenancy         | Limited                     | ✅ Through exchange      |
| RI Marketplace         | ✅ Can be bought/sold        | ❌ Cannot be bought/sold |

---

# 6. RI Marketplace

This is another important difference shown in your screenshot.

### Standard RI

```text
Standard RI
     ↓
RI Marketplace
     ↓
Can be bought/sold
```

### Convertible RI

```text
Convertible RI
     ↓
Cannot be bought/sold
in RI Marketplace
```

So:

> **Standard RI → Marketplace**

> **Convertible RI → No Marketplace**

---

# 🎯 Scenario

Imagine you have a **Standard RI** and your workload changes.

You can perform certain supported modifications, such as changing the AZ within the same Region or changing certain instance-size characteristics under the stated conditions.

But if you want to fundamentally change the RI's attributes, a Standard RI doesn't provide the same exchange mechanism.

Now imagine you have a **Convertible RI**:

```text
Current workload
      ↓
m5.large
      ↓
Workload changes
      ↓
Exchange Convertible RI
      ↓
Different eligible RI
```

This gives you more flexibility during the commitment period.
