# AWS Well-Architected Framework – General Design Principles

The goal is to build systems that are **scalable, reliable, efficient, secure, and able to evolve over time**.

The six principles shown in your notes are:

---

## 1. Stop Guessing Your Capacity Needs

### Meaning

Don't try to predict exactly how much computing capacity your application will need in the future.

Traditional infrastructure often requires you to buy servers based on estimated future demand.

With cloud computing, you can provision resources **based on actual demand**.

### Example

Suppose an application normally receives:

* 1,000 users/day
* 100 requests/sec

But during a festival or sale, traffic suddenly becomes:

* 100,000 users/day
* 10,000 requests/sec

Instead of permanently purchasing enough servers for 10,000 requests/sec, cloud resources can **scale according to demand**.

### Key idea

> **Use as little or as much capacity as required based on demand.**

This helps avoid:

* Over-provisioning → paying for unused resources
* Under-provisioning → poor performance or outages

### AWS concepts related to this

* Auto Scaling
* Elastic Load Balancing
* Serverless services
* On-demand resources

**Remember:**
`Demand changes → Capacity changes`

---

# 2. Test Systems at Production Scale

### Meaning

Don't assume that a system will work correctly at large scale simply because it works in a small testing environment.

You should test your architecture under conditions that are close to **real production workloads**.

### Example

Imagine your production application normally handles:

`10,000 requests/second`

But your testing environment only handles:

`100 requests/second`

Your application may appear perfectly healthy during testing but fail when exposed to production traffic.

### AWS approach

You can create a testing environment that resembles production, perform the tests, and then **remove the temporary resources when testing is finished**.

This is particularly useful in the cloud because infrastructure can be created and destroyed relatively easily.

### Important idea

> **Test the system under realistic conditions before relying on it in production.**

---

# 3. Automate to Make Architectural Experimentation Easier

### Meaning

Use automation instead of manually creating and modifying infrastructure.

Automation makes it easier to:

* Create infrastructure
* Change configurations
* Test different architectures
* Reproduce environments
* Roll back changes
* Detect configuration differences

### Example from your material

**AWS CloudFormation** can be used with:

* Change Sets
* Stack Updates
* Drift Detection

Instead of manually creating 20 AWS resources, you can define the infrastructure and deploy it consistently.

### Why this matters

Imagine testing two architectures:

**Architecture A**

```text
EC2 → RDS
```

**Architecture B**

```text
Lambda → DynamoDB
```

With automated infrastructure, you can create and test both environments much more easily.

### Key idea

> **Automate infrastructure so you can experiment, test, and change architecture safely.**

---

# 4. Allow for Evolutionary Architectures

### Meaning

Don't design your architecture as if it will never change.

Technology, requirements, traffic patterns, security requirements, and business needs constantly change.

Your architecture should therefore be capable of **evolving over time**.

### Example

You might initially deploy:

```text
Application → EC2
```

Later, your requirements change and you introduce:

```text
Application
     ↓
Load Balancer
     ↓
Auto Scaling EC2
```

Eventually you might move parts of the application toward:

```text
Application
     ↓
API Gateway
     ↓
Lambda
     ↓
DynamoDB
```

The important idea is that you don't need to design everything perfectly on Day 1.

### Your material mentions

* CI/CD
* Rapid releases
* Nightly releases
* Lambda runtime changes

These encourage architectures that can adapt rather than remain static.

### Key idea

> **Build architectures that can change as your requirements and technology change.**

---

# 5. Drive Architectures Using Data

### Meaning

Don't make architectural decisions purely based on assumptions or opinions.

Use **real data** to understand how your system behaves.

For example, instead of saying:

> "I think our application needs a bigger EC2 instance."

Look at actual:

* CPU utilization
* Network traffic
* Memory usage
* Request rates
* Application logs
* Error rates
* Latency

Then make the decision.

### AWS services mentioned in your material

**CloudWatch**

Can provide monitoring and metrics.

**CloudTrail**

Provides information about AWS API activity and account actions.

Together, these can provide useful information about what's happening in your environment.

### Example

You notice:

```text
CPU = 25%
Memory = 40%
Network = High
```

Instead of increasing CPU capacity blindly, you investigate the actual bottleneck.

### Key idea

> **Measure → Analyze → Decide → Improve**

---

# 6. Improve Through Game Days

### Meaning

A **Game Day** is a controlled exercise where you intentionally test how your system behaves when something goes wrong.

The purpose is to discover weaknesses **before a real incident happens**.

### Example

Imagine you have an application running on EC2.

During a Game Day, you intentionally simulate:

```text
EC2 failure
      ↓
Does another instance take over?
      ↓
Does the application remain available?
```

Your material also gives the example of intentionally generating traffic or killing EC2 instances to test recovery.

### What you're testing

For example:

* What happens if an EC2 instance fails?
* Does Auto Scaling replace it?
* Does the load balancer redirect traffic?
* Can the application recover?
* How quickly does it recover?
* Are monitoring and alerts working?

### Important

Game Days should be **controlled experiments**, not random destruction of production infrastructure.

### Key idea

> **Intentionally test failure so you can discover and fix weaknesses before real failures occur.**
