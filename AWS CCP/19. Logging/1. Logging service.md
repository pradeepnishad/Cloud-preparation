# AWS Logging Services

AWS provides several services for **recording, monitoring, visualizing, and troubleshooting activity and applications**.

The key services in your notes are:

- **AWS CloudTrail**
- **Amazon CloudWatch**
- **AWS X-Ray**

---

# 1. AWS CloudTrail

### Definition

**AWS CloudTrail logs API calls** made through interfaces such as:

- AWS SDK
- AWS CLI
- AWS Management Console/API activity

It helps answer:

> **Who did what in my AWS account?**

### What can CloudTrail tell you?

For example:

- Who created an S3 bucket?
- Who launched an expensive EC2 instance?
- Who launched a SageMaker notebook?
- Which identity made an API call?

The key idea is **activity/audit logging**.

### Why use CloudTrail?

CloudTrail can help you:

- Investigate AWS activity
- Detect developer misconfiguration
- Detect potentially malicious activity
- Determine who performed an action
- Support automated responses

### Scenario

Suppose someone launches an expensive EC2 instance unexpectedly.

You can use CloudTrail to investigate the API activity and determine **which identity performed the action and what API call was made**.

### Exam keyword

> **"Who created/launched/changed this AWS resource?" → CloudTrail**

### Memory

**CloudTrail = Track API activity**

# 2. Amazon CloudWatch

CloudWatch is a **collection of monitoring and observability capabilities**.

Your source breaks it into several components.

---

## CloudWatch Logs

### Definition

**CloudWatch Logs** provides a centralized place to store:

- AWS service log data
- Application logs

### Example

An application running on EC2 produces logs:

```text
Application
     ↓
CloudWatch Logs
     ↓
Centralized log storage
```

### Use case

If an application is producing errors, you can inspect its logs through CloudWatch Logs.

### Memory

**Logs → Log data**

---

# 3. CloudWatch Metrics

### Definition

A **metric** represents a time-ordered set of data points.

Metrics are used to monitor values over time.

For example:

```text
CPU Utilization

10:00 → 30%
10:05 → 45%
10:10 → 80%
10:15 → 95%
```

You can monitor metrics such as resource utilization and other measurable values.

### Why use metrics?

To understand **what is happening to a resource over time**.

### Exam keyword

> **"Monitor a value over time" → CloudWatch Metrics**

### Memory

**Metrics = Measurements**

---

# 4. CloudWatch Events / EventBridge

Your source describes **CloudWatch Events (EventBridge)** as triggering an event based on a condition.

For example:

```text
Condition/Event
      ↓
EventBridge
      ↓
Trigger action
```

Example from your notes:

> Every hour, take a snapshot of a server.

This represents **event-driven automation**.

### Important terminology

AWS EventBridge is the current service name. **CloudWatch Events was the former name.**

### Memory

**EventBridge = Events trigger actions**

---

# 5. CloudWatch Alarms

### Definition

**CloudWatch Alarms trigger notifications/actions based on metrics.**

For example:

```text
EC2 CPU
  ↓
CloudWatch Metric
  ↓
CPU > threshold
  ↓
CloudWatch Alarm
  ↓
Notification/action
```

### Scenario

You configure an alarm:

> If CPU utilization stays above 80%, trigger an alert.

### Why use it?

To get notified when a monitored metric reaches a configured condition.

### Exam keyword

> **"Trigger notification when metric crosses a threshold" → CloudWatch Alarm**

### Memory

**Alarm = Alert**

# 6. CloudWatch Dashboard

### Definition

**CloudWatch Dashboards create visualizations based on metrics.**

Instead of looking at individual metrics separately, you can create a dashboard to visualize important metrics together.

Example:

```text
CloudWatch Dashboard

Memory        █████
Network       █████████
Requests      ██████
```

### Why use it?

For quickly viewing the health and performance of your environment.

### Exam keyword

> **"Visualize metrics" → CloudWatch Dashboard**

### Memory

**Dashboard = Display**

# 7. AWS X-Ray

### Definition

**AWS X-Ray is a distributed tracing system.**

It helps you understand how data/request flows through different parts of an application, especially **microservices**.

### What does it help you see?

Your source highlights:

- How data moves from one application to another
- How long the movement/request took
- Whether the request failed to move forward
- Where issues occur between microservices

### Example

Imagine:

```text
User
 ↓
API
 ↓
Service A
 ↓
Service B
 ↓
Database
```

If the application is slow, X-Ray can help identify **which part of the request path is causing the problem**.

### Why use X-Ray?

For troubleshooting **distributed applications and microservices**.

### Exam keyword

> **"Trace a request across multiple microservices" → AWS X-Ray**

### Memory

**X-Ray = Trace the request path**

# CloudTrail vs CloudWatch vs X-Ray

This is one of the most important distinctions.

| Service | Main purpose | Think |
|---|---|---|
| **CloudTrail** | Records AWS API activity | **Who did what?** |
| **CloudWatch Logs** | Stores logs | **What was logged?** |
| **CloudWatch Metrics** | Monitors measurements | **What is happening?** |
| **CloudWatch Alarms** | Responds to metric conditions | **Is something wrong?** |
| **CloudWatch Dashboard** | Visualizes metrics | **Show me the status** |
| **EventBridge** | Responds to events | **Something happened → react** |
| **X-Ray** | Distributed request tracing | **Where did the request go/slow/fail?** |

Imagine an AWS e-commerce application.

Use:

**CloudWatch Logs**

```text
Application
     ↓
CloudWatch Logs
```

Use:

**AWS X-Ray**

```text
Service A → Service B → Service C
     ↓

```

Use:

**EventBridge**

```text
AWS Event
    ↓
EventBridge
    ↓
Target/action
```
