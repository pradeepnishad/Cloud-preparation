1. **Amazon DynamoDB**
2. **Amazon DocumentDB**
3. **Amazon Keyspaces**

---

## 1. Amazon DynamoDB

### Definition

**Amazon DynamoDB is a serverless NoSQL database service that supports key-value and document data models.**

It is designed to scale to **very large numbers of records** without you having to manage database servers or database shards.

### What does DynamoDB store?

It supports:

**Key-value data**

```text
UserID → User information
U101   → Pradeep
U102   → Rahul
```

And **document data**:

```json
{
  "UserID": "U101",
  "Name": "Pradeep",
  "Age": 24,
  "Skills": ["AWS", "Python", "Linux"]
}
```

### Why use DynamoDB?

Use it when you need:

* Very fast database access
* Massive scalability
* Serverless database management
* Key-value or document data
* Applications that may grow to very large scale

### Scenario

Imagine an online shopping application with millions of customers.

You could store:

```text
Customer ID → Customer information
```

and retrieve a customer's information very quickly.

### Important exam point

> **DynamoDB = Serverless + NoSQL + Key-value + Document**

Your screenshot specifically emphasizes **massive scalability**.

# 2. Amazon DocumentDB

### Definition

**Amazon DocumentDB is a managed NoSQL document database service designed to be compatible with MongoDB workloads.**

The important word here is:

> **Document**

Data is stored in document-style structures such as JSON/BSON-like documents.

Example:

```json
{
  "customer_id": "C101",
  "name": "Pradeep",
  "address": {
    "city": "Mumbai",
    "country": "India"
  },
  "orders": [
    {
      "product": "Laptop",
      "price": 60000
    }
  ]
}
```

### Why use DocumentDB?

Use it when your application works with **document-oriented data** and you want an AWS-managed database designed for **MongoDB-compatible workloads**.

### Scenario

Suppose you're building a content application where different users can have different profile structures:

```json
{
  "name": "Pradeep",
  "skills": ["AWS", "Linux"]
}
```

Another user might have:

```json
{
  "name": "Rahul",
  "skills": ["Java"],
  "experience": 5,
  "certifications": ["AWS"]
}
```

A document-oriented model can handle this type of flexible structure naturally.

### Exam point

> **DocumentDB → Document database → MongoDB compatibility**

# 3. Amazon Keyspaces

### Definition

**Amazon Keyspaces is a fully managed Apache Cassandra-compatible database service.**

Cassandra is a **NoSQL database** commonly associated with highly scalable distributed workloads.

The screenshot describes it as a NoSQL key-value/column-oriented database.

### Why use Keyspaces?

Use it when you want:

* Cassandra-compatible workloads
* Very large-scale NoSQL applications
* A managed service instead of managing Cassandra infrastructure yourself

### Scenario

Imagine an application generating enormous amounts of data from millions of devices.

You could use a Cassandra-compatible database architecture where data is distributed across a large infrastructure.

Instead of manually managing Cassandra servers, **Amazon Keyspaces manages the underlying database infrastructure**.

### Exam point

> **Keyspaces → Apache Cassandra**

## Important distinction from your previous question

You asked what a **document database** is.

Now connect it like this:

```text
NoSQL
│
├── Key-Value
│      └── DynamoDB
│
├── Document
│      ├── DynamoDB
│      └── DocumentDB
```

So **DynamoDB can be both a key-value and document database**, while **DocumentDB is specifically focused on document-oriented workloads**.
