# 🔑 What Is a Key-Value Store?

## 1. Definition

A **key-value store** is a type of **NoSQL database** that stores data as a collection of **key-value pairs**.

The basic idea is:

> **Key → Value**

For example:

```text
"user123" → "Pradeep"
"user456" → "Rahul"
"user789" → "Priya"
```

The **key** uniquely identifies the data, and the **value** contains the information associated with that key.

---

# 2. How Does It Work?

Think of it like a **dictionary** in Python:

```python
users = {
    "user123": "Pradeep",
    "user456": "Rahul",
    "user789": "Priya"
}
```

Here:

```text
Key              Value
────────────────────────────
user123     →    Pradeep
user456     →    Rahul
user789     →    Priya
```

If you know the key:

```text
user123
```

you can retrieve its associated value:

```text
Pradeep
```

---

# 3. What Can the Value Contain?

The value doesn't necessarily have to be a simple string.

It can contain a more complex piece of data.

For example:

```text
Key: user123

Value:
{
    "name": "Pradeep",
    "age": 24,
    "city": "Mumbai",
    "role": "Cloud Engineer"
}
```

So:

```text
Key
 ↓
user123

Value
 ↓
{name, age, city, role}
```

The exact data model depends on the key-value database.

---

# 4. Why Use a Key-Value Store?

Key-value databases are useful when your application primarily needs to:

> **Store and quickly retrieve data using a unique key.**

For example:

```text
Application
    ↓
"session_12345"
    ↓
Key-Value Database
    ↓
Session information
```

Instead of searching through many rows and columns, the application can directly use the key.

---

# 5. Scenario-Based Example — User Sessions

Imagine you're building a website.

When a user logs in, you need to remember their session:

```text
Key:
session_12345

Value:
{
   "user_id": 101,
   "login_time": "...",
   "role": "customer"
}
```

Later:

```text
User
 ↓
Session ID = session_12345
 ↓
Key-Value Store
 ↓
Retrieve session
```

This is a good example of a workload that can benefit from key-value storage.

# 7. Key-Value Store vs Relational Database

### Relational database

Data is organized into tables:

```text
CUSTOMERS

ID | Name    | City
---|---------|--------
101| Pradeep | Mumbai
102| Rahul   | Delhi
```

You typically query it using SQL:

```sql
SELECT * FROM customers WHERE id = 101;
```

### Key-value store

```text
101 → {
       "name": "Pradeep",
       "city": "Mumbai"
     }
```

You primarily retrieve the value using its key.

---

# 8. Key-Value Store vs Document Database

These are both NoSQL models, but their focus is different.

### Key-value

```text
Key → Value
```

Example:

```text
user101 → {user information}
```

The key is the primary way you access the value.

### Document

Documents have a structured format and can often be queried using fields inside the document.

For example:

```json
{
  "id": 101,
  "name": "Pradeep",
  "city": "Mumbai"
}
```

The distinction becomes important when you need to query/filter based on fields inside the stored data.

---

# 9. AWS Example — DynamoDB

The most important AWS service to associate with this topic is:

> **Amazon DynamoDB**

DynamoDB is a **fully managed NoSQL database service** that supports **key-value and document data models**.

A simple DynamoDB item might look conceptually like:

```text
Partition Key: user101

name: Pradeep
city: Mumbai
role: Cloud Engineer
```

The key allows DynamoDB to locate the item.

---

# 10. Why DynamoDB Is Useful

DynamoDB is designed for applications that need:

* Very fast data access
* Large-scale workloads
* Flexible data models
* Automatic scaling capabilities
* Managed infrastructure
* High availability

For example:

```text
Millions of users
       ↓
Application
       ↓
DynamoDB
       ↓
User data
```

AWS manages much of the underlying database infrastructure for you.

# 11. Key-Value Store Scenario

Imagine you're building an online gaming application.

When player `player002` logs in:
