# 🔐 Security Groups vs NACLs

This is an **important AWS networking topic** because both **Security Groups** and **Network ACLs (NACLs)** act as virtual firewalls, but they work at **different levels** and have different rule behavior.

---

# 1. Network ACL — NACL

### Definition

A **Network Access Control List (NACL)** acts as a **virtual firewall at the subnet level**.

A NACL controls traffic entering and leaving a **subnet**.

```text
VPC
 │
 ├── Subnet A
 │     ↓
 │    NACL
 │     ↓
 │   Instances
 │
 └── Subnet B
       ↓
      NACL
       ↓
     Instances
```

### How does it work?

According to your source:

> You create **Allow and Deny rules**.

For example, you can create a rule to deny traffic from a particular IP address.

```text
NACL

DENY
203.0.113.50
    ↓
Subnet
```

This is useful when you want to block a known unwanted IP at the subnet level.

### Why use NACL?

Use a NACL when you want to control traffic at the **subnet boundary**.

For example:

> A known malicious IP should be blocked from accessing resources in a subnet.

You can create a **DENY** rule for that IP.

### Important characteristics

For Cloud Practitioner, remember:

* Subnet-level firewall
* Supports **ALLOW and DENY**
* Controls traffic entering/leaving the subnet
* **Stateless**

---

# 2. Security Group

### Definition

A **Security Group acts as a virtual firewall at the instance/resource level**.

It controls traffic associated with resources such as EC2 instances.

```text
Subnet
   │
   ├── EC2
   │    └── Security Group
   │
   └── EC2
        └── Security Group
```

### How does it work?

According to your source:

> It implicitly denies all traffic. You create **only Allow rules**.

For example:

```text
Security Group

ALLOW
TCP 22
Source: appropriate IP/network
        ↓
       EC2
```

This allows SSH traffic when the corresponding rule is configured.

### Why use Security Groups?

Use Security Groups to control which network traffic is allowed to reach a particular resource.

For example:

```text
Internet
   ↓
TCP 443
   ↓
Security Group
   ↓
EC2 Web Server
```

You can allow HTTPS traffic while not allowing other unwanted inbound traffic.

### Important characteristics

* Resource/instance-level firewall
* **Allow rules only**
* **Stateful**
* Traffic is implicitly denied unless allowed by the group's rules

# 🔥 NACL vs Security Group

This table is the one you should memorize for the exam:

| Feature          | NACL                                        | Security Group                   |
| ---------------- | ------------------------------------------- | -------------------------------- |
| Firewall level   | **Subnet**                                  | **Resource/instance**            |
| Rules            | **Allow + Deny**                            | **Allow only**                   |
| Stateful         | **No — stateless**                          | **Yes — stateful**               |
| Applies to       | Subnet                                      | Resource/ENI                     |
| Default behavior | Default NACL allows traffic unless modified | Traffic is denied unless allowed |
| Example use      | Block a specific IP                         | Allow SSH/HTTPS to EC2           |

# 4. Why Would You Use Both?

They can work together.

Imagine:

```text
Internet
   ↓
NACL
   ↓
Subnet
   ↓
Security Group
   ↓
EC2
```

The traffic must pass the relevant network controls.

For example:

### NACL

```text
DENY
203.0.113.50
```

The known unwanted IP is blocked at the subnet level.

### Security Group

```text
ALLOW TCP 443
```

Only HTTPS traffic that is permitted by the security group can reach the resource.

So you can have **subnet-level controls + resource-level controls**.

# 5. Stateful vs Stateless

This is one of the most important differences.

### Security Group = Stateful

If an inbound connection is allowed, the response traffic is automatically allowed as part of that established connection.

Example:

```text
Client
  ↓
HTTPS request
  ↓
Security Group
  ↓
EC2
  ↑
HTTPS response
```

You don't need to create a separate rule specifically to allow the response traffic.

### NACL = Stateless

Inbound and outbound traffic are evaluated separately.

So you need to consider rules in **both directions**.

Think:

```text
NACL

Inbound rules
      ↓
   Subnet

Outbound rules
      ↑
   Subnet
```

### Memory trick

> **Security Group = Stateful**
> **NACL = Not Stateful**

The **"N" in NACL → Not stateful** is a useful memory trick.

# 6. Specific IP Blocking

Your screenshot specifically highlights:

> **NACL → Block a specific IP address known for abuse**

This is an important distinction for your exam.

Suppose:

```text
203.0.113.50
```

is a known unwanted IP.

You could create a NACL rule:

```text
DENY
203.0.113.50
```

### Why not Security Group?

Your source emphasizes that Security Groups use **allow rules only**, so they aren't designed to create an explicit deny rule for one particular IP.

For an explicit **DENY**, think:

> **NACL**
