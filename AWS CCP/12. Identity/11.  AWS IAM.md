# 🔐 AWS Identity and Access Management (IAM)

## 1. Definition

**AWS Identity and Access Management (IAM)** is an AWS service used to **create and manage AWS users and groups and control their access to AWS resources**.

Simple definition:

> **IAM controls who can access AWS resources and what they are allowed to do.**

The basic idea is:

```text
Who are you?
     ↓
IAM Identity
     ↓
What can you do?
     ↓
IAM Permissions / Policies
     ↓
AWS Resources
```

---

# 2. IAM Policies

An **IAM Policy** is a **JSON document** that defines permissions.

It determines what actions an identity can perform on AWS resources.

For example, a policy could allow a user to:

```text
Read S3 objects
```

but deny them permission to:

```text
Delete S3 objects
```

The screenshot describes policies as JSON documents that grant permissions to a specific **user, group, or role**.

Conceptually:

```text
IAM Policy
   ↓
Allow / Deny
   ↓
AWS API Actions
   ↓
AWS Resources
```

---

# 3. IAM Permissions

**IAM permissions** describe the AWS API actions that an identity **can or cannot perform**.

For example:

```text
s3:GetObject
```

means permission to retrieve an object from S3.

Another action could be:

```text
s3:DeleteObject
```

which relates to deleting an S3 object.

These permissions are represented inside IAM policy documents.

### Easy distinction

> **Policy = JSON document containing permissions**

> **Permission = what action is allowed/denied**

---

# 4. IAM Users

An **IAM User** represents an individual identity that can interact with AWS.

The screenshot describes users as end users who can:

* Log into the AWS Console
* Interact with AWS resources programmatically
* Use AWS through interfaces

Example:

```text
Company
│
├── Alice → IAM User
├── Bob   → IAM User
└── John  → IAM User
```

Each user can have permissions assigned through policies.

---

# 5. IAM Groups

An **IAM Group** is a collection of IAM users.

Groups are useful when multiple users need similar permissions.

For example:

```text
Developers Group
│
├── Alice
├── Bob
└── John
```

You can attach appropriate policies to the group rather than managing identical permissions individually.

Example groups:

* Administrators
* Developers
* Auditors

### Why use groups?

Imagine you have 50 developers.

Instead of assigning the same policy to every developer individually:

```text
Developer Policy
       ↓
Developers Group
       ↓
50 Users
```

This makes permission management easier.

---

# 6. IAM Roles

An **IAM Role** is an identity that can be **assumed** and has permissions through attached policies.

Your screenshot describes roles as granting AWS resources permission to perform specific AWS API actions.

A very common example is:

```text
EC2
 ↓
IAM Role
 ↓
Policy
 ↓
S3 permissions
 ↓
S3
```

Suppose an EC2 instance needs to read files from S3.

Instead of putting AWS access keys directly inside the application:

```text
EC2
 ↓
Hard-coded credentials ❌
 ↓
S3
```

you can associate an IAM role with the EC2 instance:

```text
EC2
 ↓
IAM Role
 ↓
S3 permissions
 ↓
S3
```

The application can then make the permitted AWS API calls.

---

# 7. Users vs Groups vs Roles

This is **very important for AWS exams**.

| IAM Component | Think of it as      | Main purpose                                     |
| ------------- | ------------------- | ------------------------------------------------ |
| **User**      | Person/identity     | Individual AWS identity                          |
| **Group**     | Team                | Organize users with common permissions           |
| **Role**      | Assumable identity  | Give permissions to AWS resources/users/services |
| **Policy**    | Permission document | Defines allowed/denied actions                   |

### Memory trick

> **User = Person**

> **Group = People**

> **Role = Permissions an identity can assume**

> **Policy = Rules**

---

# 8. Example

Imagine a company has:

```text
AWS Account
│
├── Developers Group
│     ├── Alice
│     ├── Bob
│     └── John
│
├── Auditors Group
│     ├── Sarah
│     └── David
│
└── EC2
      ↓
   IAM Role
      ↓
   S3 Policy
```

Developers might receive permissions to deploy applications.

Auditors might receive read-only permissions.

The EC2 instance can use its role to access other AWS services.

# 🧠 Final Summary

```text
                    IAM
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Users        Groups        Roles
        │            │            │
        └────────────┼────────────┘
                     ↓
                  Policies
                     ↓
                Permissions
                     ↓
              AWS Resources
```

### The most important thing to remember:

**IAM = Who can access what, and what can they do?**

**User → individual identity**

**Group → collection of users**

**Role → assumable identity used to grant permissions**

**Policy → JSON rules defining permissions**

**Permission → specific AWS API action that can/cannot be performed**
