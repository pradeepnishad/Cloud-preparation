# 🔐 Zero Trust on AWS

This screenshot shows **AWS identity security controls** that can be used to implement Zero Trust principles.

The main idea is:

> **Use identity and access controls to verify who can access AWS resources and under what conditions.**

---

## 1. AWS IAM

**AWS Identity and Access Management (IAM)** is the main AWS service shown in the diagram for implementing identity-based security controls.

The screenshot lists several IAM-based controls:

```text
IAM
│
├── IAM Policies
├── Permission Boundaries
├── Service Control Policies
└── IAM Policy Conditions
```

These controls determine **what identities can access and what they are allowed to do**.

---

# 2. IAM Policies

### Definition

**IAM policies** define permissions for AWS identities.

They can specify:

* Which actions are allowed or denied
* Which AWS resources can be accessed
* Under what conditions access is allowed

Example concept:

```text
User/Role
    ↓
IAM Policy
    ↓
Allow access to specific AWS resource
```

This supports the Zero Trust idea of giving users only the access they need.

---

# 3. Permission Boundaries

### Definition

A **permission boundary** establishes a maximum permissions boundary for an IAM identity.

Think:

```text
IAM Policy
    ↓
What permissions could be granted?

Permission Boundary
    ↓
What is the maximum this identity can actually have?
```

So even if an identity receives additional IAM policies, its effective permissions cannot exceed the boundary.

---

# 4. Service Control Policies (SCPs)

### Definition

**Service Control Policies (SCPs)** are organization-level policies used to control the maximum available permissions for AWS accounts in an AWS Organization.

Think:

```text
AWS Organization
      ↓
SCP
      ↓
Account permissions boundary
      ↓
IAM permissions
```

The screenshot calls these:

> **Organization-wide Policies**

So SCPs are useful when you want to enforce security restrictions across multiple AWS accounts.

---

# 5. IAM Policy Conditions

This is particularly important for **Zero Trust** because access can be restricted based on additional context.

The screenshot gives four examples.

### `aws:SourceIp`

Restrict access based on **IP address**.

```text
Request
   ↓
Source IP?
   ↓
Allowed → Access
Blocked → Deny
```

---

### `aws:RequestedRegion`

Restrict access based on the **AWS Region** being requested.

For example, an organization could restrict certain operations to approved Regions.

---

### `aws:MultiFactorAuthPresent`

Restrict access depending on whether **MFA is enabled/present** for the request.

Conceptually:

```text
MFA?
 ├── Yes → Allow
 └── No  → Restrict/Deny
```

This connects directly to the Zero Trust principle of verifying identity more strongly.

---

### `aws:CurrentTime`

Restrict access based on **time of day**.

For example:

```text
Request
   ↓
What time is it?
   ↓
Allowed period?
   ├── Yes → Allow
   └── No → Restrict
```

---

# 6. Zero Trust + IAM Conditions

The important concept is that AWS doesn't have to ask only:

> **"Who are you?"**

It can also evaluate conditions such as:

```text
Who?
 ↓
Identity

Where from?
 ↓
Source IP

Which Region?
 ↓
Requested Region

MFA?
 ↓
MFA condition

When?
 ↓
Current time
```

This gives you more context for an access decision.

---

# 7. CloudTrail

The lower section of the screenshot introduces **AWS CloudTrail**.

The source describes it as:

> **Tracks all API calls**

So CloudTrail provides a record of AWS API activity.

Conceptually:

```text
User / Role / Service
        ↓
AWS API call
        ↓
CloudTrail
        ↓
Event record
```

This is useful for auditing and investigating activity.

---

# 8. Amazon GuardDuty

The screenshot describes **Amazon GuardDuty** as detecting:

> **Suspicious or malicious activity**

It can use CloudTrail and other logs/data sources to identify potentially concerning activity.

Think:

```text
AWS activity
    ↓
CloudTrail + other data
    ↓
GuardDuty
    ↓
Suspicious activity detection
```

### Simple memory

> **GuardDuty = Detect**

---

# 9. Amazon Detective

The screenshot describes **Amazon Detective** as being used to:

* Analyze
* Investigate
* Quickly identify security issues

It can also ingest findings from **GuardDuty**.

Think:

```text
GuardDuty
   ↓
Finds suspicious activity
   ↓
Detective
   ↓
Investigate what happened
```

### Simple memory

> **Detective = Investigate**

---

# 🔥 CloudTrail vs GuardDuty vs Detective

This is worth memorizing:

| Service        | Main purpose                          |
| -------------- | ------------------------------------- |
| **CloudTrail** | Tracks API activity                   |
| **GuardDuty**  | Detects suspicious/malicious activity |
| **Detective**  | Investigates security issues          |

### Easy memory:

> **CloudTrail → Track**

> **GuardDuty → Detect**

> **Detective → Investigate**

# 🧠 Final Summary

### Identity controls

**IAM Policies** → permissions

**Permission Boundaries** → maximum permissions for an identity

**SCPs** → organization/account-level permission guardrails

**IAM Conditions** → restrict access based on context such as:

* IP
* Region
* MFA
* Time

### Security monitoring

**CloudTrail → Track**

**GuardDuty → Detect**

**Detective → Investigate**

### Zero Trust connection

> **Don't simply trust a user because they are inside the network. Verify identity and apply appropriate access conditions before allowing access to AWS resources.**
