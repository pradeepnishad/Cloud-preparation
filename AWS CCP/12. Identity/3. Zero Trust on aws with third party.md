# 🔐 Zero Trust on AWS with Third Parties

This screenshot explains how **third-party identity solutions** can be used alongside AWS to implement more advanced Zero Trust-style identity controls.

The main idea from the source is:

> **AWS provides identity and access controls, while third-party identity platforms can provide additional real-time risk and identity-based controls.**

---

## 1. AWS and Zero Trust

The source states that AWS can technically implement a **Zero Trust model**, but the identity controls shown here don't provide the same level of **intelligent, real-time identity security controls** described in the slide.

AWS provides controls such as:

```text
IAM
 ↓
Policies
 ↓
Conditions
 ↓
MFA
 ↓
Access control
```

But the source highlights that organizations may use third-party identity solutions when they need more advanced identity/risk evaluation.

---

# 2. Third-Party Identity Solutions

The screenshot lists three examples:

### Azure Active Directory (Azure AD)

Now commonly known as **Microsoft Entra ID**.

The source highlights its ability to perform real-time and calculated risk detection using additional signals.

---

### Google BeyondCorp

A Google security approach based around identity and context rather than simply trusting the network location.

The screenshot lists it as another third-party identity solution.

---

### JumpCloud

Another identity platform listed in the source for implementing additional identity-based security controls.

---

# 3. Additional Risk Signals

The source gives examples of information that can be considered when evaluating access:

### Device and Application

```text
Who is accessing?
+
What device/application are they using?
```

### Time of Day

Access can be evaluated based on when the request occurs.

### Location

The user's location can be considered as part of the access decision.

### MFA

Whether MFA is enabled/present can be considered.

### What is Being Accessed

The sensitivity or type of resource being requested can also be considered.

---

# 4. Why Are These Signals Important?

Instead of making an access decision based only on identity:

```text id="s0u6f1"
User = John
     ↓
Allow
```

A more contextual approach can consider:

```text id="y6jq99"
Identity
   +
Device
   +
Application
   +
Location
   +
Time
   +
MFA
   +
Requested resource
   ↓
Risk / access decision
```

This is closer to the **Zero Trust principle of continuously verifying access based on context**.

---

# 5. Scenario

Imagine an employee normally accesses company resources from their managed laptop in India during working hours.

A request suddenly comes from:

```text id="vly5gz"
Unknown device
      +
Unusual location
      +
Unusual time
      +
Sensitive resource
```

An identity/security platform can use these additional signals to determine that the request requires additional verification or should be restricted, depending on the organization's policies.

# 🔥 AWS Native vs Third-Party Approach

Based specifically on your course material:

| AWS IAM controls      | Third-party identity solutions |
| --------------------- | ------------------------------ |
| IAM policies          | Advanced identity controls     |
| Permission boundaries | Real-time/contextual signals   |
| SCPs                  | Risk-based evaluation          |
| IAM conditions        | Device/application signals     |
| IP conditions         | Location signals               |
| MFA conditions        | Time/context signals           |
| Region conditions     | Broader identity/risk analysis |

The important point isn't that AWS IAM is useless—it provides the **core access-control foundation**. The slide is emphasizing that additional platforms can provide more advanced identity/risk signals.
