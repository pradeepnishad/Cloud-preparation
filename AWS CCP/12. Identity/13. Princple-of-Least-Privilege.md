# 🔐 Principle of Least Privilege (PoLP)

## 1. Definition

**Principle of Least Privilege (PoLP)** is a security concept where a **user, role, or application receives only the minimum permissions required to perform a specific operation or task.**

Simple idea:

> **Give only the permissions that are actually needed — nothing extra.**

For example, if an application only needs to **read files from S3**, don't give it permission to delete buckets or modify IAM users.

```text
❌ Too many permissions
User → Read + Write + Delete + IAM Admin + ...

✅ Least privilege
User → Only required permission
```

---

# 2. Why Use Least Privilege?

The main purpose is to **reduce the potential impact of compromised accounts, users, applications, or credentials**.

Suppose an application only needs:

```text
s3:GetObject
```

Giving it:

```text
s3:*
```

provides much broader access than necessary.

With least privilege:

```text
Application
     ↓
Only required permission
     ↓
S3 objects
```

If the application's credentials are compromised, the attacker's available permissions are more limited.

# 3. Just-Enough-Access (JEA)

Your source introduces **Just-Enough-Access (JEA)**.

### Definition

JEA means:

> **Permit only the exact actions required for an identity to perform a task.**

Example:

A developer needs to restart an EC2 instance.

Instead of:

```text
EC2 Administrator
```

give only the required capability, such as permission to perform the necessary EC2 restart action.

```text
Developer
   ↓
JEA
   ↓
Required EC2 action only
```

### Memory

**JEA → What permissions are needed?**

---

# 4. Just-In-Time (JIT)

**Just-In-Time (JIT)** focuses on **how long** the permissions are available.

Your source defines it as:

> Permitting the smallest length of duration an identity can use permissions.

Example:

An administrator needs elevated access for 30 minutes to troubleshoot an issue.

Instead of keeping administrator permissions permanently:

```text
Admin permissions
     ↓
30 minutes
     ↓
Automatically removed
```

### Memory

**JIT → How long are permissions needed?**

---

# 5. JEA vs JIT

This distinction is worth remembering:

| Concept  | Focus               | Question                                 |
| -------- | ------------------- | ---------------------------------------- |
| **JEA**  | Permissions/actions | **What can you do?**                     |
| **JIT**  | Time/duration       | **How long can you do it?**              |
| **PoLP** | Overall principle   | **What is the minimum access required?** |

Think:

```text
PoLP
 │
 ├── JEA → Minimum actions
 │
 └── JIT → Minimum time
```

# 6. Risk-Based Adaptive Policies

Your source also introduces **risk-based adaptive policies**.

The idea is that each access attempt can receive a **risk score** representing how likely the request is to come from a compromised source.

The score can consider factors such as:

* Device
* User location
* IP address
* Service being accessed
* When the access occurs

Conceptually:

```text
Access Request
      ↓
Risk Analysis
      ↓
Risk Score
      ↓
Access decision/policy
```

For example, an access request could be evaluated differently depending on the device, location, IP address, and service being accessed.

### Important source note

Your source specifically states that **at the time of the recording, AWS IAM did not have risk-based adaptive policies built into IAM**.

So for your notes, preserve that as a **source/time-specific statement**, rather than treating it as a timeless AWS fact.
