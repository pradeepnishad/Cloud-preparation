# 1. EC2 Spot Instances

## Definition

**EC2 Spot Instances** allow you to use available EC2 capacity at a discounted price, with the important condition that AWS can interrupt the instance when that capacity is needed.

The screenshot groups Spot Instances with Reserved Instances and Savings Plans as ways to save on compute costs.

### Why use it?

When your workload:

* Can tolerate interruptions
* Doesn't require guaranteed continuous availability
* Can be restarted/replaced
* Is flexible about when it runs

### Scenario

Suppose you're processing 1,000 independent jobs:

```text
Job 1
Job 2
Job 3
...
Job 1000
```

If some instances are interrupted, the jobs can be retried later.

Spot can therefore be useful for this type of flexible workload.

### Avoid Spot for:

```text
Critical production server
Always-on workload
Workload that cannot tolerate interruption
```

### 🧠 Memory

> **Spot = Cheap compute + interruption risk**

# 2. Reserved Instances

## Definition

**Reserved Instances** provide a pricing option for EC2 where you commit to a particular usage arrangement for a longer term in exchange for a discount compared with On-Demand pricing.

The screenshot describes this as saving money by committing to yearly contracts.

### Why use it?

When you have a workload that you expect to run consistently.

Example:

```text
Company application
      ↓
EC2
      ↓
Runs continuously
      ↓
Long-term predictable usage
```

Instead of treating the workload as completely flexible, you can make a longer-term commitment to reduce cost.

### Scenario

A company knows that its application will require EC2 capacity continuously for the next year.

A Reserved Instance pricing option may be appropriate.

### 🧠 Memory

> **Reserved Instance = Predictable usage + commitment = potential savings**

---

# 3. Savings Plans

## Definition

**Savings Plans** provide discounted AWS compute pricing in exchange for committing to a certain amount of compute usage/spend over a term.

Compared with a traditional EC2 Reserved Instance, Savings Plans can provide more flexibility across certain compute usage.

For Cloud Practitioner, remember the main idea:

> **Commit to consistent compute usage → receive discounted pricing.**

### Scenario

Your organization consistently spends money on AWS compute every month.

Instead of paying entirely at standard On-Demand rates, it can make a longer-term commitment through a Savings Plan and receive discounted rates.

### 🧠 Memory

> **Savings Plan = Commit to compute usage → save money**

---

# 4. Spot vs Reserved vs Savings Plans

This is an important comparison.

| Option                | Main idea                                       | Best suited to                                 |
| --------------------- | ----------------------------------------------- | ---------------------------------------------- |
| **On-Demand**         | Pay standard rates without long-term commitment | Flexible/unpredictable workloads               |
| **Spot**              | Discounted spare capacity, can be interrupted   | Interruptible workloads                        |
| **Reserved Instance** | Commitment-based EC2 pricing                    | Predictable EC2 usage                          |
| **Savings Plans**     | Commitment-based compute discount               | Consistent compute usage with more flexibility |

### Easy memory:

```text
Spot
↓
Cheap but can be interrupted

Reserved
↓
Commit to predictable EC2 usage

Savings Plan
↓
Commit to compute usage
```

# 5. AWS Batch

## Definition

**AWS Batch** is a service that **plans, schedules, and executes batch computing workloads** across AWS compute services.

A **batch workload** is generally a job that can run without requiring continuous interactive user involvement.

For example:

```text
Input
 ↓
Job
 ↓
Compute
 ↓
Result
```

You may have thousands of jobs:

```text
Job 1 ──┐
Job 2 ──┤
Job 3 ──┤
Job 4 ──┤──→ AWS Batch → Compute → Results
...     │
Job 1000┘
```

---

## Why use AWS Batch?

Instead of manually deciding:

> "Which compute resource should run each job?"

AWS Batch helps schedule and execute the jobs.

The screenshot also notes that AWS Batch can utilize **Spot Instances** to reduce costs.

### Scenario

A research company needs to process thousands of independent scientific calculations overnight.

AWS Batch can help:

```text
Thousands of jobs
       ↓
AWS Batch
       ↓
Compute resources
       ↓
Jobs executed
       ↓
Results
```

### 🧠 Memory

> **AWS Batch = Schedule and run batch jobs**

# 6. AWS Compute Optimizer

## Definition

**AWS Compute Optimizer** analyzes historical usage information and provides recommendations intended to help **reduce costs and improve performance**.

The screenshot specifically highlights:

> **Reduce costs and improve performance**

It uses machine learning to analyze previous usage history.

### How it works

Conceptually:

```text
AWS Resource
     ↓
Usage history
     ↓
Compute Optimizer
     ↓
Analyze
     ↓
Recommendation
```

For example, suppose an EC2 instance consistently uses very little CPU and memory.

Compute Optimizer might recommend a different instance configuration.

---

## Scenario

You have:

```text
EC2
CPU usage → consistently low
Memory usage → consistently low
```

You may be paying for more capacity than the workload needs.

Compute Optimizer can provide a recommendation to help right-size the resource.

### 🧠 Memory

> **Compute Optimizer = Analyze usage → Recommend better sizing**

# 7. EC2 Auto Scaling Groups — ASG

## Definition

An **EC2 Auto Scaling Group (ASG)** automatically adds or removes EC2 instances according to configured scaling requirements.

This is primarily a **capacity management** concept.

The screenshot describes it as:

> Automatically adding or removing EC2 servers to meet current traffic demand.

---

## Why use ASG?

Traffic doesn't always stay constant.

For example:

```text
Normal traffic
     ↓
3 EC2 instances
```

During a traffic spike:

```text
High traffic
     ↓
6 EC2 instances
```

After traffic decreases:

```text
Low traffic
     ↓
3 EC2 instances
```

The idea is:

> **Run the amount of capacity needed for the workload.**

---

## Scenario

An e-commerce website normally has:

```text
3 EC2 instances
```

During a sale:

```text
Traffic ↑
   ↓
ASG
   ↓
6 EC2 instances
```

After the sale:

```text
Traffic ↓
   ↓
ASG
   ↓
3 EC2 instances
```

This is an example of **elasticity**.

### 🧠 Memory

> **ASG = Automatically add/remove EC2 capacity**

# 8. Elastic Load Balancer — ELB

## Definition

**Elastic Load Balancing (ELB)** distributes incoming traffic across multiple targets such as EC2 instances.

The screenshot also highlights that ELB can redirect traffic away from unhealthy instances toward healthy ones.

Conceptually:

```text
                Users
                  ↓
             Load Balancer
             /     |     \
            ↓      ↓      ↓
          EC2-A  EC2-B  EC2-C
```

---

# 9. Why Use ELB?

Without a load balancer:

```text
Users
  ↓
One EC2
```

That instance could become overloaded or fail.

With ELB:

```text
Users
  ↓
ELB
 ├── EC2-A
 ├── EC2-B
 └── EC2-C
```

Traffic can be distributed across multiple instances.

If one instance becomes unhealthy:

```text
ELB
├── EC2-A ❌
├── EC2-B ✅
└── EC2-C ✅
```

ELB can stop sending traffic to the unhealthy target and route traffic to healthy targets.

---

# 10. ELB and Availability Zones

The screenshot specifically mentions that traffic can be routed to EC2 instances running in different **Availability Zones (AZs)**.

For example:

```text
                    ELB
                  /     \
                 ↓       ↓
              AZ-1     AZ-2
               EC2       EC2
```

This helps build applications that can continue operating if an instance or AZ experiences a problem, depending on the overall architecture.

### 🧠 Memory

> **ELB = Distribute traffic**

# 11. ASG + ELB Together

This is a **very important combination**.

ELB and ASG solve different problems.

### ELB

> **Where should traffic go?**

### ASG

> **How many EC2 instances should we have?**

Together:

```text
                     Users
                       ↓
                      ELB
                   /       \
                  ↓         ↓
                EC2        EC2
                  ↑         ↑
                  └────┬────┘
                       ↑
                      ASG
                       ↓
             Add/remove instances
             according to demand
```

### Example

Traffic increases:

```text
Traffic ↑
   ↓
ASG adds EC2
   ↓
ELB distributes traffic
```

Traffic decreases:

```text
Traffic ↓
   ↓
ASG removes EC2
   ↓
ELB sends traffic to remaining healthy instances
```

### 🧠 Memory

> **ASG = Number of servers**

> **ELB = Distribution of traffic**

# 12. AWS Elastic Beanstalk

## Definition

**AWS Elastic Beanstalk** makes it easier to deploy web applications without requiring developers to manually configure all the underlying AWS services.

The screenshot compares it to **Heroku**.

The idea is:

```text
Your Application
      ↓
Elastic Beanstalk
      ↓
AWS infrastructure
      ↓
Application deployed
```

Instead of manually setting up every component yourself, Beanstalk handles much of the deployment and environment management for you.

---

# 13. Why Use Elastic Beanstalk?

Imagine you're a developer who has a web application.

Without a higher-level deployment service, you might need to configure:

```text
EC2
Security Groups
Load Balancer
Auto Scaling
Application deployment
Monitoring
```

Elastic Beanstalk simplifies the deployment process.

### Scenario

You have a Python web application:

```text
Python Web App
      ↓
Elastic Beanstalk
      ↓
AWS environment
      ↓
Application running
```

You focus primarily on the application while Beanstalk handles much of the underlying deployment configuration.

### Important:

> **Elastic Beanstalk does NOT mean AWS has completely eliminated the underlying infrastructure.**

It is a managed application deployment/orchestration experience built using AWS resources.

### 🧠 Memory

> **Elastic Beanstalk = Easy application deployment**
