# ☁️ AWS Computing Services

The screenshot is introducing the major AWS **compute options** by dividing them into three concepts:

```text
AWS COMPUTE
│
├── Virtual Machines
│      ├── EC2
│      └── Lightsail
│
├── Containers
│      ├── ECS
│      ├── ECR
│      ├── ECS Fargate
│      └── EKS
│
└── Serverless
       └── Lambda
```

The biggest thing to understand is **how much of the underlying server AWS manages for you**.

---

# 1. Virtual Machines

## Definition

A **Virtual Machine (VM)** is an emulation of a physical computer using software.

It behaves like a computer/server with:

```text
CPU
RAM
Storage
Network
Operating System
Applications
```

Conceptually:

```text
Physical Server
       ↓
 Virtualization
       ↓
┌──────┬──────┬──────┐
│ VM 1 │ VM 2 │ VM 3 │
└──────┴──────┴──────┘
```

Each VM can run its own operating system and applications.

---

# 2. Amazon EC2

**Amazon EC2 (Elastic Compute Cloud)** lets you launch virtual machines in AWS.

You can configure things such as:

* CPU
* RAM
* Operating system
* Storage
* Networking
* Security

Example:

```text
AMI
 +
Instance Type
 +
Storage
 +
Networking
      ↓
EC2 Instance
      ↓
Operating System
      ↓
Application
```

### When to use EC2?

Use EC2 when you need significant control over a virtual server.

For example:

> "I need a Windows Server and I want to install and configure my own applications."

EC2 is suitable.

### Key idea

> **EC2 = Virtual server with a high level of customer control.**

---

# 3. Amazon Lightsail

The screenshot describes **Amazon Lightsail** as a **managed virtual server service** and a more "friendly" version of EC2 for users who don't need as much AWS complexity.

Think:

```text
EC2
 ↓
More configuration/control
 ↓
More AWS knowledge

Lightsail
 ↓
Simpler setup
 ↓
Easier for straightforward applications
```

For example, suppose you simply want to launch a:

```text
Linux/Windows server
      ↓
WordPress
      ↓
Website
```

Lightsail provides a simplified experience.

### Why use Lightsail?

When you need a straightforward virtual server but don't want to deal with as many EC2 configuration choices.

### Memory

> **Lightsail = Simple virtual server experience**

---

# 4. Containers

Now we move from **VMs** to **containers**.

A container packages an application and its required components so it can run consistently in a container environment.

The screenshot describes containers as virtualizing an **operating-system environment** to run multiple workloads.

A simplified comparison:

### VM

```text
Physical Server
      ↓
Hypervisor
      ↓
VM
 ├── OS
 └── Application
```

### Container

```text
Physical/Virtual Infrastructure
          ↓
    Container Runtime
          ↓
 ┌────────┬────────┬────────┐
 │Container│Container│Container│
 └────────┴────────┴────────┘
      Applications
```

Containers are commonly used with **microservices**.

---

# 5. What Are Microservices?

Instead of building one huge application:

```text
        Large Application
              │
 ┌────────────┼────────────┐
 ↓            ↓            ↓
Orders      Payments      Users
```

you can separate the application into smaller services:

```text
Orders Service
      ↕
Payment Service
      ↕
User Service
      ↕
Notification Service
```

Each service can potentially be developed, deployed and scaled independently.

---

# 6. Amazon ECS

**Amazon ECS (Elastic Container Service)** is a **container orchestration service**.

The screenshot describes it as supporting Docker containers.

### What does orchestration mean?

Suppose you have many containers:

```text
Container 1
Container 2
Container 3
Container 4
Container 5
```

Someone needs to manage:

* Where containers run
* Starting/stopping containers
* Container placement
* Scaling
* Networking
* Health/recovery behavior

That's where **container orchestration** comes in.

ECS helps manage containers on AWS.

---

# 7. ECS With EC2

One way to run ECS workloads is using EC2 capacity.

Conceptually:

```text
ECS
 ↓
EC2 Cluster
 ├── EC2
 │    ├── Container
 │    └── Container
 │
 └── EC2
      ├── Container
      └── Container
```

Here, you're still responsible for managing the EC2 capacity underneath the ECS workloads.

### When to use?

When you want to run containerized applications and want control over the underlying compute infrastructure.

### Memory:

> **ECS = Orchestrate containers**

---

# 8. Amazon ECR

This is an important distinction:

> **ECS runs containers. ECR stores container images.**

**Amazon ECR (Elastic Container Registry)** is a repository for container images.

Think of a container image as a saved package/template used to create a container.

```text
Dockerfile
    ↓
Build
    ↓
Container Image
    ↓
ECR Repository
    ↓
ECS / Other container service
    ↓
Running Container
```

### Example

You build your application:

```text
Python Application
      ↓
Docker Image
      ↓
Push to ECR
      ↓
ECS pulls image
      ↓
Container runs
```

---

# 9. Image vs Container

Don't confuse these.

### Container Image

A packaged/saved image used to create containers.

```text
Image = Blueprint/package
```

### Container

A running instance of that image.

```text
Image
  ↓
Run
  ↓
Container
```

Easy analogy:

> **Image = recipe/package**

> **Container = running instance**

---

# 10. ECR vs ECS

Very important for exams:

| Service | Purpose                    |
| ------- | -------------------------- |
| **ECR** | Store container images     |
| **ECS** | Orchestrate/run containers |

Memory:

> **ECR = Container Registry**

> **ECS = Container Service**

---

# 11. ECS Fargate

Now we get to **ECS Fargate**.

Fargate is a **serverless compute engine for containers**.

The screenshot describes it as a serverless container orchestration option.

The key difference is:

### ECS with EC2

```text
ECS
 ↓
EC2
 ↓
Containers
```

You need to manage the EC2 capacity.

### ECS with Fargate

```text
ECS
 ↓
Fargate
 ↓
Containers
```

AWS manages the underlying server infrastructure for the containers.

You don't need to provision and manage EC2 instances for the Fargate tasks.

---

# 12. Why Use Fargate?

Suppose you only care about your container:

```text
My Application
     ↓
Docker Container
     ↓
Run it
```

You don't want to worry about:

```text
Which EC2 server?
How many EC2 servers?
Server patching?
Underlying server capacity?
```

Fargate abstracts that infrastructure away.

### Memory:

> **Fargate = Run containers without managing the underlying servers.**

---

# 13. ECS vs ECS Fargate

| ECS on EC2                     | ECS + Fargate                                    |
| ------------------------------ | ------------------------------------------------ |
| Containers run on EC2 capacity | Containers run on Fargate                        |
| Customer manages EC2 capacity  | AWS manages underlying compute infrastructure    |
| More control                   | Less infrastructure management                   |
| You manage EC2 instances       | No EC2 instances to manage for the Fargate tasks |

The key exam concept:

> **Fargate is serverless compute for containers.**

---

# 14. Amazon EKS

**Amazon EKS (Elastic Kubernetes Service)** is a **managed Kubernetes service**.

### What is Kubernetes?

**Kubernetes (K8s)** is open-source software used for container orchestration.

It helps manage large numbers of containers.

```text
Kubernetes
│
├── Containers
├── Scheduling
├── Scaling
├── Networking
├── Service discovery
└── Health/recovery
```

EKS provides Kubernetes capabilities as an AWS managed service.

---

# 15. ECS vs EKS

This is a common exam distinction.

### ECS

AWS's own container orchestration service.

```text
AWS
 ↓
ECS
 ↓
Containers
```

### EKS

AWS's managed Kubernetes service.

```text
AWS
 ↓
EKS
 ↓
Kubernetes
 ↓
Containers
```

### Memory:

> **ECS = AWS container orchestration**

> **EKS = Managed Kubernetes**

---

# 16. Serverless

The screenshot then introduces **Serverless**.

### Definition

In this context:

> **Serverless means AWS manages the underlying servers/infrastructure for you, so you don't directly provision or manage those servers.**

It does **not** mean that servers don't exist.

There are still servers underneath.

```text
Your Application
       ↓
Serverless Service
       ↓
AWS infrastructure
       ↓
Physical Servers
```

AWS simply abstracts the underlying servers away from you.

---

# 17. AWS Lambda

**AWS Lambda is a serverless compute service that lets you run code without provisioning or managing servers.**

Instead of launching:

```text
EC2
 ↓
OS
 ↓
Application
```

you provide your function:

```text
Function Code
      ↓
AWS Lambda
      ↓
AWS runs it
```

For example:

```python
def lambda_handler(event, context):
    return "Hello World"
```

You upload the function, configure it, and AWS handles the underlying compute environment.

---

# 18. How Lambda Works

The basic idea:

```text
Event
  ↓
Lambda Function
  ↓
Execute Code
  ↓
Response
```

An event could come from another AWS service or an application.

For example:

```text
S3
 ↓
New file uploaded
 ↓
Lambda
 ↓
Process file
```

You don't need to create an EC2 server just to run that small piece of code.

---

# 19. Lambda Pricing Concept

The screenshot emphasizes that Lambda is charged based on the **runtime of the function**, with billing measured in small time increments according to the applicable Lambda pricing model.

The key Cloud Practitioner concept is:

> **Lambda is usage-based/serverless compute rather than paying for an always-running server instance.**

For example:

```text
Function runs
     ↓
You are charged according to usage
```

This is different from keeping an EC2 instance running continuously.

---

# 20. EC2 vs Lambda

This is one of the most important comparisons.

| EC2                              | Lambda                                  |
| -------------------------------- | --------------------------------------- |
| Virtual server                   | Serverless functions                    |
| You manage guest OS              | AWS manages underlying infrastructure   |
| Long-running workloads possible  | Event/function-oriented execution       |
| More control                     | Less infrastructure management          |
| Pay for allocated instance usage | Usage-based function execution          |
| You provision instance capacity  | AWS manages underlying compute capacity |

### Memory:

> **EC2 = Manage a virtual server**

> **Lambda = Run code without managing servers**

# 21. The Big Picture

Now combine everything from the screenshot:

```text
                 AWS COMPUTE
                     │
       ┌─────────────┼──────────────┐
       ↓             ↓              ↓
 Virtual Machines  Containers    Serverless
       │             │              │
   ┌───┴───┐      ┌──┴─────┐       │
   ↓       ↓      ↓        ↓       ↓
  EC2   Lightsail ECS      EKS   Lambda
                  │
                  ↓
               Fargate
                  │
                  ↓
                ECR
```

But remember **ECR is a registry for images**, rather than a compute runtime.

# 🎯 How to Choose

Think about what you need.

### "I need a virtual server."

→ **EC2**

### "I need a simpler managed virtual server."

→ **Lightsail**

### "I need to run/manage Docker containers."

→ **ECS**

### "I need to store Docker/container images."

→ **ECR**

### "I want to run containers without managing servers."

→ **Fargate**

### "I need managed Kubernetes."

→ **EKS**

### "I just want to run code without managing servers."

→ **Lambda**

```text
Docker Image
     ↓
    ECR
     ↓
    ECS
     ↓
 ┌───┴────┐
 ↓        ↓
EC2    Fargate
```

And separately:

```text
Code
 ↓
Lambda
 ↓
AWS-managed compute
```

### Final memory trick

**EC2 → VM**

**Lightsail → Simple VM**

**ECS → Containers**

**ECR → Container Images**

**Fargate → Serverless Containers**

**EKS → Kubernetes**

**Lambda → Serverless Functions**

> **The overall progression is: EC2 gives you the most direct server control, while services such as Fargate and Lambda abstract more of the underlying infrastructure away from you.**
