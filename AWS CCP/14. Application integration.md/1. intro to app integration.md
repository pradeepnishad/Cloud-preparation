# 🔗 Application Integration

## 1. Definition

**Application Integration** is the process of allowing **two independent applications to communicate and work with each other**, commonly with the help of an **intermediate system**.

Simple idea:

```text
Application A
      ↓
Intermediate System
      ↓
Application B
```

Instead of applications being tightly dependent on each other, they can communicate through integration mechanisms.

---

## 2. Why Use Application Integration?

Cloud workloads often encourage systems and services to be **loosely coupled**.

### Loosely coupled means:

One application doesn't need to be directly dependent on another application to perform its work.

For example:

```text
Order Application
      ↓
Integration System
      ↓
Payment Application
```

If the payment application is temporarily unavailable, the integration system can help decouple the two applications rather than requiring them to communicate directly at every moment.

# 3. Common Application Integration Patterns

Your source lists six common systems/design patterns:

1. **Queueing**
2. **Streaming**
3. **Pub/Sub**
4. **API Gateways**
5. **State Machine**
6. **Event Bus**

These are the important categories to recognize.

---

## 4. Queueing

**Queueing** allows applications to communicate through a queue.

```text
Application A
     ↓
   Queue
     ↓
Application B
```

Application A sends work/messages to the queue, and Application B processes them.

The important concept:

> **Queueing → messages/work waiting to be processed**

---

## 5. Streaming

**Streaming** is used when applications need to process a continuous flow of data/events.

```text
Data Sources
    ↓
 Continuous Stream
    ↓
Application
```

Think of continuously generated data rather than individual isolated requests.

---

## 6. Pub/Sub

**Pub/Sub = Publish/Subscribe.**

One application publishes a message/event, and multiple interested applications can subscribe to it.

```text
             Publisher
                 ↓
              Message
                 ↓
             Pub/Sub
          ↙      ↓      ↘
       App A    App B    App C
```

The publisher doesn't need to communicate individually with every subscriber.

---

## 7. API Gateway

An **API Gateway** provides an entry point through which applications/clients can communicate with backend services through APIs.

Conceptually:

```text
Client
  ↓
API Gateway
  ↓
Backend Services
```

This is useful when applications communicate through APIs.

---

## 8. State Machine

A **state machine** represents a workflow as a series of states and transitions.

For example:

```text
Order Created
     ↓
Payment
     ↓
Processing
     ↓
Shipping
     ↓
Completed
```

Each state represents a stage of the workflow.

---

## 9. Event Bus

An **event bus** allows applications/services to communicate by sending and receiving **events**.

```text
Application A
      ↓
    Event
      ↓
  Event Bus
   ↙     ↘
 App B   App C
```

For example, an application could publish:

```text
"OrderPlaced"
```

Other applications interested in that event can respond.
