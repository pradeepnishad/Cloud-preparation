# 🚪 Amazon API Gateway

## 1. What is an API Gateway?

An **API Gateway** is a service/program that sits between a **single entry point** and **multiple backend services**.

```text
Clients
  ↓
API Gateway
  ↓
Multiple Backends
```

It acts as the **front door** for applications to access backend data, business logic, or functionality.

---

## 2. Amazon API Gateway

**Amazon API Gateway** is an AWS service for **creating secure APIs at any scale**.

It allows applications such as:

* Mobile apps
* Web applications
* IoT devices

to communicate with backend AWS services.

From your diagram:

```text
Mobile App ──┐
Web App    ──┼── HTTP/S ──→ API Gateway ──→ Lambda
IoT Device ──┘                       ├──────→ DynamoDB
                                    ├──────→ Kinesis
                                    ├──────→ EC2
                                    └──────→ AWS services
```

So instead of exposing every backend service directly to clients, the clients communicate through the **API Gateway**.

# 3. Why use API Gateway?

The screenshot highlights several important capabilities.

### 🔹 Throttling

Controls how many requests can be sent to your API over a period of time.

Example:

```text
Client → 10,000 requests/sec
             ↓
        API Gateway
             ↓
       Limit traffic
```

This can help prevent backend services from being overwhelmed.

---

### 🔹 Logging

API Gateway can work with monitoring/logging services such as **CloudWatch** to provide visibility into API activity.

You can monitor things such as requests and errors.

---

### 🔹 Routing

API Gateway can determine where requests should go.

For example:

```text
GET /tasks
      ↓
API Gateway
      ↓
Task backend

POST /tasks
      ↓
API Gateway
      ↓
Task creation backend
```

Your screenshot shows routes such as:

```text
GET    /tasks
GET    /tasks/{id}
POST   /tasks/{id}
DELETE /tasks/{id}
```

---

### 🔹 Request and Response Formatting

API Gateway can handle the processing/formatting of requests and responses between clients and backend services.

This allows the client-facing API interface to be separated from the internal backend implementation.

---

# 4. API Gateway Cache

Your diagram also shows **API Gateway Cache**.

Caching can store responses so that repeated requests can potentially be served from the cache rather than repeatedly calling the backend.

```text
Client
  ↓
API Gateway
  ↓
Cache → Response
  │
  └── Backend if needed
```

This can reduce backend requests and improve response performance for appropriate workloads.

---

# 5. Scenario Example

Imagine you're building a **task management application**.

Your mobile application needs to perform:

```text
GET /tasks
GET /tasks/123
POST /tasks
DELETE /tasks/123
```

Instead of the mobile application directly communicating with multiple backend services:

```text
Mobile App → Lambda
Mobile App → DynamoDB
Mobile App → EC2
```

you can use:

```text
              ┌→ Lambda
              │
Mobile App → API Gateway → DynamoDB
              │
              └→ Other AWS services
```

The mobile application has **one API entry point**, while API Gateway handles communication with the backend.

# 6. API Gateway vs Load Balancer

Don't confuse these two.

| API Gateway                                  | Load Balancer                           |
| -------------------------------------------- | --------------------------------------- |
| API front door                               | Distributes network/application traffic |
| Designed around APIs                         | Designed around traffic distribution    |
| Request routing                              | Routes traffic to healthy targets       |
| API management features                      | Load balancing/health checks            |
| Throttling, API-related controls             | Traffic distribution                    |
| Can integrate with Lambda and other services | Commonly routes to EC2/ECS/etc.         |

### 🧠 Easy memory

**API Gateway → API front door**

**Load Balancer → Traffic distributor**
