## 📄 What is a Document Database?

### 1. Definition

A **document database** is a type of **NoSQL database** that stores data as **documents**, rather than rows and columns like a relational database.

A document usually stores data in a JSON-like format:

```json
{
  "user_id": "U101",
  "name": "Pradeep",
  "age": 24,
  "city": "Mumbai",
  "skills": ["AWS", "Linux", "Python"]
}
```

Here, the entire JSON-like structure is one **document**.

---

### 2. How is it different from a relational database?

A relational database might store the same information like this:

| user_id | name    | age | city   |
| ------- | ------- | --: | ------ |
| U101    | Pradeep |  24 | Mumbai |

A document database stores it more like:

```json
{
  "user_id": "U101",
  "name": "Pradeep",
  "age": 24,
  "city": "Mumbai"
}
```

The document can also contain **nested data**:

```json
{
  "user_id": "U101",
  "name": "Pradeep",
  "address": {
    "city": "Mumbai",
    "country": "India"
  },
  "skills": [
    "AWS",
    "Linux",
    "Python"
  ]
}
```

This is one of the major advantages of document databases: **related information can be stored together inside a document.**

---

### 3. Why use a document database?

Use it when your application works naturally with **JSON-like, flexible, changing data**.

For example, an e-commerce application could have:

```json
{
  "order_id": "ORD1001",
  "customer": "U101",
  "items": [
    {
      "product": "Laptop",
      "quantity": 1
    },
    {
      "product": "Mouse",
      "quantity": 2
    }
  ],
  "status": "shipped"
}
```

You don't necessarily need separate tables for customer, order, and items for this particular representation.

---

### 4. Document Database vs Key-Value Store

This is important for your AWS exam.

**Key-value:**

```text
Key       → Value

user101   → Pradeep
user102   → Rahul
```

The primary idea is:

> **Give me this key → give me its value.**

**Document database:**

```text
user101 → {
             "name": "Pradeep",
             "age": 24,
             "city": "Mumbai"
          }
```

The document can contain **structured/nested fields**, and document databases generally support querying based on fields inside the document.

So:

> **Key-value = Key → Value**
> **Document = Key/ID → Structured document**

---

### 5. AWS Example

**Amazon DynamoDB** supports both **key-value** and **document** data models.

For example, a DynamoDB item could look like:

```json
{
  "UserID": "U101",
  "Name": "Pradeep",
  "Age": 24,
  "Skills": ["AWS", "Python", "Linux"]
}
```

So DynamoDB isn't only a simple key-value store; it can also store **document-style data**.

---

### 6. When would you use a document database?

Common examples:

* User profiles
* Product catalogs
* Shopping carts
* Content management
* Mobile/web applications
* Applications where fields can vary between records
* JSON-based application data

For example, products can have different attributes:

```json
{
  "product": "Laptop",
  "ram": "16GB",
  "storage": "1TB"
}
```

while another product might have:

```json
{
  "product": "Phone",
  "camera": "50MP",
  "battery": "5000mAh"
}
```

The structure can be more flexible than a traditional fixed table.

---

## Quick comparison

| Type           | Data model              | Example AWS service |
| -------------- | ----------------------- | ------------------- |
| Relational     | Tables → Rows → Columns | RDS                 |
| Key-value      | Key → Value             | DynamoDB            |
| Document       | JSON-like documents     | DynamoDB            |
| Object         | Objects in buckets      | S3                  |
| Data warehouse | Analytical datasets     | Redshift            |

### 🧠 Memory trick

**Relational → Tables**
**Key-value → Key → Value**
**Document → JSON-like document**
**Object → Object in storage**

For your AWS Cloud Practitioner exam, the key thing to remember is:

> **Document database = NoSQL database that stores structured data as flexible, JSON-like documents. Amazon DynamoDB supports the document data model.**
