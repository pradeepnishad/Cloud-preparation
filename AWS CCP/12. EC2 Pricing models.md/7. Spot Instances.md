# 💸 EC2 Spot Instances

## 1. Definition

**Spot Instances let you use AWS's unused EC2 compute capacity at a heavily discounted price.**

AWS has spare/idle compute capacity that it wants to utilize. Spot Instances allow customers to use that capacity at a much lower price than On-Demand.

Your source states:

> **Spot Instances provide a discount of up to 90% compared to On-Demand pricing.**

Think of it like:

> ✈️ An airline discounting empty seats rather than letting them remain unused.

---

# 2. Why Use Spot Instances?

The biggest reason is **very low compute cost**.

They are designed for workloads that can tolerate interruption and have:

* Flexible start times
* Flexible end times
* Workloads that can restart/retry
* Very low-cost compute requirements

```text
On-Demand
   ↓
Higher cost
   ↓
More predictable availability

Spot
   ↓
Much lower cost
   ↓
Can be interrupted
```

---

# 3. The Major Disadvantage — Interruption

This is the **most important thing to remember**.

AWS can terminate your Spot Instance when the underlying capacity is needed by other On-Demand customers.

For example:

```text
Spot Instance running
        ↓
AWS needs the capacity
        ↓
Spot Instance can be terminated
```

Therefore:

> **Spot Instances are NOT suitable for workloads that cannot tolerate interruption.**

---

# 4. When Should You Use Spot Instances?

Your source gives examples of workloads with flexible start/end times.

### Batch workloads

A job can start whenever capacity is available and finish when processing is complete.

```text
Data
 ↓
Batch processing
 ↓
Results
```

If the instance is interrupted, the workload can potentially restart.

---

### CI/CD Jobs

Build and testing workloads can be good candidates when they can tolerate interruptions.

```text
Code
 ↓
Build
 ↓
Test
 ↓
Deploy
```

---

### Big Data

The source specifically mentions:

> **MapReduce jobs**

These workloads can use distributed processing and can be designed to tolerate individual compute interruptions.

---

### Load Balancing Workloads

The screenshot also shows load-balancing workloads as an example.

The important idea is that multiple instances can participate in a workload, so losing one instance may be manageable depending on the architecture.

# 5. AWS Batch

Your source highlights:

> **AWS Batch is an easy and convenient way to use Spot Pricing.**

AWS Batch is designed for running **batch computing jobs** and can make it easier to use Spot capacity for suitable workloads.

Think:

```text
Batch Jobs
     ↓
AWS Batch
     ↓
Spot Instances
     ↓
Lower compute cost
```

---

# 6. Termination Conditions

The source states that Spot Instances:

> **Can be terminated by AWS at any time**

This is the key difference from normal On-Demand thinking.

### If AWS terminates the Spot Instance

According to your source:

> You don't get charged for a partial hour of usage.

### If you terminate the Spot Instance yourself

The source says:

> You will still be charged for any hour that it ran.

For your exam, remember the distinction:

```text
AWS terminates
→ Source says no charge for partial hour

You terminate
→ Source says you are charged for the hour it ran
```

# 🔥 Spot vs On-Demand vs Reserved

|                | On-Demand                     | Reserved Instance            | Spot                                     |
| -------------- | ----------------------------- | ---------------------------- | ---------------------------------------- |
| Main idea      | Pay as you use                | Commit for discount          | Use unused capacity                      |
| Commitment     | None                          | 1/3 year                     | None like RI                             |
| Cost           | Standard                      | Discounted                   | Up to 90% discount in source             |
| Predictability | Higher                        | Higher                       | Lower                                    |
| Interruption   | Normal EC2 behavior           | Normal EC2 behavior          | **Can be interrupted**                   |
| Best for       | Short/unpredictable workloads | Steady predictable workloads | Flexible/interruption-tolerant workloads |

---

# 🎯 Exam Scenarios

### Scenario 1

You need the **lowest possible EC2 compute cost** and your workload can tolerate interruptions.

→ **Spot Instances**

### Scenario 2

You are running a batch processing job that can restart if interrupted.

→ **Spot Instances**

### Scenario 3

You need a server that must remain available continuously and cannot tolerate interruption.

→ **Don't choose Spot as the basis for that requirement.**

### Scenario 4

You have predictable EC2 usage for several years.

→ **Reserved Instance**

### Scenario 5

You need a server temporarily with no long-term commitment.

→ **On-Demand**
