
# 🕵️ Amazon GuardDuty

### What is GuardDuty?

According to the slide, **Amazon GuardDuty is a threat detection service** that continuously monitors AWS environments for:

- Malicious activity
- Suspicious activity
- Unauthorized behavior

It uses **Machine Learning** to analyze AWS logs and identify potential security threats.

Think of GuardDuty as a **security monitoring/detection system**:

```text
AWS Environment
      │
      ├── CloudTrail Logs
      ├── VPC Flow Logs
      └── DNS Logs
              │
              ▼
        Amazon GuardDuty
              │
              ▼
       Analyze Activity
              │
              ▼
          Findings 🚨
```

---

# 🔍 What is IDS/IPS?

The slide first introduces **IDS/IPS**.

### IDS — Intrusion Detection System

An IDS:

> **Detects** suspicious or malicious activity.

It monitors systems or networks and generates alerts when something suspicious is detected.

Think:

**IDS = Detect & Alert**

---

### IPS — Intrusion Prevention System

An IPS goes a step further by attempting to **prevent/block** malicious activity.

Think:

**IPS = Detect + Prevent**

---

# 🛡️ Where does GuardDuty fit?

The important thing from your slide is:

> **GuardDuty = Threat Detection Service**

So don't think of GuardDuty primarily as a firewall or traffic-blocking service.

Its main job is to **detect threats and generate findings**.

```text
Suspicious Activity
       ↓
GuardDuty detects it
       ↓
Finding 🚨
       ↓
You investigate/respond
```

---

# 📊 What logs does GuardDuty analyze?

Your slide specifically lists **three important sources**:

### 1. CloudTrail Logs

CloudTrail records **API activity** in your AWS environment.

For example:

```text
Someone → calls an AWS API
              ↓
         CloudTrail
              ↓
         Activity recorded
```

GuardDuty can analyze this activity to identify suspicious behavior.

---

### 2. VPC Flow Logs

VPC Flow Logs provide information about **network traffic flows** within your VPC.

Conceptually:

```text
Instance A ───────► Instance B
      │
      └── Network information
              ↓
        VPC Flow Logs
              ↓
          GuardDuty
```

---

### 3. DNS Logs

DNS logs contain information about DNS queries.

GuardDuty can analyze these queries for suspicious patterns.

So remember:

> **GuardDuty → CloudTrail + VPC Flow Logs + DNS Logs**

That's a very useful **Cloud Practitioner exam association** from your material.

---

# 🚨 What is a GuardDuty Finding?

This is another important word on your slide.

A **finding** is an alert/report generated when GuardDuty identifies potentially suspicious or malicious activity.

The screenshot on the right shows an example:

```text
Policy:IAMUser/RootCredentialUsage

Severity: LOW
Region: us-east-1
Count: 36
```

The finding indicates that an API was invoked using **root credentials** from an IP address.

So GuardDuty is essentially saying:

> 🚨 "Something potentially suspicious happened. Investigate this."

---

# 🤖 Machine Learning

Your slide specifically says GuardDuty uses **Machine Learning** to analyze the logs.

The basic idea:

```text
Large amount of AWS activity
             ↓
       GuardDuty ML
             ↓
   Detect suspicious patterns
             ↓
         Findings
```

You don't have to manually inspect every single log entry.

GuardDuty continuously analyzes the activity and identifies potential threats.

---

# ⚡ GuardDuty + automated response

The bottom of the slide mentions that findings can be used to **automate incident response** via **CloudWatch Events** or third-party services.

The basic architecture is:

```text
              AWS Activity
                   │
                   ▼
              GuardDuty
                   │
                   ▼
                Finding
                   │
                   ▼
        CloudWatch Events
                   │
          ┌────────┴────────┐
          ▼                 ▼
    Automated Action    3rd Party
                         Service
```

So GuardDuty doesn't necessarily mean:

> "GuardDuty automatically fixes everything."

Instead, it **detects and produces findings**, which can then be used to trigger response workflows.

# 🆚 GuardDuty vs AWS Shield

This is a **very important distinction** because you're currently learning both.

| Service | Main purpose |
|---|---|
| 🛡️ **AWS Shield** | Protect against **DDoS attacks** |
| 🕵️ **Amazon GuardDuty** | **Detect threats and suspicious activity** |

### Example

Someone launches a huge DDoS attack against your website:

**Shield → DDoS protection**

Someone compromises credentials and starts performing suspicious AWS API activity:

**GuardDuty → detects suspicious behavior**

---

# 🆚 GuardDuty vs Inspector

You just learned **Amazon Inspector** too, so keep these separate:

| Service | Think |
|---|---|
| **GuardDuty** | 🕵️ **Threat detection** |
| **Inspector** | 🔍 **Vulnerability assessment** |
| **Shield** | 🛡️ **DDoS protection** |
| **WAF** | 🚧 **Web application traffic filtering** |

### Easy example

Imagine you have an EC2 server.

**Inspector:**

> "This server has these security vulnerabilities."

**GuardDuty:**

> "Something suspicious appears to be happening in your AWS environment."

**Shield:**

> "Your application is being targeted by a DDoS attack."

**WAF:**

> "This web request matches a malicious/undesired rule, so filter it."
