# 🔐 AWS CloudHSM

This slide is the **dedicated HSM / high-control alternative to AWS KMS**. Let's break down exactly what your slide is teaching.

---

## 1. What is CloudHSM?

**AWS CloudHSM** is a **single-tenant HSM as a service**.

That means AWS provides the HSM infrastructure, but the HSM is **dedicated to you** rather than shared with multiple customers.

The slide says AWS automates:

- Hardware provisioning
- Software patching
- High availability
- Backups

### Simple idea

> **CloudHSM = Dedicated hardware security module managed by AWS infrastructure.**

```text
Your AWS Account
       │
       ↓
 ┌───────────────┐
 │ AWS CloudHSM  │
 │               │
 │ 🔐 Your Keys  │
 └───────────────┘
       │
       ↓
 Your Applications
```

# 2. FIPS 140-2 Level 3

This is an important exam point from your slide.

CloudHSM lets you generate and use encryption keys on:

> **FIPS 140-2 Level 3 validated hardware**

So remember:

**CloudHSM → Single-tenant → FIPS 140-2 Level 3**

Compared with the previous KMS slide:

**KMS → Multi-tenant HSM**

---

# 3. Why would you use CloudHSM?

CloudHSM is useful when you need **greater control over your cryptographic keys and HSM environment**.

For example, your organization may have requirements that specifically call for dedicated HSM hardware.

The important distinction is:

```text
AWS KMS
   ↓
Managed key management
   ↓
Simpler AWS integration

AWS CloudHSM
   ↓
Dedicated HSM
   ↓
More direct HSM control
```

---

# 4. Open HSM industry standards

The slide says CloudHSM is built on **Open HSM industry standards** and can integrate with:

### PKCS#11

A standard interface used by applications to communicate with cryptographic hardware.

### Java Cryptography Extensions (JCE)

Java cryptography framework/extensions that applications can use to perform cryptographic operations.

### Microsoft CryptoNG (CNG)

Microsoft's cryptography API/framework for Windows applications.

For the Practitioner exam, the important idea is:

> **CloudHSM supports standard cryptographic interfaces, making it easier to integrate with applications.**

---

# 5. Key migration

An interesting point on the slide:

> You can transfer your keys to other commercial HSM solutions.

This means CloudHSM can make it easier to **migrate cryptographic keys on or off AWS**, subject to the supported mechanisms and requirements.

Think:

```text
Commercial HSM
      ↕
  AWS CloudHSM
      ↕
Commercial HSM
```

This can be useful if an organization needs to move its cryptographic infrastructure between environments.

---

# 6. KMS + CloudHSM together

This is probably the **most important advanced concept on this slide**.

The slide says:

> **Configure AWS KMS to use an AWS CloudHSM cluster as a custom key store rather than the default KMS key store.**

So CloudHSM doesn't necessarily replace KMS.

You can have:

```text
             AWS KMS
                │
                ↓
       Custom Key Store
                │
                ↓
        CloudHSM Cluster
                │
                ↓
        🔐 Cryptographic Keys
```

### Why?

You can use the **KMS management experience/API** while having the underlying key material protected by your **CloudHSM cluster**.

# 🆚 KMS vs CloudHSM

| | **AWS KMS** | **AWS CloudHSM** |
|---|---|---|
| Type | Managed key management | HSM as a service |
| Tenancy in your slide | **Multi-tenant** | **Single-tenant** |
| Hardware | AWS-managed HSM infrastructure | Dedicated HSM |
| FIPS level in slide | Level 2 | **Level 3** |
| Control | Easier/managed | More direct control |
| AWS integration | Very broad | Application/HSM integration |
| Key store | Default KMS key store | Can be used as **KMS custom key store** |
