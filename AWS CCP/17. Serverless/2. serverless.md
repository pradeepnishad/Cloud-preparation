# What is Serverless?

## Definition

**Serverless architecture** generally describes **fully managed cloud services** where the cloud provider abstracts away much of the underlying infrastructure.

The important point from your source is that **“serverless” is not simply Yes/No**. A cloud service can have **different degrees of serverlessness**.

Think of it as a **scale**:

> More infrastructure managed by AWS → More serverless  
> Less infrastructure managed by AWS → Less serverless

---

## Characteristics of Serverless

A serverless service could have most or all of these characteristics:

### 1. Highly elastic and scalable
Resources can adjust according to workload and demand.

Example:

```text
Low demand → few resources
High demand → more resources
Demand decreases → resources scale down
```

This is particularly useful for workloads that don't have consistent traffic.

---

### 2. Highly available

The service is designed to remain available without you having to manually build and manage all the underlying infrastructure.

---

### 3. Highly durable

For services where durability applies, the cloud provider handles much of the underlying infrastructure required to protect and maintain the stored data/service.

---

### 4. Secure by default

The service provides built-in security capabilities, although **you still have security responsibilities** depending on the service and configuration.

For example, you still need to properly configure:
- IAM permissions
- Access controls
- Data permissions
- Application security

---

# 5. Abstracts the underlying infrastructure

This is one of the most important ideas.

With a traditional server:

```text
You
 ↓
OS
 ↓
VM/Server
 ↓
Hardware
```

You may need to manage many of these layers.

With a highly serverless service:

```text
You
 ↓
AWS Service
 ↓
AWS-managed infrastructure
```

AWS handles much of the underlying infrastructure, allowing you to focus on the **business task/application**.

---

# 6. Pay-for-Value

Your source describes serverless as:

> **Pay-for-Value**

The idea is that you generally pay based on the **execution or usage of the service**, rather than paying for idle servers.

For example, instead of keeping a server running 24/7:

```text
Traditional server

Running → $$
Idle     → $$
Idle     → $$
Idle     → $$
```

A serverless workload can be closer to:

```text
No execution → little/no usage cost
      ↓
Execution
      ↓
Pay for usage/execution
```

The exact pricing model depends on the AWS service.

---

# 7. Scale-to-Zero

This is an important serverless concept.

**Scale-to-zero** means that when the serverless resource isn't being used, it can potentially scale down to **zero active capacity**, so there is no charge for idle server capacity in the way there would be for a continuously running server.

However, **not every serverless AWS service necessarily scales to zero**, so treat this as a characteristic rather than a universal rule.

---

# Serverless vs Traditional Infrastructure

| Traditional infrastructure | Serverless |
|---|---|
| You manage more infrastructure | AWS manages more infrastructure |
| Servers may run continuously | Resources can be usage-driven |
| Pay for provisioned capacity | Often pay based on usage/execution |
| Scaling may require configuration | Often highly elastic |
| More infrastructure management | Less infrastructure management |
| You manage more operational tasks | AWS handles more underlying tasks |

---

# Example

Suppose you have an image-processing application.

### Traditional approach

```text
User
 ↓
EC2
 ↓
Operating System
 ↓
Application
 ↓
Image Processing
```

You need to manage the EC2 environment.

### Serverless approach

```text
User
 ↓
S3
 ↓
Lambda
 ↓
Process Image
```

When an image is uploaded, Lambda can execute the processing code.

You focus on the **image-processing logic**, while AWS manages the underlying compute infrastructure.

---

# Why Use Serverless?

Serverless is useful when you want to:

- Reduce infrastructure management
- Automatically handle changing workloads
- Build event-driven applications
- Pay according to usage
- Focus more on application/business logic
- Avoid managing idle servers
- Build highly scalable applications

---

# Important Exam Concept

Don't memorize:

> **Serverless = No servers**

That's incorrect.

Instead remember:

> **Serverless = Servers still exist, but the cloud provider manages the underlying infrastructure for you.**

And from your source:

> **Serverless is a degree/scale, not simply a Yes/No classification.**

### Memory Trick

**Serverless = Managed infrastructure + Elasticity + Usage-based value + Less server management**

---

## Summary

**Serverless architecture** generally refers to highly managed cloud services where the underlying infrastructure is abstracted away from you.

Key characteristics:

**Elastic → Available → Durable → Secure → Abstracted Infrastructure → Pay-for-Value → Potential Scale-to-Zero**

The biggest idea to remember for the AWS exam:

> **You focus on the business task; AWS manages more of the underlying infrastructure.**
