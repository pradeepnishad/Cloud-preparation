# AWS Serverless Services

## 1. What is Serverless?

### Definition
**Serverless** is a cloud computing model where the **cloud provider manages the underlying servers, infrastructure, and operating system** for you.

You focus mainly on your **application, code, or data**, while AWS handles the underlying infrastructure.

> **Serverless does NOT mean there are no servers.**  
> Servers still exist, but **you don't have to provision, manage, patch, or maintain them directly.**

### Key characteristics
- AWS manages the underlying infrastructure.
- You generally pay based on usage.
- Services can automatically scale.
- You don't need to manage servers directly.
- Reduces infrastructure administration.

### Simple example

Instead of:

**You → EC2 → Install OS → Patch OS → Configure server → Deploy application**

With serverless:

**You → AWS Serverless Service → Application**

AWS handles much of the underlying infrastructure.

# 2. Amazon DynamoDB

### Definition
**Amazon DynamoDB** is a serverless **NoSQL database** supporting **key-value and document data models**.

The source highlights that it is designed to scale to **billions of records** without requiring you to manage database servers or shards.

### Why use it?
Use DynamoDB when you need:
- NoSQL database
- High scalability
- Key-value or document data
- Low operational overhead
- Applications that need fast access to data

### Scenario
An e-commerce application stores:

```text
UserID → User information
1001   → {Name: "John", Cart: 5 items}
1002   → {Name: "Alex", Cart: 2 items}
```

Instead of managing database servers yourself, DynamoDB handles the underlying infrastructure.

### Exam point
**Serverless + NoSQL + key-value/document → DynamoDB**

# 3. Amazon S3

### Definition
**Amazon S3 (Simple Storage Service)** is a **serverless object storage service**.

You store objects/files in S3 buckets without managing disks, filesystems, or storage servers.

### Why use it?
Use S3 for:
- Images
- Videos
- Documents
- Backups
- Logs
- Static website files
- Large amounts of unstructured data

### Scenario

A website allows users to upload profile pictures:

```text
User
 ↓
Application
 ↓
S3 Bucket
 ↓
Profile Image
```

You don't need to create or maintain a storage server.

### Exam point

**Serverless + object storage → S3**

---

# 4. Amazon ECS Fargate

### Definition
**AWS Fargate** is a **serverless compute engine for containers**.

It allows you to run containers without directly managing the underlying EC2 servers.

### ECS vs Fargate

**ECS with EC2:**

```text
ECS
 ↓
EC2 instances
 ↓
Containers
```

You have to manage the EC2 infrastructure.

**ECS with Fargate:**

```text
ECS
 ↓
Fargate
 ↓
Containers
```

AWS manages the underlying compute infrastructure.

### Why use it?
Use Fargate when:
- You want to run containers.
- You don't want to manage EC2 servers.
- You want container-based applications with serverless infrastructure management.

### Scenario

You have a Dockerized Python API:

```text
Docker Image
     ↓
ECS
     ↓
Fargate
     ↓
Running Container
```

You focus on the container/application rather than managing the underlying server.

### Exam point

**Serverless containers → Fargate**

# 5. AWS Lambda

### Definition
**AWS Lambda** is a **serverless functions service** that allows you to run code without provisioning or managing servers.

You upload your function code and configure things such as memory and execution settings.

### Why use it?
Lambda is useful for:
- Event-driven applications
- Backend APIs
- Automation
- File processing
- Scheduled tasks
- Lightweight application logic

### Scenario

A user uploads an image to S3:

```text
User
 ↓
S3
 ↓
Lambda
 ↓
Process Image
```

Lambda runs the code when the event occurs.

### Important concept

You don't normally keep a Lambda server running yourself.

Instead:

**Event → Lambda executes → Function finishes**

### Exam point

**Serverless + functions/code execution → Lambda**

# 6. AWS Step Functions

### Definition
**AWS Step Functions** is a **state machine service** used to coordinate multiple AWS services into **serverless workflows**.

Think of it as a **visual workflow/flowchart for cloud applications**.

### Why use it?

Suppose an application needs:

```text
Start
 ↓
Validate Order
 ↓
Charge Payment
 ↓
Update Database
 ↓
Send Email
 ↓
End
```

Step Functions can coordinate these individual steps.

### Benefits
- Coordinates multiple AWS services.
- Creates logical workflow steps.
- Tracks execution.
- Can handle failures and retries.
- Makes workflows easier to visualize.

### Scenario

An order-processing system:

```text
Order received
      ↓
Validate order
      ↓
Payment
      ↓
Update DynamoDB
      ↓
Send notification
      ↓
Order completed
```

Individual steps could use services such as Lambda, DynamoDB, and SNS.

### Exam point

**Serverless workflow/state machine → Step Functions**

# 7. Amazon Aurora Serverless

### Definition
**Aurora Serverless** is the serverless, on-demand version of **Amazon Aurora**.

It is designed for workloads where database capacity may need to adjust according to demand.

### Why use it?

Useful when:
- Database traffic varies.
- You don't want to continuously manage database capacity.
- Applications have unpredictable or intermittent workloads.

### Scenario

Imagine an application that normally receives:

```text
100 requests/hour
```

but occasionally receives:

```text
50,000 requests/hour
```

A serverless database option can be useful for workloads where demand changes significantly.

### Exam point

**Serverless relational/Aurora database → Aurora Serverless**

# Serverless Services — Quick Comparison

| Service | What it provides | Remember |
|---|---|---|
| **DynamoDB** | NoSQL database | Key-value / Document |
| **S3** | Object storage | Store objects/files |
| **Fargate** | Container compute | Serverless containers |
| **Lambda** | Function execution | Run code |
| **Step Functions** | Workflow orchestration | State machine |
| **Aurora Serverless** | Serverless relational database | On-demand Aurora |

## Easy Memory Trick

**DynamoDB → Data**  
**S3 → Storage**  
**Fargate → Containers**  
**Lambda → Code**  
**Step Functions → Workflow**  
**Aurora Serverless → Database**

### One architecture example

A serverless e-commerce application could look like:

```text
              Users
                ↓
          API Gateway
                ↓
             Lambda
           ↙       ↘
    DynamoDB       S3
       ↓
   Step Functions
       ↓
   Other AWS Services
```

The key idea is that the development team doesn't need to directly manage the underlying servers for these services.

### ⚠️ Exam distinction

Don't confuse:

- **EC2** → You manage the virtual server.
- **Fargate** → AWS manages the underlying compute for your containers.
- **Lambda** → AWS manages the underlying compute and you run functions.
- **S3** → Object storage, not a traditional server/filesystem.
- **DynamoDB** → NoSQL database.
- **Step Functions** → Coordinates workflows; it isn't the compute itself.

## Summary

> **Serverless = AWS manages the underlying infrastructure, while you focus on using the service/application and generally pay according to usage.**

**DynamoDB = NoSQL**  
**S3 = Object Storage**  
**Fargate = Containers**  
**Lambda = Functions**  
**Step Functions = Workflows**  
**Aurora Serverless = Database**
