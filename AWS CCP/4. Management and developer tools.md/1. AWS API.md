# ☁️ AWS Application Programming Interface (API)

## 1. Definition

An **Application Programming Interface (API)** is software that allows two applications or services to **communicate and exchange information with each other**.

The most common type of API communication is through **HTTP/S requests**.

### Simple example

```text
Application A
     ↓
    API
     ↓
Application B
```

The API acts as a **bridge/interface** between the two applications.

---

# 2. AWS APIs

AWS services can be controlled and interacted with through **APIs**.

AWS APIs are commonly accessed using **HTTPS requests**.

For example:

```text
Your Application
      ↓
   HTTPS Request
      ↓
  AWS API
      ↓
AWS Service
```

Each AWS service has its own **Service Endpoint** where API requests are sent.

For example:

```text
monitoring.us-east-1.amazonaws.com
```

This is an endpoint for the AWS monitoring service in the `us-east-1` Region.

---

# 3. Example of an AWS API Request

An AWS API request can contain information such as:

```text
GET / HTTP/1.1

host: monitoring.us-east-1.amazonaws.com

x-amz-target: GraniteServiceVersion20100801.GetMetricData

x-amz-date: 20180112T092034Z

Authorization: AWS4-HMAC-SHA256 Credential=REDACTEDREDACTED/20180411/....

Content-Type: application/json

Accept: application/json

Content-Encoding: amz-1.0

Content-Length: 45

Connection: keep-alive
```

You don't normally need to manually construct requests like this when working with AWS.

---

# 4. Signed Requests & Authorization

AWS needs to verify that the request is coming from an **authorized identity**.

Therefore, authenticated AWS API requests are typically **signed** using AWS credentials.

```text
AWS Credentials
      ↓
Generate signed request
      ↓
HTTPS Request
      ↓
AWS API
      ↓
Request authenticated
      ↓
AWS Service
```

The signature helps AWS verify the request and its integrity.

> **Important:** Never expose or hard-code your AWS credentials in applications or public code.

---

# 5. How Do We Interact With AWS APIs?

Users rarely send raw HTTP requests directly to AWS APIs.

Instead, AWS provides several **Developer Tools** that make interacting with APIs much easier.

```text
                         AWS
                          ↑
                          |
                         API
                    ↗     ↑     ↖
                   /      |      \
                  /       |       \
       Management      AWS SDK    AWS CLI
        Console
```

There are three important ways to remember:

---

## ① AWS Management Console

The **AWS Management Console** is a **WYSIWYG (What You See Is What You Get) web interface**.

Instead of writing API requests yourself:

```text
You
 ↓
AWS Management Console
 ↓
AWS API
 ↓
AWS Service
```

For example, when you click **"Launch instance"** in the console, the console communicates with AWS services through APIs behind the scenes.

### Simple:

> **Console = GUI/Web Interface**

---

## ② AWS SDK

**AWS SDKs (Software Development Kits)** allow developers to interact with AWS APIs using their **preferred programming language**.

For example:

```text
Python
Java
JavaScript
C#
Go
...
```

Conceptually:

```text
Python Application
       ↓
     AWS SDK
       ↓
    AWS API
       ↓
   AWS Service
```

### Simple:

> **SDK = Use AWS APIs through programming code**

This will become particularly relevant as you're starting **Python**, because you can eventually use Python SDKs to automate AWS tasks.

---

## ③ AWS CLI

The **AWS Command Line Interface (CLI)** allows you to interact with AWS services through a **terminal/shell**.

For example:

```text
Terminal
   ↓
 AWS CLI
   ↓
 AWS API
   ↓
AWS Service
```

Instead of clicking through the console, you can execute commands from your terminal.

### Simple:

> **CLI = Use AWS through the terminal**

---

# 6. Console vs SDK vs CLI

| Method                 | How you interact     | Best suited for                      |
| ---------------------- | -------------------- | ------------------------------------ |
| **Management Console** | Web/GUI              | Humans, visual management            |
| **AWS SDK**            | Programming language | Applications & automation            |
| **AWS CLI**            | Terminal/shell       | Command-line management & automation |
| **Raw HTTP Request**   | Direct API request   | Advanced/direct API interaction      |

---

# 7. Why Use AWS APIs?

AWS APIs are the **foundation behind many ways of interacting with AWS**.

They allow you to:

* Create AWS resources
* Configure resources
* Modify resources
* Delete resources
* Retrieve information
* Automate AWS operations
* Build applications that interact with AWS

The important concept is:

```text
Console ──┐
          │
CLI ──────┼──→ AWS API ──→ AWS Services
          │
SDK ──────┘
```

The **Console, CLI, and SDK are different interfaces for interacting with AWS APIs**.

---

# 9. When Should You Use Each?

### Management Console

Use when:

* You're learning AWS
* You want a visual interface
* You're manually configuring resources
* You want to quickly inspect resources

### CLI

Use when:

* You prefer the terminal
* You need repeatable commands
* You're scripting/automating AWS tasks
* You're managing resources from a shell

### SDK

Use when:

* You're building applications
* You want to automate AWS using code
* Your application needs to interact with AWS
* You want to integrate AWS into your software

# ☁️ AWS Service Endpoints

## 1. Definition

An **AWS Service Endpoint** is a specific URL/address that you use to **send requests to a particular AWS service**.

Simple definition:

> **Service Endpoint = The network address where you send API requests for an AWS service.**

For example:

```text id="7q2wzj"
Your Application
       ↓
HTTPS Request
       ↓
AWS Service Endpoint
       ↓
AWS Service
```

---

# 2. What Is an AWS Service Endpoint?

Each AWS service provides endpoints through which you can communicate with that service.

For example, from the previous API example:

```text id="w6u1oj"
monitoring.us-east-1.amazonaws.com
```

This is an endpoint for the **Amazon CloudWatch monitoring service** in the `us-east-1` Region.

Break it down:

```text id="7v3g4m"
monitoring
    ↓
AWS Service

us-east-1
    ↓
AWS Region

amazonaws.com
    ↓
AWS domain
```

So you can think of it as:

> **Service + Region + AWS domain**

---

# 3. Why Use Service Endpoints?

Applications need a way to **communicate with AWS services**.

The endpoint tells the request:

> **"Where should this API request go?"**

For example:

```text id="4s6j4j"
Python Application
       ↓
AWS SDK
       ↓
AWS API
       ↓
CloudWatch Endpoint
       ↓
CloudWatch
```

Without an appropriate endpoint, the request wouldn't know which AWS service/endpoint to communicate with.

---

# 4. How Does It Work?

Suppose your application wants information from CloudWatch.

Conceptually:

```text id="9r4q3q"
1. Application creates request
          ↓
2. AWS SDK / CLI prepares request
          ↓
3. Request is sent to service endpoint
          ↓
4. AWS authenticates request
          ↓
5. AWS service processes request
          ↓
6. Response is returned
```

Example endpoint:

```text id="g9h9dr"
monitoring.us-east-1.amazonaws.com
```

Your request is sent to that address.

---

# 5. Service Endpoints and Regions

AWS services can have **regional endpoints**.

For example:

```text id="8i7gqw"
us-east-1
   ↓
service.us-east-1.amazonaws.com

eu-west-1
   ↓
service.eu-west-1.amazonaws.com

ap-south-1
   ↓
service.ap-south-1.amazonaws.com
```

The exact endpoint format varies depending on the AWS service.

### Important:

Not every AWS service works exactly the same way with Regions and endpoints. Some services are **regional**, while some have **global** aspects.

For Cloud Practitioner, the important concept is:

> **An AWS service endpoint is the address used to access an AWS service API, often associated with a specific AWS Region.**

---

# 6. When Do You Use Service Endpoints?

You generally interact with service endpoints when:

* Using AWS APIs directly
* Using the AWS CLI
* Using AWS SDKs
* Building applications that communicate with AWS
* Configuring network connectivity to AWS services

You usually **don't need to manually type the endpoint** when using the AWS Console, CLI, or SDK because these tools handle much of this for you.

---

# 7. Scenario-Based Example

Suppose you're writing a Python application that needs to retrieve CloudWatch metrics.

You could conceptually have:

```text id="8t8dkt"
Python Application
        ↓
AWS SDK
        ↓
CloudWatch API
        ↓
monitoring.us-east-1.amazonaws.com
        ↓
CloudWatch
        ↓
Metrics returned
```

The SDK handles the underlying API communication, so you don't have to manually construct the entire HTTP request.

---

# 8. Service Endpoint vs AWS API

These two terms are related but **not the same**.

### AWS API

The **interface** that allows you to communicate with an AWS service.

```text
API
↓
How you communicate
```

### Service Endpoint

The **network address** where the API request is sent.

```text
Endpoint
↓
Where you send the request
```

Think of it like a phone:

```text
API
→ The communication system

Endpoint
→ The phone number/address you contact
```

---

# 9. Service Endpoint vs AWS Console

### AWS Console

You interact through a web interface:

```text
You
 ↓
AWS Console
 ↓
AWS APIs
 ↓
AWS Services
```

### Direct API communication

```text
Application
 ↓
HTTPS Request
 ↓
Service Endpoint
 ↓
AWS API
 ↓
AWS Service
```

The Console, CLI, and SDK make API interaction easier; they don't eliminate the underlying AWS APIs.
