# AWS Organizations and Accounts

This topic is about **managing multiple AWS accounts centrally**. The screenshot introduces AWS Organizations, Root Account Users, Organizational Units, and Service Control Policies.

---

## 1. AWS Organizations

### Definition

**AWS Organizations** is a service that allows you to centrally manage multiple AWS accounts.

According to your source, it allows you to:

* Create new AWS accounts
* Centrally manage **billing**
* Control **access**
* Manage **compliance**
* Manage **security**
* Share resources across AWS accounts

### Simple idea

Instead of managing 10 AWS accounts independently:

```text
                 AWS Organizations
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
      Dev Account   Test Account   Prod Account
```

You can manage them as part of one organization.

### Why use it?

It's useful for companies that have multiple AWS accounts for different:

* Teams
* Environments
* Departments
* Projects
* Business units

### Scenario

A company has:

```text
Company
│
├── Development Account
├── Testing Account
├── Production Account
├── Security Account
└── Finance Account
```

AWS Organizations allows the company to manage these accounts centrally.

# 2. AWS Account vs User Account

This is **very important** for the exam.

### AWS Account

An **AWS Account** is the container that holds your AWS resources.

For example:

```text
AWS Account
│
├── EC2
├── S3
├── RDS
├── VPC
└── IAM Users
```

### User Account / IAM User

An **IAM User** is an identity that can be given permissions to access resources within an AWS account.

So:

> **AWS Account ≠ User Account**

Think:

```text
AWS Account
    ↓
contains resources
    ↓
IAM Users access those resources
```

# 3. Root Account User

### Definition

The **Root Account User** is the single sign-in identity associated with an AWS account that has complete access to the services and resources in that account.

Your screenshot highlights:

* Every AWS account has a Root Account User.
* The root user has complete access.
* There is one root user per AWS account.
* Root should not be used for normal daily tasks.

### Important distinction

```text
AWS Organization
       ↓
Multiple AWS Accounts
       ↓
Each AWS Account
       ↓
One Root Account User
```

So if you have 5 AWS accounts, each account has its own root user.

# 4. Organizational Units — OUs

### Definition

An **Organizational Unit (OU)** is a group of AWS accounts within an AWS Organization.

OUs can also contain other OUs, allowing you to create a hierarchy.

Example:

```text
Organization
│
├── Production OU
│   ├── Production-India
│   └── Production-US
│
├── Development OU
│   ├── Dev-Team-A
│   └── Dev-Team-B
│
└── Security OU
    ├── Security
    └── Logging
```

### Why use OUs?

OUs allow you to organize accounts logically and apply centralized policies to groups of accounts.

### Scenario

Suppose your organization has:

```text
Development
Development Account 1
Development Account 2
Development Account 3
```

You can place those accounts into a **Development OU**.

You can then apply organizational controls to that OU.

# 5. Service Control Policies — SCPs

### Definition

**Service Control Policies (SCPs)** provide centralized control over the **maximum available permissions** for accounts in an AWS Organization.

Your screenshot describes SCPs as giving central control over allowed permissions for accounts in the organization.

### Important concept

An SCP **does not directly grant permissions** to users.

Instead, it establishes the **maximum permissions** that identities in affected member accounts can have.

Think:

```text
SCP
 ↓
Maximum permissions allowed
 ↓
IAM policies
 ↓
Actual permissions
```

### Example

Suppose an IAM administrator gives a user:

```text
Allow:
ec2:*
```

But an SCP applied to the account denies access to a particular EC2 action.

The user cannot use that action.

So:

> **IAM says what you can do.**
> **SCP says what the account is allowed to permit.**

# 6. AWS Organizations Hierarchy

The overall structure can look like:

```text
                 Organization
                      │
                Management Account
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
       OU: Dev                OU: Production
          │                       │
     ┌────┴────┐             ┌────┴────┐
     ↓         ↓             ↓         ↓
   AWS       AWS           AWS       AWS
 Account   Account        Account   Account
```

This is the key relationship you should understand.

---

# 7. Management Account

Your screenshot calls this the **Master/Root Account**.

The modern AWS terminology is **management account**.

It is the AWS account that manages the organization.

It is different from the **root user**.

### Don't confuse these:

| Term                   | Meaning                                         |
| ---------------------- | ----------------------------------------------- |
| **AWS Organization**   | Collection of AWS accounts managed together     |
| **Management Account** | Account that manages the organization           |
| **AWS Account**        | Individual AWS account containing resources     |
| **Root User**          | Special identity associated with an AWS account |
| **IAM User**           | Identity created for users/workloads            |
| **OU**                 | Group/hierarchy of AWS accounts                 |
| **SCP**                | Organization-level permission guardrail         |

# 8. Important Exam Concept

The screenshot says:

> **AWS Organizations must be turned on; once turned on it cannot be turned off.**

And:

> You can create as many AWS accounts as you like, with one account being the Master/Root Account.

For your exam notes, preserve this source framing, but remember that AWS terminology has evolved: **Master Account is now called Management Account**.

# Scenario-Based Example

Imagine a company called **ABC Corp**.

They have:

```text
ABC Organization
│
└── Management Account
       │
       ├── Development OU
       │      ├── Dev Account
       │      └── Test Account
       │
       ├── Production OU
       │      ├── Production-India
       │      └── Production-US
       │
       └── Security OU
              └── Security Account
```

The company can use **SCPs** to establish organization-wide restrictions.

For example:

```text
Production OU
      ↓
SCP
      ↓
Restrict certain AWS actions
      ↓
Production accounts
```

Within an individual account, administrators can then use **IAM policies** to decide which users/roles can actually perform permitted actions.

| **OU**                         | Group of AWS accounts                          |

**Organization → Accounts → OUs → SCPs**

And:

**AWS Account = Where resources live**
**IAM User = Who accesses them**
**SCP = Maximum boundary for the account**
