# AWS CDK

## 1. Definition

**AWS CDK (Cloud Development Kit)** is an **Infrastructure as Code (IaC) framework** that lets you define AWS infrastructure using familiar programming languages instead of writing CloudFormation templates directly.

You can use languages such as:

* TypeScript
* JavaScript
* Python
* Java
* C#
* Go

The important relationship is:

```text
Your Programming Language
          ↓
       AWS CDK
          ↓
 CloudFormation Template
          ↓
 AWS CloudFormation
          ↓
   AWS Infrastructure
```

So the key point is:

> **CDK is not a replacement for CloudFormation. CDK generates CloudFormation templates, and CloudFormation provisions the AWS resources.**

---

# 2. Why Do We Need CDK?

With CloudFormation, you can write:

```yaml
Resources:
  MyBucket:
    Type: AWS::S3::Bucket
```

That's perfectly fine.

But for large infrastructure, CloudFormation templates can become quite lengthy.

With CDK, you can use a programming language.

For example, Python:

```python
from aws_cdk import aws_s3 as s3

bucket = s3.Bucket(
    self,
    "MyBucket"
)
```

CDK then synthesizes this into a CloudFormation template.

So instead of directly writing:

```text
YAML/JSON
     ↓
CloudFormation
```

you can write:

```text
Python/TypeScript/etc.
          ↓
         CDK
          ↓
 CloudFormation
```

---

# 3. How CDK Works

The basic workflow is:

```text
Developer
    ↓
Write CDK code
    ↓
cdk synth
    ↓
CloudFormation template
    ↓
cdk deploy
    ↓
CloudFormation
    ↓
AWS resources
```

Two commands are particularly important:

```bash
cdk synth
```

and:

```bash
cdk deploy
```

### `cdk synth`

**Synthesizes** your CDK application into a CloudFormation template.

Conceptually:

```text
Python code
    ↓
CDK
    ↓
CloudFormation YAML/JSON
```

### `cdk deploy`

Deploys the generated CloudFormation infrastructure to AWS.

```text
CDK
 ↓
CloudFormation
 ↓
AWS
```

---

# 4. CDK vs CloudFormation

This distinction is extremely important.

### CloudFormation

You directly write a template:

```yaml
Resources:
  MyBucket:
    Type: AWS::S3::Bucket
```

### CDK

You write programming code:

```python
bucket = s3.Bucket(
    self,
    "MyBucket"
)
```

CDK then generates the CloudFormation template.

Think:

> **CloudFormation = infrastructure template**

> **CDK = programming interface for defining infrastructure that ultimately becomes CloudFormation**

---

# 5. CDK Constructs

One of the most important CDK concepts is a **Construct**.

A construct is a reusable building block representing AWS infrastructure.

For example:

```python
s3.Bucket(...)
```

represents an S3 bucket construct.

Other examples:

```text
S3 Bucket
Lambda Function
DynamoDB Table
VPC
EC2
Load Balancer
API Gateway
```

You can combine constructs to create larger architectures.

---

# 6. Levels of Constructs

CDK constructs are commonly described using three levels:

### L1 — CFN Resources

These are very close to the underlying CloudFormation resources.

Example concept:

```text
CfnBucket
CfnInstance
CfnVPC
```

They give you detailed control but require more configuration.

---

### L2 — Curated Constructs

These provide higher-level abstractions around AWS resources.

For example:

```python
s3.Bucket(...)
```

Instead of configuring every CloudFormation property manually.

They often provide sensible defaults and convenience methods.

---

### L3 — Patterns

These are higher-level architectural patterns combining multiple resources.

For example, conceptually:

```text
Load Balancer
      ↓
     ECS
      ↓
   Database
```

Instead of individually creating every component, a pattern can provide a complete architecture.

### Memory:

```text
L1 → Low-level
L2 → Higher-level AWS resource
L3 → Architecture pattern
```

For Cloud Practitioner, just understand the concept of **constructs**. You don't need to memorize all three levels yet.

---

# 7. CDK Uses Normal Programming Concepts

This is one of the biggest advantages of CDK.

Because you're using a programming language, you can use things like:

```text
Variables
Functions
Classes
Loops
Conditions
Modules
Libraries
```

For example:

```python
for i in range(3):
    # define infrastructure
```

This can be useful when infrastructure becomes complex.

You can also create reusable infrastructure components.

# 9. CDK and AWS APIs

You learned earlier:

```text
Console
CLI
SDK
```

All of these ultimately interact with AWS through APIs.

CDK is slightly different in purpose.

```text
CDK code
   ↓
CloudFormation template
   ↓
CloudFormation
   ↓
AWS APIs
   ↓
Resources
```

So CDK is primarily an **infrastructure definition/deployment framework**, not simply another way to make individual API calls.

---

# 10. CDK vs SDK

This distinction is important.

### AWS SDK

Used by applications to interact with AWS services.

For example, Python Boto3:

```python
import boto3

s3 = boto3.client("s3")
s3.list_buckets()
```

This is application code interacting with AWS.

### AWS CDK

Used to **define infrastructure**.

```python
bucket = s3.Bucket(
    self,
    "MyBucket"
)
```

This describes infrastructure that CDK will synthesize/deploy.

### Memory:

> **SDK → Application interacts with AWS**

> **CDK → Code defines AWS infrastructure**

---

# 11. CDK vs CLI

### AWS CLI

```bash
aws s3 ls
```

You are executing an AWS operation.

### CDK

```python
bucket = s3.Bucket(self, "MyBucket")
```

You are defining infrastructure.

So:

```text
CLI
 ↓
"Do this operation."

CDK
 ↓
"Define this infrastructure."
```

# 13. CDK and CloudFormation Stacks

CDK applications can define **CloudFormation stacks**.

Conceptually:

```text
CDK Application
      ↓
CDK Stack
      ↓
CloudFormation Stack
      ↓
AWS Resources
```

For example:

```text
MyApplication
│
├── NetworkStack
│     └── VPC
│
├── ComputeStack
│     └── EC2
│
└── DatabaseStack
      └── RDS
```

This allows infrastructure to be organized into logical components.

---

# 14. When Should You Use CDK?

CDK is particularly useful when:

* Your team is comfortable with programming languages.
* Infrastructure is becoming complex.
* You want reusable infrastructure components.
* You want to use software engineering practices for infrastructure.
* You want infrastructure stored in Git.
* You want to integrate IaC with CI/CD.
* You're primarily working with AWS.

---

# 15. When Should You Use CloudFormation Directly?

CloudFormation can be preferable when:

* You want a native AWS IaC solution.
* Your team already works with CloudFormation templates.
* You need direct access to CloudFormation template capabilities.
* The infrastructure is relatively straightforward.
* You don't need the additional abstraction provided by CDK.

---

# 16. CDK vs Terraform vs CloudFormation

This is the bigger picture:

|                     | CloudFormation | CDK                                 | Terraform                 |
| ------------------- | -------------- | ----------------------------------- | ------------------------- |
| Type                | IaC service    | IaC framework                       | IaC tool                  |
| Developer           | AWS            | AWS                                 | HashiCorp                 |
| Configuration       | YAML/JSON      | Programming languages               | HCL                       |
| AWS                 | Native         | AWS-focused                         | Yes                       |
| Multi-cloud         | No             | Not its primary purpose             | Yes                       |
| Uses CloudFormation | —              | **Yes**                             | No                        |
| Abstraction         | Template       | Programming abstractions/constructs | Declarative configuration |

The most important relationship:

```text
              AWS Infrastructure

                    ↑
                    │
        ┌───────────┴───────────┐
        │                       │
 CloudFormation                Terraform
        ↑
        │
       CDK
```

CDK sits **on top of CloudFormation**.
