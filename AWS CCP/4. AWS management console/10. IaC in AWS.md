# ☁️ Infrastructure as Code (IaC) in AWS

**IaC = Infrastructure as Code.**

It is one of the most important concepts you should learn if you're moving from **Cloud Engineer → DevOps → Platform Engineer**.

> **Infrastructure as Code means defining and managing infrastructure using code or machine-readable configuration files instead of manually creating and configuring resources through a GUI.**

Instead of doing this manually:

```text
AWS Console
   ↓
Create VPC
   ↓
Create Subnet
   ↓
Create Route Table
   ↓
Create Security Group
   ↓
Create EC2
   ↓
Configure everything
```

You describe the desired infrastructure in files:

```text
IaC files
   ↓
IaC tool
   ↓
AWS APIs
   ↓
AWS infrastructure
```

---

# 1. Why Do We Need IaC?

Imagine your company needs this architecture:

```text
                    Internet
                       ↓
                Load Balancer
                       ↓
             ┌─────────┴─────────┐
             ↓                   ↓
          EC2-A                EC2-B
          AZ-1                 AZ-2
             └─────────┬─────────┘
                       ↓
                      RDS
```

Manually creating this involves many steps.

You have to configure:

* VPC
* Subnets
* Route tables
* Internet Gateway
* Security Groups
* EC2 instances
* Load Balancer
* RDS
* IAM
* Networking

And then imagine doing it again for:

```text
Development
Testing
Staging
Production
```

Manual configuration becomes:

> **Slow + repetitive + difficult to reproduce + prone to human error.**

IaC solves this by defining the infrastructure in code.

# 3. Example: Terraform

Terraform is one of the most widely used IaC tools in cloud/DevOps.

A simplified example:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"
}
```

Instead of clicking:

```text
EC2
 ↓
Launch instance
 ↓
Choose AMI
 ↓
Choose instance type
 ↓
Configure
 ↓
Launch
```

you define what you want in code.

Terraform then communicates with AWS to create/manage the infrastructure.

# 4. What Does "Infrastructure as Code" Actually Mean?

There are three important ideas.

### Infrastructure

Things such as:

```text
VPC
Subnet
EC2
S3
RDS
Load Balancer
Security Groups
IAM
```

### As

You're treating infrastructure in the same way you treat software configuration.

### Code

You define infrastructure using:

```text
Configuration files
Templates
Variables
Modules
Version control
```

So:

> **Infrastructure becomes something that can be written, reviewed, versioned, tested and reproduced.**

---

# 5. AWS IaC Tools

AWS has several IaC-related options.

## AWS CloudFormation

**AWS CloudFormation** is AWS's native Infrastructure as Code service.

You define AWS infrastructure using templates.

Templates can use:

```text
YAML
JSON
```

Example conceptually:

```yaml
Resources:
  MyBucket:
    Type: AWS::S3::Bucket
```

CloudFormation reads the template and creates/manages the resources.

---

# 6. Terraform

**Terraform** is an infrastructure-as-code tool from HashiCorp.

It isn't AWS-specific.

It can manage infrastructure across multiple providers.

For example:

```text
Terraform
   ├── AWS
   ├── Azure
   ├── Google Cloud
   └── Other providers
```

This makes Terraform particularly relevant if you're learning both **AWS and Azure**.

---

# 7. CloudFormation vs Terraform

| CloudFormation               | Terraform                |
| ---------------------------- | ------------------------ |
| AWS-native                   | Multi-cloud              |
| Developed by AWS             | Developed by HashiCorp   |
| Primarily AWS infrastructure | AWS, Azure, GCP, etc.    |
| YAML/JSON templates          | HCL                      |
| Deep AWS integration         | Broad provider ecosystem |
| AWS-specific IaC             | General-purpose IaC      |

For **AWS Cloud Practitioner**, understand both conceptually.

For your **Cloud/DevOps career**, Terraform is worth learning deeply.

# 8. IaC vs AWS CLI

You just learned AWS CLI, so this distinction is important.

### AWS CLI

You tell AWS:

> **"Perform this operation."**

Example:

```bash
aws ec2 describe-instances
```

or:

```bash
aws s3 mb s3://my-bucket
```

You're executing individual commands.

---

### IaC

You tell the IaC tool:

> **"This is the infrastructure configuration I want."**

For example:

```hcl
resource "aws_instance" "web" {
  instance_type = "t3.micro"
}
```

The IaC tool determines what needs to be created/changed.

---

# 9. IaC vs SDK

Same idea.

### SDK

Your application says:

```python
ec2.describe_instances()
```

You're writing program logic that calls AWS APIs.

### IaC

You describe infrastructure:

```text
I want:
VPC
 ├── Subnet
 ├── Security Group
 └── EC2
```

The IaC engine manages the infrastructure required to reach that desired state.

---

# 10. IaC and Desired State

This is a **very important concept**.

Suppose your Terraform configuration says:

```text
EC2
instance_type = t3.medium
```

Your actual infrastructure currently has:

```text
EC2
instance_type = t3.micro
```

The IaC tool detects that the actual infrastructure doesn't match the desired configuration.

Conceptually:

```text
Desired State
     │
     │ compare
     ↓
Actual State
     │
     ↓
Required changes
```

Then the tool can make the required changes.

This is why IaC is often described as **declarative**.

---

# 11. Declarative vs Imperative

This is an important DevOps concept.

## Imperative

You tell the system **how to do something**.

For example:

```text
1. Create VPC
2. Create subnet
3. Create route table
4. Create security group
5. Create EC2
```

You're specifying the steps.

---

## Declarative

You describe **what the final state should look like**.

```text
I want:

VPC
 ├── Public Subnet
 │      └── EC2
 │
 └── Private Subnet
        └── Database
```

The IaC tool determines the necessary actions.

Terraform is primarily **declarative**.

---

# 12. Why IaC Is Powerful

## 1. Repeatability

You can reproduce the same infrastructure.

```text
Terraform
   ↓
Dev Environment

Terraform
   ↓
Test Environment

Terraform
   ↓
Production Environment
```

---

## 2. Consistency

Instead of having:

```text
Dev → configuration A

Test → configuration B

Prod → configuration C
```

you can use the same infrastructure definitions with environment-specific variables where appropriate.

---

## 3. Version Control

IaC files can be stored in Git.

For example:

```text
Git Repository

terraform/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
```

Now infrastructure changes can be tracked.

You can see:

```text
Who changed it?
What changed?
When?
Why?
```

A developer proposes:


```text

   ↓

   ↓
```

# 14. Automation

IaC enables infrastructure automation.

For example:

```text

   ↓

   ↓
Terraform
   ↓
AWS
   ↓
```

# 15. Disaster Recovery

Imagine your infrastructure is accidentally destroyed.

If your infrastructure was manually configured, reconstructing everything can be difficult.

With IaC:

```text
Git Repository
      ↓
IaC
      ↓
AWS
      ↓
Recreate infrastructure
```

The exact recovery process still depends on your architecture and data backups, but IaC makes **rebuilding infrastructure** much easier.

Important:

> IaC does **not** replace data backups.

# 17. IaC and Drift

Another important concept is **configuration drift**.

Suppose Terraform says:

```text
EC2 = t3.medium
```

But someone manually changes the instance configuration outside Terraform.

Now:

```text
Terraform configuration
        ≠
Actual AWS infrastructure
```

This difference is called:

> **Drift**

Conceptually:

```text
Desired State
     ↓
    IaC
     │
     │ doesn't match
     ↓
Actual State
     ↓
Drift
```

This is one reason teams try to control manual changes to IaC-managed infrastructure.

---

# 18. IaC and Idempotency

You may encounter the word **idempotent**.

The basic idea:

> Running the same desired-state operation repeatedly should not keep creating unwanted duplicate infrastructure.

For example, if your configuration says:

```text
I need ONE VPC
```

running the IaC workflow again should recognize that the desired resource already exists rather than blindly creating another identical VPC every time.

This is a major concept in infrastructure automation.

# 19. IaC and Modules

As infrastructure grows, you don't want one enormous file.

You can organize reusable components.

For example:

```text
Terraform
│
├── VPC Module
├── EC2 Module
├── RDS Module
├── Security Module
└── Monitoring Module
```

Then reuse them.

For example:

```text
Development
    ↓
VPC Module

Production
    ↓
VPC Module
```

with different inputs/configuration.

# 21. Terraform's Basic Workflow

When you eventually learn Terraform, you'll encounter:

```bash
terraform init
```

Initializes the Terraform working directory.

Then:

```bash
terraform plan
```

Shows what Terraform intends to change.

Then:

```bash
terraform apply
```

Applies the changes.

And:

```bash
terraform destroy
```

destroys resources managed by the configuration.

### Mental model:

```text
init
 ↓
plan
 ↓
apply
```

And:

```text
destroy
```

is the destructive operation.

Be particularly careful with `destroy`.

For example:

```text
CloudFormation Stack
```

# 🔥 The Most Important Distinction

Remember these four:

| Technology  | Main idea                                                   |
| ----------- | ----------------------------------------------------------- |
| **Console** | Manually manage through GUI                                 |
| **CLI**     | Manage through commands                                     |
| **SDK**     | Manage/interact through application code                    |
| **IaC**     | Define and manage infrastructure through configuration/code |

### Simple memory:

> **Console = Click**

> **CLI = Command**

> **SDK = Code that talks to AWS**

> **IaC = Code that defines infrastructure**

For your **Cloud Engineer → DevOps → Platform Engineer** path, IaC is a skill you should eventually take seriously. After your AWS networking fundamentals, I'd put **Terraform + Git + CI/CD** near the top of your next practical learning phase.
