# 🔑 AWS Access Keys

These screenshots are explaining **AWS Access Keys**, which are used for **programmatic access to AWS** through tools such as the **AWS CLI, AWS SDKs, and APIs**.

This is an important topic because you've just learned:

**API → CLI → SDK → CloudShell → IAM**

Access keys are the credentials that can be used by programmatic tools to authenticate to AWS.

---

## 1. Definition

An **AWS Access Key** is a credential used to authenticate programmatic requests to AWS.

An access key consists of two parts:

```text
Access Key
   │
   ├── Access Key ID
   │
   └── Secret Access Key
```

Think of them as:

> **Access Key ID = username-like identifier**

> **Secret Access Key = secret credential**

Together, they can be used by the AWS CLI, SDKs, and other tools to authenticate requests.

---

# 2. Why Do We Need Access Keys?

When you use the AWS Management Console:

```text
You
 ↓
Browser
 ↓
AWS Management Console
 ↓
AWS
```

You normally authenticate through the console's sign-in process.

But suppose you're using the AWS CLI:

```bash
aws ec2 describe-instances
```

There is no browser login happening for every command.

The CLI needs credentials to authenticate the request.

So:

```text
You
 ↓
AWS CLI
 ↓
Access Credentials
 ↓
AWS API
 ↓
AWS Service
```

The same concept applies to an AWS SDK.

For example, an application using Python/Boto3 may need AWS credentials to make authenticated AWS API calls.

---

# 3. Access Key ID vs Secret Access Key

This distinction is very important.

### Access Key ID

Example:

```text
AKIAIOSFODNN7EXAMPLE
```

It identifies the credential.

### Secret Access Key

Example:

```text
wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

This is the **secret part** used when authenticating/signing requests.

### Think:

```text
Access Key ID
      +
Secret Access Key
      ↓
AWS Credentials
```

The screenshot refers to the access key as **AWS credentials**.

---

# 4. Access Keys vs Console Password

The first screenshot makes an important distinction.

### Console access

Uses a password/sign-in mechanism:

```text
Username/identity
      +
Password
      ↓
AWS Management Console
```

### Programmatic access

Uses credentials such as:

```text
Access Key ID
      +
Secret Access Key
      ↓
AWS CLI / SDK / API
```

So remember:

| Access method          | Typical credential/interface |
| ---------------------- | ---------------------------- |
| AWS Management Console | Console sign-in credentials  |
| AWS CLI                | AWS credentials              |
| AWS SDK                | AWS credentials              |
| AWS API                | Authenticated credentials    |

---

# 5. How Access Keys Are Used

Imagine you run:

```bash
aws s3 ls
```

The flow is roughly:

```text
You
 ↓
AWS CLI
 ↓
Credentials
 ↓
AWS API request
 ↓
Authentication/authorization
 ↓
Amazon S3
 ↓
Response
```

The credentials authenticate the request.

Then **IAM permissions** determine what that identity is actually allowed to do.

This distinction is extremely important:

> **Credentials prove who/what is making the request.**

> **IAM permissions determine what that identity is allowed to do.**

---

# 6. Access Keys Don't Automatically Give Full Access

This is one of the most important points from the screenshot:

> **Access Keys have whatever access the associated user has to AWS resources.**

For example, suppose an IAM user has permission to:

```text
S3 → Read
```

If that user's access key is used:

```text
Access Key
    ↓
IAM User
    ↓
S3 Read permission
```

The key doesn't magically provide administrator access.

Similarly, if the identity has:

```text
EC2 → Read
S3 → Read
```

then programmatic access through its credentials is limited according to those permissions.

---

# 7. Why Security Is Extremely Important

The first screenshot gives these warnings:

* **Never share your access keys**
* **Never commit access keys to a codebase**
* Access keys can be deactivated
* A user can have two active access keys

The most important one:

> **Never expose your Secret Access Key.**

For example, don't put this into GitHub:

```python
access_key = "AKIA..."
secret_key = "...."
```

That's a serious credential exposure.

---

# 8. Access Keys and GitHub

Imagine you write:

```python
import boto3

aws_access_key = "AKIA..."
aws_secret_key = "SECRET..."
```

and then:

```text
git add .
git commit
git push
```

Now the credentials could be exposed through your repository.

Therefore:

```text
❌ Hard-code credentials
❌ Commit credentials to Git
❌ Send credentials in chat/email
❌ Put credentials in public repositories
```

Prefer secure credential mechanisms such as IAM roles, temporary credentials, or IAM Identity Center where appropriate.

---

# 9. Two Active Access Keys

The screenshot says:

> **You can have two active Access Keys.**

For an IAM user, this can be useful when **rotating credentials**.

For example:

```text
Old Key → Active
New Key → Active
```

You can update your applications/tools to use the new key:

```text
Application
    ↓
New Access Key
```

Then deactivate the old key:

```text
Old Key → Inactive
```

This allows credential rotation without necessarily causing downtime.

### Simple rotation process

```text
Create new key
      ↓
Update application
      ↓
Test
      ↓
Deactivate old key
      ↓
Delete old key when no longer needed
```

---

# 10. Deactivating an Access Key

An access key can be **deactivated**.

Conceptually:

```text
Access Key
   │
   ├── Active
   │
   └── Inactive
```

An inactive access key cannot be used for normal authentication.

This is useful if you suspect a key has been exposed or you're performing credential rotation.

# 11. Where AWS CLI Stores Credentials

The second screenshot shows the AWS CLI credentials file:

```text
~/.aws/credentials
```

On Linux/macOS, `~` means your home directory.

So:

```text
~/.aws/credentials
```

means:

```text
Home directory
   ↓
.aws
   ↓
credentials
```

The file can contain profiles.

For example:

```ini
[default]
aws_access_key_id=...
aws_secret_access_key=...

[example]
aws_access_key_id=...
aws_secret_access_key=...
region=ca-central-1
```

### Important concept:

> **Default profile = used when you don't explicitly specify another profile.**

---

# 12. What Is an AWS Profile?

A **profile** is a named set of AWS configuration/credential settings used by the AWS CLI and SDK credential chain.

For example:

```text
[default]
   ↓
Development credentials

[production]
   ↓
Production credentials
```

Then you can specify:

```bash
aws ec2 describe-instances --profile production
```

Instead of:

```bash
aws ec2 describe-instances
```

which uses the default profile when no other credential source/profile is selected.

---

# 13. `aws configure`

The screenshot shows:

```bash
aws configure
```

This command interactively configures credentials and default settings for the AWS CLI.

It can ask for:

```text
AWS Access Key ID
AWS Secret Access Key
Default region
Default output format
```

For example:

```text
$ aws configure

AWS Access Key ID:     ...
AWS Secret Access Key: ...
Default region:        us-west-2
Default output format: json
```

This can populate the AWS CLI configuration/credentials files.

# 14. Environment Variables

The second screenshot also shows environment variables:

```bash
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_DEFAULT_REGION=us-west-2
```

These are environment variables that AWS CLI/SDK credential/configuration mechanisms can read.

So another possible flow is:

```text
Environment Variables
        ↓
AWS CLI / SDK
        ↓
AWS API
```

This can be particularly useful in automation and CI/CD environments.

# 15. Credential Sources

At a high level, AWS tools can obtain credentials from different sources.

For your current level, understand these:

```text
AWS CLI / SDK
     │
     ├── Environment variables
     │
     ├── AWS credentials/config files
     │
     ├── IAM roles
     │
     └── Other supported credential providers
```

You don't always need to manually enter access keys.

In fact, for AWS workloads running on AWS infrastructure, **IAM roles and temporary credentials are generally preferred over long-term access keys**.

# 17. Scenario Example

Suppose you're managing AWS infrastructure using the CLI.

You run:

```bash
aws ec2 describe-instances
```

The CLI needs credentials.

You have:

```text
Access Key ID
       +
Secret Access Key
```

The CLI uses those credentials to authenticate the request.

AWS then evaluates the permissions associated with that identity.

If the identity has permission:

```text
ec2:DescribeInstances
```

the request can succeed.

If it doesn't:

```text
AccessDenied
```

So:

```text
Credentials → Authentication
IAM Policy → Authorization
```

### This distinction is worth memorizing.
