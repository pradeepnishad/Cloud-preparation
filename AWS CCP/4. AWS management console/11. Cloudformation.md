# AWS CloudFormation

## 1. Definition

**AWS CloudFormation is an AWS-native Infrastructure as Code (IaC) service that lets you define, provision, and manage AWS resources using templates instead of creating each resource manually through the AWS Management Console.**

In simple words:

> **CloudFormation = Write a template describing your AWS infrastructure → CloudFormation creates and manages it for you.**

For example, instead of manually creating:

```text
VPC
 ↓
Subnets
 ↓
Route Tables
 ↓
Internet Gateway
 ↓
Security Groups
 ↓
EC2
 ↓
RDS
```

you can describe the infrastructure in a CloudFormation template.

```text
CloudFormation Template
        ↓
AWS CloudFormation
        ↓
AWS APIs
        ↓
AWS Resources
```

---

# 2. What Problem Does CloudFormation Solve?

Imagine you manually create a production environment.

You create:

```text
VPC
2 Subnets
2 Route Tables
Internet Gateway
NAT Gateway
Security Groups
EC2
RDS
Load Balancer
```

Now your company wants the **same architecture** for development.

You could manually recreate everything.

That's:

* Slow
* Repetitive
* Error-prone
* Difficult to reproduce
* Difficult to track

With CloudFormation:

```text
CloudFormation Template
          ↓
     Development
```

and the same template can be used as a basis for:

```text
Development
Testing
Staging
Production
```

with different parameters/configuration where required.

---

# 3. How CloudFormation Works

The basic architecture is:

```text
                CloudFormation Template
                         ↓
                   CloudFormation
                         ↓
                    AWS APIs
                         ↓
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
       VPC              EC2              RDS
```

The template describes the **desired infrastructure**.

CloudFormation then creates and manages the AWS resources defined by that template.

---

# 4. CloudFormation Templates

A **template** is the file where you define your infrastructure.

CloudFormation templates are commonly written in:

* **YAML**
* **JSON**

YAML is generally easier for humans to read.

A very simple example:

```yaml
AWSTemplateFormatVersion: '2010-09-09'

Resources:

  MyBucket:
    Type: AWS::S3::Bucket
```

This describes an S3 bucket.

You aren't manually clicking:

```text
S3
 ↓
Create bucket
 ↓
Enter configuration
 ↓
Create
```

Instead, the template declares:

```text
I want an S3 bucket.
```

CloudFormation handles the provisioning.

---

# 5. Important CloudFormation Concept: Stack

This is **very important for exams**.

A **CloudFormation stack** is a collection of AWS resources that CloudFormation manages together from a template.

Think:

```text
Template
   ↓
CloudFormation
   ↓
Stack
   ↓
AWS Resources
```

For example:

```text
Production Stack
│
├── VPC
├── Subnets
├── Route Tables
├── Security Groups
├── EC2
├── Load Balancer
└── RDS
```

CloudFormation manages these resources as part of the stack.

### Easy memory:

> **Template = blueprint**

> **Stack = deployed infrastructure based on the blueprint**

---

# 6. Template vs Stack

This distinction is extremely important.

| Template                         | Stack                                  |
| -------------------------------- | -------------------------------------- |
| Blueprint/configuration          | Actual deployed resources              |
| YAML/JSON file                   | Collection of AWS resources            |
| Describes what should be created | Represents the deployed infrastructure |
| Input to CloudFormation          | Managed by CloudFormation              |

Think about a house:

```text
House blueprint → Template

Actual constructed house → Stack
```

# 8. Resources

**Resources** are the AWS infrastructure components you want CloudFormation to create.

Example:

```yaml
Resources:

  MyBucket:
    Type: AWS::S3::Bucket
```

Here:

```text
MyBucket
   ↓
Logical ID

AWS::S3::Bucket
   ↓
AWS resource type
```

The `Resources` section is fundamental.

You can define:

```text
EC2
S3
VPC
Subnet
Security Group
RDS
Load Balancer
IAM
Lambda
```

and many other AWS resources.

---

# 9. Logical ID

Look at:

```yaml
Resources:

  MyBucket:
    Type: AWS::S3::Bucket
```

`MyBucket` is the **logical ID**.

It is the identifier you use inside the template to refer to that resource.

For example:

```yaml
Resources:

  WebServer:
    Type: AWS::EC2::Instance

  WebBucket:
    Type: AWS::S3::Bucket
```

Here:

```text
WebServer → logical ID
WebBucket → logical ID
```

---

# 10. Resource Type

This:

```yaml
Type: AWS::S3::Bucket
```

specifies the type of AWS resource.

Examples:

```text
AWS::S3::Bucket
AWS::EC2::Instance
AWS::RDS::DBInstance
AWS::EC2::VPC
AWS::EC2::Subnet
```

So:

```text
Type
 ↓
What AWS resource should CloudFormation create?
```

---

# 11. Properties

Resources can have properties.

For example:

```yaml
Resources:

  MyInstance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: t3.micro
      ImageId: ami-xxxxxxxx
```

Conceptually:

```text
Resource
   ↓
EC2
   ↓
Properties
   ├── Instance Type
   └── AMI
```

Properties specify how the resource should be configured.

---

# 12. Parameters

Suppose you don't want to hard-code values.

You can use **Parameters**.

Example:

```yaml
Parameters:

  InstanceType:
    Type: String
    Default: t3.micro
```

Then:

```yaml
Resources:

  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !Ref InstanceType
```

Now you can provide a different instance type when creating/updating the stack.

For example:

```text
Development → t3.micro

Production → larger instance
```

This makes templates reusable.

---

# 13. Outputs

**Outputs** allow a CloudFormation stack to return useful information after resources are created.

For example:

```yaml
Outputs:

  BucketName:
    Value: !Ref MyBucket
```

The output could provide information such as:

```text
Bucket name
Load Balancer DNS name
VPC ID
Subnet ID
```

Think:

> **Outputs = information you want to get from the stack.**

---

# 14. CloudFormation and Dependencies

Imagine:

```text
VPC
 ↓
Subnet
 ↓
EC2
```

EC2 depends on the subnet.

CloudFormation can understand resource relationships and create resources in an appropriate order when dependencies are represented through references or dependencies.

Conceptually:

```text
Create VPC
   ↓
Create Subnet
   ↓
Create EC2
```

This is another advantage over manually performing a long sequence of infrastructure operations.

---

# 15. Updating Infrastructure

One of the useful things about CloudFormation is that you can modify your template.

For example, initially:

```text
EC2 = t3.micro
```

Then change the configuration:

```text
EC2 = t3.medium
```

and update the stack.

CloudFormation determines what changes need to occur based on the updated template and resource properties.

Conceptually:

```text
Old Template
     ↓
Current Stack

New Template
     ↓
CloudFormation
     ↓
Determine changes
     ↓
Update resources
```

---

# 16. CloudFormation Change Sets

Before making certain stack updates, **Change Sets** can help you preview the changes CloudFormation intends to make.

For example:

```text
Current infrastructure
        ↓
New template
        ↓
Change Set
        ↓
Review proposed changes
        ↓
Execute
```

This is useful because infrastructure changes can have significant consequences.

---

# 17. CloudFormation Rollback

Suppose a stack update fails.

CloudFormation can use rollback behavior to return resources to a previous working state in applicable scenarios.

Conceptually:

```text
Existing Stack
      ↓
Update
      ↓
Something fails
      ↓
Rollback
      ↓
Previous state
```

This is one reason CloudFormation is useful for controlled infrastructure management.

---

# 18. CloudFormation and IaC

CloudFormation is an example of **Infrastructure as Code**.

The relationship is:

```text
Infrastructure as Code
        │
        ├── CloudFormation
        │
        └── Terraform
```

CloudFormation is specifically designed for AWS infrastructure.

Terraform can manage infrastructure across multiple providers.

---

# 19. CloudFormation vs Terraform

This is something you'll encounter frequently.

| Feature           | CloudFormation          | Terraform                     |
| ----------------- | ----------------------- | ----------------------------- |
| Developer         | AWS                     | HashiCorp                     |
| Type              | IaC                     | IaC                           |
| AWS support       | Native                  | Yes                           |
| Multi-cloud       | Not its primary purpose | Yes                           |
| Template language | YAML / JSON             | HCL                           |
| AWS integration   | Native                  | Provider-based                |
| Main use          | AWS infrastructure      | Multi-provider infrastructure |

### Simple memory:

> **CloudFormation = AWS-native IaC**

> **Terraform = multi-cloud IaC**

# 25. Important Concept: Infrastructure Drift

Suppose CloudFormation created:

```text
EC2 → t3.medium
```

But someone manually changes the resource outside CloudFormation.

Now:

```text
CloudFormation configuration
          ≠
Actual AWS infrastructure
```

This difference is called **drift**.

CloudFormation provides drift detection capabilities to identify differences between the expected configuration and actual resource configuration for supported resources.

Memory:

> **Drift = actual infrastructure has moved away from the configuration CloudFormation expects.**

# 27. When Should You Use CloudFormation?

Use CloudFormation when you want to:

* Automate AWS infrastructure deployment
* Reproduce environments
* Standardize architectures
* Manage infrastructure as code
* Track infrastructure changes through Git
* Reduce manual configuration
* Deploy many AWS resources together
* Integrate infrastructure with CI/CD
* Manage AWS-native infrastructure consistently

---

# 28. When Would You Not Need It?

For example, you're simply experimenting with AWS and want to quickly create one S3 bucket.

You can use:

```text
Console
```

or:

```bash
aws s3 mb ...
```

You don't necessarily need CloudFormation for every tiny operation.

But once infrastructure becomes **repeatable, complex, shared, or production-oriented**, IaC becomes much more valuable.
