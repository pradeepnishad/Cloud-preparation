# VMs vs Containers

## 1. Definition

### Virtual Machine (VM)

A **VM** is a virtualized computer that runs its own operating system on top of a **hypervisor**.

```text
EC2 Instance
 └── Hypervisor
      └── Host OS
           └── VM
                ├── Application
                ├── Libraries
                └── Packages
```

Each VM generally carries its own OS environment, which requires more resources.

### Container

A **container** is a lightweight isolated environment that packages an application together with its required libraries, packages, and dependencies.

Containers share the **host operating system kernel** rather than requiring a complete guest OS for every application.

```text
EC2 Instance
 └── Host OS
      └── Docker Daemon
           ├── Container → Django
           ├── Container → MongoDB
           └── Container → RabbitMQ
```

---

## 2. Why use Containers?

The screenshot highlights that containers allow multiple applications to run in **virtually isolated environments**.

Each container can have its own:

* Application
* Libraries
* Packages
* Binaries
* OS dependencies

This helps prevent dependency/configuration conflicts between applications.

### Example

Suppose you have:

```text
Application A → Django
Application B → MongoDB
Application C → RabbitMQ
```

Instead of installing everything directly on the same environment, you can run:

```text
Container 1 → Django
Container 2 → MongoDB
Container 3 → RabbitMQ
```

Each application gets its own isolated environment and dependencies.

## 3. VM vs Container

| Feature                  | VM                               | Container                           |
| ------------------------ | -------------------------------- | ----------------------------------- |
| Virtualization           | Hardware/VM level                | OS-level                            |
| Main component           | Hypervisor                       | Container runtime/daemon            |
| OS                       | Each VM generally has its own OS | Containers share host OS kernel     |
| Resource usage           | Higher                           | Lower                               |
| Startup                  | Generally slower                 | Generally faster                    |
| Isolation                | Strong isolation                 | Process/application-level isolation |
| Application dependencies | Inside VM                        | Inside container                    |
| Density                  | Fewer workloads per host         | More workloads per host             |

## 4. Scenario

Imagine an EC2 instance with limited resources.

### VM approach

```text
EC2
 ↓
Hypervisor
 ↓
VM 1 → Django + OS
VM 2 → MongoDB + OS
VM 3 → RabbitMQ + OS
```

Each VM requires its own OS environment, creating additional overhead.

### Container approach

```text
EC2
 ↓
Host OS
 ↓
Docker
 ├── Django container
 ├── MongoDB container
 └── RabbitMQ container
```

The containers share the host OS kernel while maintaining separate application environments.

This can leave more resources available for workloads, as illustrated in the source.

---

## 5. When to use Containers

Containers are particularly useful when you want:

* Application isolation
* Consistent application environments
* Different dependency versions
* Lightweight workloads
* Fast deployment/startup
* High application density
* Microservices architectures

For example:

```text
Frontend → Container
Backend  → Container
API      → Container
Worker   → Container
```

Each component can be developed, deployed, and scaled independently.

## 6. AWS Connection

In AWS, you can run containers using services such as:

* **Amazon ECS** → container orchestration
* **Amazon EKS** → managed Kubernetes
* **AWS Fargate** → serverless compute for containers
* **Amazon ECR** → container image registry

A simple architecture could be:

```text
Developer
   ↓
Docker Image
   ↓
Amazon ECR
   ↓
ECS / EKS
   ↓
Containers
```

## 7. Important distinction

### VM

> **Virtualize the machine**

### Container

> **Package and isolate the application**

Think:

**VM = Full computer**
**Container = Application environment**

---

## Summary

* **VMs** provide virtual machines using a hypervisor.
* VMs generally require their own operating-system environment, increasing resource overhead.
* **Containers** package applications with their dependencies.
* Containers share the host OS kernel and provide process/application-level isolation.
* Containers are generally lighter and allow more workloads to run on the same infrastructure.
* **EC2** can be used as the underlying compute platform for both VMs and container workloads.
* **ECS/EKS/Fargate** are AWS services commonly used for running containers.
* **ECR** stores container images.

**Container → Host OS → Container Runtime → Application**
