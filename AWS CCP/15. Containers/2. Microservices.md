# What are Microservices?

## 1. Definition

**Microservices architecture** is an architecture where an application is divided into **multiple smaller applications/services**, with each service responsible for a specific business function.

From your screenshot:

> **Microservices:** Multiple apps, each responsible for one thing.

The key idea is **separation of functionality**.

---

## 2. Monolithic vs Microservices

### Monolithic Architecture

A monolithic application is essentially **one application responsible for everything**.

```text
                 Monolithic Application
 ┌─────────────────────────────────────────┐
 │ Load Balancing │ Caching │ Database     │
 │─────────────────────────────────────────│
 │ Marketing                               │
 │ HTML/CSS │ JavaScript │ Assets          │
 │─────────────────────────────────────────│
 │ Frontend                                │
 │ JS Framework │ HTML Templates            │
 │─────────────────────────────────────────│
 │ Backend                                 │
 │ API │ ORM │ PDFs │ Reports │ Thumbnails │
 └─────────────────────────────────────────┘
```

The functionality is **tightly coupled**.

If one part needs significant changes, it can affect the overall application.

---

### Microservices Architecture

Instead of one large application:

```text
             Microservices
                  │
 ┌────────────────┼─────────────────┐
 │                │                 │
Load Balancing  Caching          Database
 │
 ├── Frontend
 │    ├── HTML/CSS
 │    ├── JavaScript
 │    └── Assets
 │
 ├── API Service
 │
 ├── PDF Service
 │
 ├── Thumbnail Service
 │
 └── Reports Service
```

Each service is responsible for a specific function.

The screenshot describes the functionality as **isolated and stateless**.

---

## 3. Why use Microservices?

The main reason is to **separate application functionality into smaller, independent services**.

For example, instead of:

```text
One application
 ├── PDF generation
 ├── Reports
 ├── Thumbnails
 ├── API
 └── Frontend
```

you can have:

```text
PDF Service
Reports Service
Thumbnail Service
API Service
Frontend Service
```

Each service can be developed and operated separately.

---

## 4. Scenario

Imagine an e-commerce application.

### Monolithic

```text
E-Commerce Application
 ├── Users
 ├── Products
 ├── Payments
 ├── Orders
 ├── Notifications
 └── Reports
```

Everything is part of one application.

### Microservices

```text
                 E-Commerce
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
 User Service   Product Service  Order Service
       │             │             │
       ↓             ↓             ↓
 Payment Service  Notification Service
```

For example, the **Notification Service** can be responsible only for sending notifications.

The **Order Service** handles orders.

The **Payment Service** handles payments.

## 6. Monolithic vs Microservices

| Monolithic                                     | Microservices                                   |
| ---------------------------------------------- | ----------------------------------------------- |
| One large application                          | Multiple smaller services                       |
| Functionality tightly coupled                  | Functionality separated                         |
| One application responsible for many functions | Each service focuses on a specific function     |
| Changes can affect larger parts of application | Services can be developed independently         |
| Usually simpler to start                       | More distributed-system complexity              |
| Scaling can involve the whole application      | Individual services can be scaled independently |

---

## 7. Important Concept: Stateless

Your screenshot specifically mentions **stateless** microservices.

A stateless service does not depend on information stored in its own local memory between requests.

For example:

```text
Request 1 → Service A
Request 2 → Service B
Request 3 → Service A
```

The application should not require Service A to remember the previous request locally.

State can instead be stored in an external system such as a database or cache.

---

## 8. When to use Microservices

Microservices are useful when an application has multiple distinct functions that benefit from being developed, deployed, or scaled independently.

For example:

* Large applications
* Distributed applications
* Independently scalable components
* Teams working on different services
* Cloud-native architectures

However, microservices also introduce additional complexity because you now have multiple services communicating over a network.

---

## Summary

**Monolithic:**

> One application → many responsibilities → tightly coupled

**Microservices:**

> Multiple applications/services → individual responsibilities → isolated functionality
